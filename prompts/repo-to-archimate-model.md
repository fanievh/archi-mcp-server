# Prompt — Generate a full ArchiMate model from a code repository

> **How to use:** Paste everything below the line into an agent session that has the **Archi MCP Server** tools connected and an Archi model **open**. Replace `{{REPO_PATH}}` with the absolute path (or git URL) of the repository to model. The agent should also have read access to that repository (a coding agent with filesystem/git tools, or the repo checked out locally).

> ⚠️ **This file is the source of truth. Two self-contained copies are installed as the `/repo-to-archi` slash command** — `~/.claude/commands/repo-to-archi.md` (user-level, any folder) and `.claude/commands/repo-to-archi.md` (project-level, committed). They **embed** this prompt and do **not** auto-update. **After editing this file, re-sync both command copies** (they additionally carry a `$ARGUMENTS` repo-path token and a remote-URL clone step in place of the `{{REPO_PATH}}` placeholder). Ask Claude to "re-sync the repo-to-archi command" and it will copy the body across.

> 📁 **Canonical home.** The source of truth for this prompt now lives in the top-level `prompts/` folder — the first entry in a shared prompt-library convention that is mirrored across the project's repositories.

## ROLE

You are a software architect who reverse-engineers a codebase into a well-formed, multi-layer **ArchiMate 3.2** model using the **Archi MCP Server** tools. You produce a model an architect would accept on review: correct concept choices, valid relationships, honest about what is observed versus inferred, and laid out so the views are actually readable.

## INPUT

- **Repository:** `{{REPO_PATH}}`
- **Version / ref (optional):** `{{REPO_REF}}` — a **tag, release, branch, or commit** to model instead of the current checkout. If set, obtain a **non-destructive** checkout of it and analyse that, never the live working tree: for a local repo `git -C {{REPO_PATH}} worktree add --detach <tmp> {{REPO_REF}}` (remove the worktree when done); for a URL `git clone --depth 1 --branch {{REPO_REF}} <url> <tmp>` (tag or branch), or a full clone + `git checkout {{REPO_REF}}` for a bare commit SHA. Record the resolved ref/commit in the model (a model property or root note) and in the final report. Leave empty to analyse the current checkout / default branch.
- **Target:** the Archi model currently open in the connected Archi MCP server.

## OBJECTIVE

Populate the open model with **elements, relationships, folders, views, view objects, and view connections** that cover the architecture and design of the solution in the repository, across **as many ArchiMate layers as the evidence supports**. Code primarily evidences the **Application** and **Technology** layers; **Business**, **Motivation**, **Strategy**, and **Implementation & Migration** are included where the repository's **docs state them** or where they can be **reasonably inferred**, and every concept records *how strongly it is grounded* — `code`, `documented`, or `inferred` (and, for `inferred`, whether it is *structural* — reproducible from the code — or *speculative*; see *Evidence marking*).

**Scope boundary — model what the code IS; report (don't grade) what it lacks.** This run produces a faithful structural/behavioural *representation* of the repository, not an architecture-quality verdict. Where you can evaluate the architecture against design/analysis lenses (quality attributes, design patterns, NFRs/SLAs), **report evidenced facts and evidenced absences** ("layered into 4 packages with enforced imports"; "no documented availability target found") but **withhold quality judgements** ("leaky", "over-used", scored ratings) — a tool that met the repo minutes ago has no standing to grade it, and one wrong verdict poisons trust in the faithful model. Tell the reader up front that the design/quality lens is a *gap-surfacing aid for their own review*, not an assessment. See *Architecture-aspect coverage* and the final report.

## HOW TO READ THIS PROMPT — GATES vs GUIDANCE

This prompt carries two kinds of rule, and a long run under cost pressure blurs them. Read them differently:

- **GUIDANCE** (the default, the bulk of this prompt) — judgment exercised under the principles. Adapt it to the repo; a logged, reasoned deviation is correct. Guidance carries hedge-words on purpose ("prefer", "usually", "recommended", "where it helps") — they signal room to think.
- **GATE** — a hard pass/fail check on the *artifact*. A gate is stated **without hedge-words**: if its condition is unmet, the draft is **not ready** — fix it, or record a **named, explicit exception** in the final report (which gate, which view/element, why). "I ran low on budget" is not an exception. Every past failure of this prompt clustered on gates that read like guidance — a skipped glyph, notes never re-assessed, an unnamed note edited by guessed ID — so the gates are pulled out of the prose and listed once here and again at close-out (Phase 7).

**Gate manifest — the hard checks; every one green before the draft is presented.** Each gate is *defined* in full where cited; this table is the load-bearing index, not the definition.

| # | Gate | Pass condition (falsifiable) | Defined in |
|---|---|---|---|
| **G1** | Read-only until build | No mutating call before Phase 3; full analysis precedes the first write. | Phase 0–2; *Constraints* |
| **G2** | Model open | `get-model-info` confirms an open model, or the run **stops**. | Phase 0.1 |
| **G3** | Evidence on every element | Every element carries `evidence` + `evidenceMark` + `source` + the `Evidence:` doc line; grade is weakest-link; every `inferred` carries `inferenceType` (and `structural` ⇒ a non-empty `evidenceSignal`). | *Evidence marking* |
| **G4** | Glyph on every placed object | Every element view-object carries the channel-4 `labelExpression` glyph (or its ASCII fallback on a genuine render failure). | *Evidence marking* ch.4; Phase 4.3 |
| **G5** | No invention | No on-canvas element without a scanned-anchor citation; `inferred-speculative` is never drawn. | *Completeness contract* Gate 3 |
| **G6** | Every candidate dispositioned | Each Phase-1 candidate resolves to captured / consciously-folded / deemed-insignificant / absent-for-cause — none silent. | *Completeness contract* Gate 2 |
| **G7** | Onion spine bound | When `onion = stack`, the same unit at L0/L1/L2 is joined by a decomposition edge (or nesting). | Phase 4; *Constraints* |
| **G8** | Behaviour branches shown | A multi-path scenario renders a named branch marker (OR-junction) and/or an augmenting diagram — never a silent happy-path linearisation. | Phase 4 behaviour-fidelity gate |
| **G9** | Junction render-clean | Every junction ≈14×14; no junction renders oversized and no connection label sits on a junction's fill (confirmed by export, not the metric). | *Constraints* (junctions) |
| **G10** | Notes auto-fit | Every note/legend is created and edited **without** a `height` parameter, so the server auto-fits and the text never clips. | *Evidence marking* (sizing the note) |
| **G11** | Terminal close-out per view | After **any** pass that adds/moves/resizes/styles a view object — notes and images included — the **final** action on that view is `assess-layout` **and** an eyeballed `export-view` PNG. The render is authoritative. | Phase 6 (close-out gate) |
| **G12** | Fresh IDs for unnamed objects | After any compaction, and for every unnamed object (note, image, junction, group), IDs are re-queried from `get-view-contents` and disambiguated by content/geometry — never inferred from batch position or memory. | *Working mode*; *Constraints* |
| **G13** | Provenance never blurred | No creative rendering makes a `documented`/`inferred` concept read as a `code` fact; the evidence grade survives every presentational choice. | *Constraints* (clarity vs purity) |
| **G14** | First-gen is a draft | The first generation ends at the Phase-7 close-out checkpoint — never presented as finished. | Phase 7 |

Everything not in this table is guidance: optimise it for the reader, log the deviations, move on.

## METHOD — work in phases. Do not skip the preflight or the verify.

> **Working mode — iterative, resumable, model-as-checkpoint.** A full-repo run is long; assume your context may be compacted or the session may end before you finish. **Do not treat your conversation memory as the source of truth — the open Archi model is the durable checkpoint.** Work so any interruption is recoverable:
> - **Commit in small batches.** One `bulk-mutate` per subsystem (its elements + relationships) and per view. Each batch is atomic (a failed batch applies *nothing* — no half-states) and persists durably on success. Never carry a large body of uncommitted work across many steps.
> - **Resume by diffing, every run.** At the start of *every* run — first or resumed — redo the read-only preflight + Phase 1 analysis (both deterministic and cheap) to regenerate the target inventory, then **diff it against the live model** (`get-model-info`, `get-folders`, `get-views`, `search-elements`) and act only on the gap. `get-or-create-element` / `search-and-create` / search-before-create make re-creation a safe no-op.
> - **Re-query IDs; never trust remembered ones (gate G12).** After any compaction, fetch IDs fresh (`search-elements`, `get-view-contents`) instead of reusing IDs captured earlier in the conversation — they may have fallen out of your context or be stale. **This binds hardest for *unnamed* objects — notes, images, junctions, groups** — which `get-view-contents` returns but which carry no name to match on: identify them by **content and geometry**, never by their position in an earlier `bulk-mutate` batch (assuming "note 2 of 3" by batch order is exactly how a legend gets moved into a routing lane and overwritten with a band-label's text while a sibling clips). Re-read the view before editing any of them. And when you edit a note, **omit `height`** so the server's auto-fit still runs — an explicit height silently disables the fit and clips the text (see *Evidence marking → Sizing the note*, gate G10).
> - **Stable names = resumability.** Name every element deterministically from the code's own terms, so a resumed run's search-before-create matches what already exists. Unstable or paraphrased names silently create duplicates.
> - **Order for coherence.** Within each subsystem: elements → relationships → views. Whatever exists at any interruption is then internally consistent and independently useful.
> - **Optional durable progress marker.** Record a short build-status list (subsystems/views done) in a model/root-folder property or a single note, so the next context can read where you stopped — though the presence of the elements and views is itself the ledger.

### Phase 0 — Preflight (read-only)
1. List the available MCP tools and confirm the Archi tools are present. Call `get-model-info` to confirm a model is open and capture its name. If no model is open, **stop** and tell the user to open or create one.
2. Call `get-folders` (or `get-folder-tree`) and `get-views` to see what already exists. **Do not duplicate.** If the model is non-empty, prefer `get-or-create-element` / `search-and-create` and reconcile against existing content rather than blindly adding. **This is also the resume step:** if the model already holds part of *this* build (from an earlier interrupted run), treat what exists as done and continue only the gap — see *Working mode* above.
3. **Discover the server's own guidance resources — they are authoritative; this prompt defers to them.** Via the MCP resource mechanism, list resources and read `archimate://recipes/index` (view-shape decision table + the invariant build sequence), `archimate://reference/archimate-layers` (element-type decision aid), `archimate://reference/archimate-relationships` (valid relationships), and `archimate://reference/archimate-view-patterns` (layout rules). Fetch a specific `archimate://recipes/<family>` page later, only when a view matches it. If these resources are unavailable, fall back to this prompt's heuristics and layout guidance.
4. **Probe the environment's verification capabilities once, and record them.** Test for a text-search tool (`rg --version` || `grep --version`) and for any code-intelligence / call-graph index over the repo (an MCP code-analysis tool, a generated index). Record model properties `repoToArchi.tooling.search` = `rg` | `grep` | `none` and `repoToArchi.tooling.callgraph` = `<name>` | `none`. These gate later verification: **with no search tool you may not assert a falsifiable "searched and found nothing" result** — see *Verify drawn dependencies* and *Architecture-aspect coverage*. Do not assume any of these tools is present (a general repo may have none); degrade honestly when they are absent.

### Phase 1 — Analyse the repository (read-only, build a model in your head first)
Read the repo at `{{REPO_PATH}}` and extract architecture signals (if a `{{REPO_REF}}` version was requested, read from the non-destructive checkout of that ref, per *Input* — not the live working tree). Look at, in roughly this order:
- **`README`, `/docs`, ADRs, design notes** — stated purpose, stakeholders, goals, constraints, decisions. Anything the docs assert explicitly is `documented` evidence (the team's own words), not something you need to infer — prefer it over deduction wherever it covers the same concept.
- **Build/manifest files** — `pom.xml`, `build.gradle`, `package.json`, `go.mod`, `*.csproj`, `requirements.txt`, `Cargo.toml`, etc. → modules, services, and **external dependencies** (frameworks, drivers, SDKs).
- **Top-level directory layout** — modules, services, bounded contexts, layered packages.
- **Entry points & interfaces** — `main`/bootstrap, HTTP/gRPC controllers, route tables, message consumers, CLI commands, public API surface, OpenAPI/proto/GraphQL schemas.
- **Domain model** — entities, aggregates, value objects, DB schemas/migrations, ORM mappings → data and business objects.
- **Integration & infra** — `Dockerfile`, `docker-compose.yml`, Kubernetes/Helm, Terraform/Pulumi, CI config, `.env`/config → datastores, brokers, caches, runtimes, deploy topology.
- **Inter-module dependencies** — import/call graph between the units above → relationships.
- **Runtime behaviour** — trace **1–3 key end-to-end scenarios** (request-handling pipeline, an event flow publish→consume, a job/orchestration sequence) through controllers/handlers/consumers → ordered `Process`/`Function`/`Event` steps and who performs each. These feed the behaviour/process-flow views in Phase 4; without them the model is all structure and no behaviour.

Produce a short internal inventory: candidate **components, services, interfaces, functions, data objects, nodes, artifacts, external systems**, and the **dependencies** between them. **Do not create anything yet.**

**Also run the per-altitude anchor scan** — for each altitude, name the *evidence anchors* you scanned and enumerate the candidate significant units they surface (you do this now; it grounds the Phase 1.5 altitude recommendation *and* seeds the per-altitude completeness contract, so neither is a flat default). The anchors differ per altitude — and crucially, **L0/L1 candidates come largely from the docs, not the code**:
- **L0 Context** — *anchors:* capability map, context / C4-context diagram, reference/conceptual architecture, the README's "what is this / who uses it", domain glossary, mission/scope, `SECURITY.md`. *Candidates:* the deployable(s) as a system-in-context, the external systems/actors they integrate, named business capabilities/services. Mostly `documented`-grade.
- **L1 Landscape** — *anchors:* ADRs, stated layer/tier policy, module / bounded-context overview docs, named patterns asserted in prose (hexagonal, layered, event-driven), topology docs, interface contracts (OpenAPI / proto) — **unioned with** the natural clusters of L2 units. *Candidates:* deployables × their major subsystems (services / bounded contexts / distinct-responsibility packages), logical components, the Motivation principles/constraints. A documented subsystem with no code under it is still a candidate (and a finding worth a line).
- **L2 Component** — *anchors:* build graph / dependency manifest, package & module boundaries, public API surface, the class/artifact inventory. *Candidates:* addressable internal components one level finer, artifacts, data objects, nodes. Mostly `code`-grade.
- **Record "not scanned" distinctly from "scanned and empty"** — an anchor that exists but went unscanned is a hole in the census, not an absence of content; the completeness contract treats the two differently.
- **Flag** any top-decile fan-out / hub units (a few units that wire to many) — they drive readability more than raw counts.

### Phase 1.5 — Confirm altitude depth, onion scope, and (if rich docs exist) model intent — once, first run only

**Resumability first — the model is the source of truth, not this conversation.** Before asking anything, read the model properties `repoToArchi.altitude`, `repoToArchi.onion`, and `repoToArchi.docMode` (set on the model root). **If present → this is a resume:** adopt them silently, never ask again. **If absent → first run:** proceed with the single checkpoint below. **If no answer arrives** (non-interactive / unattended run) → record the recommendation as the chosen value and continue, noting in the final report it was *auto-selected, unconfirmed*. **Never block on this.**

**Size the work, and treat first-gen as a draft for review.** From the Phase-1 anchor scan, set an effort tier (record `repoToArchi.effortTier` and restate it in the report): **S** (≤~15 significant units, 1–2 clusters) — one pass suffices; **M** (~15–40 units, 3+ clusters, or sparse docs) — expect several passes and at least one self-review against the completeness contract before the draft is ready; **L** (>40 units, multiple bounded contexts, or rich docs) — do **not** finish in one pass: build the L0/L1 spine, then surface the deeper L2/L3 candidates at the close-out checkpoint rather than silently skipping them. The tier is explicit permission to spend the time the complexity warrants — a cheap flat-and-finish pass is never the default for M/L, and running long on a large repo is correct, not a failure. **First generation ends at the close-out checkpoint (Phase 7), not at a model presented as complete.**

| Tier | Triggers (any one raises the tier) | Working pattern |
|---|---|---|
| **S** | ≤~15 significant units · 1–2 clusters · single deployable · thin/absent docs | One pass; floor + index; a single L0/L2 onion is legitimate. |
| **M** | ~15–40 units · 3+ clusters · sparse but real docs · 2–3 repo-class facets | Several passes; ≥1 self-review against the completeness contract + aspect coverage before the draft is ready; don't default to flat. |
| **L** | >40 units · multiple bounded contexts/services · rich architecture docs · high top-decile fan-out | Don't one-shot; build the L0/L1 spine first, surface deeper L2/L3 candidates at close-out. Running long is correct. |

Mixed signals → take the **higher** tier.

**Altitude is the *floor*, not a single picked level.** The model is an onion: it orients the reader at **L0 Context** (the big picture), then peels to **L1 Landscape**, then to **L2 Component**, each as its own view(s). The altitude question decides only *how deep the onion goes* — its deepest, most-detailed level. **Recommend the deepest level whose own view stays within the readability budget (~25–40 elements/view)**, grounded in the Phase 1 anchor scan; detail finer than that, for a single complex subsystem, is a *zoom view*, not a deeper floor for everything (see *Zoom in where it matters*). The per-view budget governs each view's density — it **no longer forces the whole model down to one level**, because each altitude gets its own view and its own budget.

**Onion scope — produce the full L0→floor stack, or a single level?** The default for a richly-documented solution is the **full stack** (`onion = stack`): L0 and L1 carry the abstract, conceptual, reference-architecture content that lives in the *docs*, not the code, and guide the reader big-picture-first. A thin repo with no conceptual/architecture docs has nothing true to put above the code structure → a **single level** at the floor (`onion = single`) is honest, and refusing to peel an onion that has no inner layer is correct, not a gap. Record as model property `repoToArchi.onion` = `stack` | `single`.

**Checkpoint = one confirm, not an interrogation.** Put every question in the *same single checkpoint*, each pre-selected to its recommendation so a one-word reply or silence accepts all:
1. **Altitude floor** — state the recommendation in one sentence; offer one finer and one coarser alternative, each costed in approximate element count and honest about *what folds away* at that rung.
2. **Onion scope** — `stack` vs `single`, pre-selected by doc-richness (substantial conceptual/architecture docs → `stack`; thin → `single`): *"Build the full L0→L«floor» onion stack from the architecture docs, or a single-level model at L«floor»?"*
3. **docMode** — only when substantial docs exist (next paragraph).

**Ambiguity gate:** where one option clearly dominates (the alternatives are degenerate), skip *that* sub-question, auto-pick, and state the choice loudly with an easy-correction affordance ("say the word to change"). **Record `repoToArchi.altitude`, `repoToArchi.onion`, and `repoToArchi.docMode`** so the next run resumes silently.

**docMode — only when Phase 1 found substantial tech docs** (`docs/architecture.md`, an ADR set, a real `/docs`). Does the model **complement** the docs (lean on them; mark `documented` elements with a doc-ref property; overlap = shared names/anchors only; do **not** duplicate doc prose) or stand as an **independent** asset (absorb doc-stated concepts that fit the agreed altitudes *into* the model, still evidence-graded `documented`, lifting documented invariants/principles/constraints into the Motivation layer rather than leaving them doc-only)? **Default = independent** when good docs exist (the richer asset — it captures doc-stated intent the code cannot show; pick **complement** to keep the model lean and point at the docs in place). Record as model property `repoToArchi.docMode` = `complement` | `independent`. If no substantial docs exist, skip this sub-question (and `onion` defaults to `single`).

**Wire docMode into the build (Phase 3):** in **complement** mode, give each `documented` element a `source`/doc-ref property pointing at where the doc states it (e.g. `docs/architecture.md#4-layer-architecture`) and do not restate the doc's prose in the model. In **independent** mode, additionally lift documented invariants / principles / constraints into the model (e.g. Motivation **Principle**/**Constraint** elements) at the agreed altitudes — so stated rules (like a strict layer-import policy) are captured, not left doc-only. **How this is *proven* is the per-altitude completeness contract (below): the former independent-mode "non-empty invariant source set yielding zero Motivation elements is a contract failure" check is now one instance of that general, every-level gate.**

### Phase 2 — Map to ArchiMate (decide concepts and relationships)
First apply the **Level of detail** significance test (below) to decide what earns an element *at all* — model significant units at a consistent altitude and fold implementation detail (helpers, DTOs, glue) into the unit that owns it. Then, for each surviving candidate, apply the mapping heuristics below to decide the **layer**, the **element type**, the **evidence** value, and the **relationships** it participates in. Prefer fewer, accurate concepts over many speculative ones. Use the project's **ubiquitous language** for names (match code/domain terms), not invented marketing terms.

### Phase 3 — Create the model content (folders → specializations → elements → relationships)
1. **Folders carry the onion's *levels*; the canvas carries the ArchiMate *layers* — two orthogonal axes, kept on different controls so the reader never fuses them.** Group the **views** (Phase 4) into level sub-folders of the Views folder that sort in reading order for free — `L0 · Context`, `L1 · Landscape`, `L2 · Component` (Archi sorts alphabetically, so the `L0/L1/L2` prefix *is* the journey order). The ArchiMate **layer** (Business / Application / Technology / Motivation) is read *spatially on each view* — bands, lanes, colour — **not** via folders. Keep **elements** in Archi's native layer-based folders, sub-grouped by **service / bounded context / subsystem** with `create-folder` (nest with the parent folder id); demote any further layer sub-foldering to a secondary level, used only where an `L2` component count gets large. Keep names domain-meaningful. (When `onion = single`, create just the one level folder for its view(s).)
2. **Specializations (create *before* elements so the batches can apply them):** create the two evidence stereotypes — **«documented»** and **«inferred»** — with `create-specialization` (code-grounded elements stay unspecialized). Also create repeating domain stereotypes that ArchiMate lacks a native type for (e.g. «microservice», «REST API», «message topic», «database») so the model reads cleanly.
3. **Elements & relationships:** create in **batches** with `bulk-mutate`, using `$N.id` back-references so a relationship in the same batch can point at an element created earlier in the batch. Group batches by subsystem to keep them reviewable. On every element set, per *Evidence marking*: the `evidence` property, the `evidenceMark` glyph property, the optional `source` property, an `Evidence: …` line in the `documentation` field, and (for `documented`/`inferred` only) the matching specialization from step 2. Carry `evidence` onto relationships too where the tool allows properties. **Also fill the per-element `documentation` prose now** (What / Responsibility / Collaborators, plus Rationale / Caveat where the evidence earns them) so it is deterministic and resume-stable — see *Level of detail → Document each element as prose* (relationships get the lighter Evidence + Meaning form). **Write a literal `&` / `<` / `>` in every name and label — never the HTML entity `&amp;` / `&lt;` / `&gt;`** (Archi stores the literal entity text; the JSON-muscle-memory `&amp;` is a recurring footgun — canonical rule in *Constraints & guardrails → Junctions, folders & `&` literals*).
4. **Validation-sync rule:** the server enforces **Archi's own** relationship-validity rules — it is never stricter nor more lenient than the Archi GUI. If a relationship is rejected, the source/target/type combination is invalid in ArchiMate; **pick a valid alternative** (e.g. fall back from *Triggering* to *Association*) rather than retrying the same call. Report any concept you wanted but could not legally express.

### Phase 4 — Build views (recipe-driven; scale the count to the repo)

**Use the server's viewpoint recipes — do not re-derive layouts.** The model now exists; views are governed by `archimate://recipes/index` (read in Phase 0): a Step-0 decision table (conventional vs non-conventional shape) and the **invariant build sequence** every view runs.

**Build the onion as a stack of views, peeling top-down (when `onion = stack`).** Each *earned* altitude gets its own view(s) — and a level **earns** a view only when it carries **distinct, evidence-backed content**. Emitting an L1 that is just L0 with the boxes nudged apart breaks the reader's trust in *every* level boundary, so skip it: a small system may legitimately ship **L0 + L2 and skip L1**. The lever is "emit a level when there's evidence to fill it," never a quota of three. Name views so they sort by level then sequence, the number echoing the folder so a deep-linked title is self-locating:
- `0 · Start Here` (sorts first)
- `L0 · Context` → e.g. `0.0 · System in Context`
- `L1 · Landscape` → `1.0 · Capability Map`, `1.1 · Application Landscape`, `1.2 · Deployment Landscape`
- `L2 · Component` → `2.1 · «Subsystem» — Components`, `2.2 · …`

**Tag every view with its altitude** via the view property `repoToArchi.level` = `L0` | `L1` | `L2` — this is what makes the "every significant element sits on a *level-appropriate* view" check mechanical (see *Per-altitude completeness contract*). Within each level, scale the view count to the codebase (a single service's L2 may be one view; a multi-service repo's L2 is one application-structure view per service / bounded context). When `onion = single`, produce only the floor level's view(s) plus, if warranted, the index.

**L2-orphan check — do this in Phase 4, as you build, not at close-out.** Every L2 element you create needs either its own zoom view **or** an explicit *fold* (shown nested on its parent's view) / *defer* (recorded as a close-out breadth candidate). An L2 element that exists in the model but lands on **no** view is an **orphan** — catch them while building each subsystem's view, not at the Phase-6 gate (where a past run caught its Response/DTO orphans late).

**The onion's spine — bind the same element across altitudes.** L0's system node, L1's subsystem, and L2's components are the **same elements** shown at different granularity (one ArchiMate element can appear on many views — use that), bound by a durable decomposition relationship so the model navigates as one onion rather than three disconnected drawings. The relationship *type* is your call — **Composition/Aggregation is the idiomatic decomposition; nesting is acceptable** — but the **binding itself is not optional**. Without it, "three views" is three posters on a wall, and a later editor can't tell L1 is a decomposition of L0 rather than a parallel invention.

**The Why-spine — stratify the *why* across altitudes, mirroring the structural onion.** Rationale obeys the same floor discipline as structure: don't pour all motivation into one level (the recurring failure is dumping the whole "why" into L1). Stratify the Motivation layer top-down — **L0 carries the single apex Purpose** (*exactly one* Goal/Driver: the one-sentence reason the system exists), **L1 carries the Drivers/Goals** that decompose it, **L2 carries component-bound Requirements/Outcomes** only where a component earns one. Bind the spine with Motivation **realization/influence** relationships: every L1 driver traces up to the L0 Purpose, every L2 requirement to an L1 driver — an orphaned driver with no parent purpose is the tell that motivation was dumped at the wrong floor. Keep it **thin** — the failure mode here is over-population, not under: the significance test applies to Why elements too (one apex Purpose, a handful of L1 drivers, requirements only where they change a decision; a Motivation layer that mirrors every component is noise). **Source the apex Purpose from the README's *purpose statement*** (its "what is this / who uses it", or a Goals/Motivation/Overview section — wherever it sits, *not* positionally the first paragraph, which may be a badge wall or a quote), and **distil it to one architectural sentence — do not transcribe**: a README opening is human-rail copy written to persuade, so run it through a strip test (remove superlatives — *powerful/seamless/modern/robust/blazing-fast*; if nothing architectural survives — a problem, a user, a capability — it is marketing: re-derive from the doc body or fall to `inferred`). Mark the apex Purpose `documented` with its `source`; where no doc states intent and you infer it from code, mark it `inferred` and never let a code-implied "why" masquerade as stated intent. This is the Why instance of the per-altitude completeness contract and the two-rails provenance rule — not a new mechanism.

**Behaviour views are orthogonal to the onion** — model the **few key end-to-end scenarios** a newcomer must understand (typically 1–5), each placed at whichever altitude reads best (usually L1/L2), per the behaviour-process-flow recipe below. They are not a fourth level.

**Navigation / index view → a guided tour, not a switchboard (when the model is large).** If the model runs to more than ~4–5 views or a few dozen elements, create an **"Overview / Start Here"** view — **named so it sorts first** (prefix `0 · Start Here`; Archi lists views alphabetically). Make it *narrate the descent* rather than list views flatly: order the clickable view references (`add-view-reference-to-view`, double-click navigates) **top-down L0 → L1 → L2** with a half-line saying what each click gives the reader; host the **full evidence legend** here (a one-line key still goes on every view — see *Evidence marking*); and add a **short confidence line** that delivers the completeness story *without the audit* — e.g. *"Business, Application and Technology fully traversed; L0/L1 sourced from docs (see ◐); nothing material dropped silently."* The disposition **ledger itself stays in the run report and the model documentation field, never on the canvas** — show the reader the conclusion, keep the working out of the path (see *Per-altitude completeness contract* and *Final report*). Tiny models (1–2 views) skip the index.

**For each view:**
0. **Choose the layout mode before placing anything, and record why** (structure / landscape views). For any structure view with **more than ~10 elements**, pick and log one mode in the view property `repoToArchi.layoutRationale`: **`grouped` / `nested`** — native-group lanes (`add-group-to-view`) or element-nesting (`parentViewObjectId`), then `auto-layout-and-route mode:"grouped"` — **this is also ONE atomic call** (it runs `layout-within-group` → `arrange-groups` → `optimize-group-order` → `auto-route-connections` in one operation), so grouped is *not* more work than flat; or **`flat`** — reserved for small (≲10-element) structure views and behaviour/flow views, and a choice you must justify in the rationale and report (a flat dense structure view is the single biggest routing-quality risk — `nonOrthogonalTerminalCount` 6–19 flat vs ~0–1 grouped). `targetRating` escalates *spacing, not structure*, so it never rescues a should-be-grouped view — make the mode choice here, up front. Where it makes the onion spine *visible*, render the parent subsystem as a container nesting its components (see *the onion's spine*) rather than a flat list whose only tie to its subsystem is the view name.
1. **Classify it** via `archimate://recipes/index` Step 0. *Conventional* shapes (layered band-stack, landscape grid, hierarchy/tree, object bands, org structure) need **no recipe** — apply the `archimate://reference/archimate-view-patterns` principles. *Non-conventional* shapes — **fetch the one matching family page and match its topology block:**
   - `archimate://recipes/application-integration` — apps around an integration hub (ESB / API gateway / broker)
   - `archimate://recipes/behaviour-process-flow` — **a process flow + hand-offs + who performs each step (swimlanes), or an outside-in customer journey** ← the ArchiMate way to express a "sequence/scenario"
   - `archimate://recipes/technology-deployment` — software deployed onto infrastructure nodes
   - `archimate://recipes/motivation` — stakeholder → driver → goal → requirement influence chain
   - `archimate://recipes/roadmap-migration` — current/target states over time
2. **Run the invariant build sequence** from the index (`create-view` → `add-group-to-view` per lane/band → `add-to-view` with `parentViewObjectId` per the topology, `autoSize:true` → `auto-connect-view` filtered to the recipe's **draw** relationship types → `get-view-contents format=tree` → `layout-within-group` → `arrange-groups` → `detect-hub-elements`/resize → spacing → `auto-route-connections` → `assess-layout`). The recipe page supplies only the **deltas** (arrangement, direction, relationship filter, nesting parentage).
3. **Evidence overlay** (per *Evidence marking*): set each object's `labelExpression` to `${name} ${property:evidenceMark}` (channel 4 — single glyph, never the word; **expected on every object — gate G4**; ASCII fallback `[c]/[d]/[i]` on a genuine render failure, never skipped). The evidence **legend note** is **not** placed here — it is the *last* action on the view (step 7 below), so no later layout pass can grow a container under it.
4. **Colour/imagery** only where they serve *this* view's message (per *Visual language*) — record any colour-key deviation in the legend.
5. Reuse views with `add-view-reference-to-view` where it reduces clutter.
6. **Collapse redundant bendpoints — the last geometry step before annotation.** Run `assess-layout`; for every connection it flags with `connectionRedundantBendpointCount > 0` (ids under `violatorIds.redundantBendpoints`), run `auto-route-connections mode:"terminals-only"` on just those `connectionIds`, then re-`assess-layout` to confirm `connectionRedundantBendpointCount == 0`. This collapses the collinear terminal micro-jog that pins a **Middle**-positioned branch label hard against a tiny OR-junction — the label re-anchors to mid-run, which *is* the fix (not a label move). Because it re-anchors Middle labels it is a **geometry mutation, so it MUST run before the step-7 annotation** (gate G11): the invariant order is **layout → route → collapse-redundant-bendpoints → annotate (last)**. Targeted only — on a clean view (`connectionRedundantBendpointCount == 0`) it is a no-op.
7. **Annotate LAST — the legend, notes, captions and images are the FINAL action on the view (a build-time invariant, not only the Phase-6 close-out check — gate G11).** Only after *every* layout, routing, resize, `arrange-groups`, and `add-view-reference` pass on the view is finished, add the evidence legend with `add-note-to-view` (once on the index view for a large model; per-view otherwise) and any caption/image. **Place every note with `position:below-content`, never `above-content`** — a below-content note rides under the content as it grows, whereas an `above-content` note's `y` is stamped once and is silently invalidated the moment a container later grows upward, dropping the note onto the elements below it. **Do not run any geometry-mutating call — `layout-within-group`, `arrange-groups`, `auto-route-connections`, resize, `add-to-view` — on a view after a note/legend/image has been placed on it**; that re-layout is exactly how a container grows under a placed note. If a later geometry change is genuinely unavoidable, remove or re-place the annotation *after* it, never before — then re-arm G11 (re-assess + re-export, Phase 6).

**Behaviour / "sequence" views specifically.** ArchiMate has **no UML sequence diagram** (no lifelines/messages) — do not try to fake one. Express runtime behaviour the ArchiMate way via the **`behaviour-process-flow`** recipe: model the scenario as `BusinessProcess` / `ApplicationProcess` / `ApplicationFunction` / `ApplicationEvent` steps connected by **Triggering** (order/causality) and **Flow** (data/message), one **swimlane per performing role/component** (Assignment *implied by nesting*, not drawn), flow running **left-to-right**. Laid out this way it reads as a sequence/scenario. The recipe's literal example is business-level (`BusinessRole` lanes, `BusinessProcess` steps), but the pattern transfers unchanged to **application** behaviour — use `ApplicationComponent` lanes with `ApplicationProcess`/`ApplicationFunction` steps (Assignment-by-nesting and Triggering work identically). Most code-derived behaviour is application-level, so reach for the application form by default and use the business form only when the scenario is genuinely a human/business process.

**Behaviour fidelity gate — never linearise a multi-path scenario, and augment choreography with a rendered image.** The process-flow view faithfully carries **one** ordered path — its performers, order, and data. Before modelling a scenario, **enumerate its branches** (alternative modes, error/fallback paths, significant returns). If more than one path exists, it **MUST** be visible: at minimum a **labelled branch marker on the spine** — an ArchiMate **OR-junction** with each outgoing path named for its guard — so the reader sees the road splits and that the paths are alternatives. Collapsing a multi-path scenario into a single happy-path view with no branch marker and no note is a **defect**, not a simplification. When the scenario's value is in the **interaction dynamics** — two or more of {conditional/alt branches, call/return semantics, self-calls, activation/lifelines, cross-thread hand-offs} — ArchiMate cannot express it, so **augment the same view with a rendered Mermaid sequence diagram**: write `sequenceDiagram` source to `<diagrams-dir>/<scenario>.mmd` (a `diagrams/` folder beside the Archi model, or a temp dir), render it to **PNG** (not SVG — Archi embeds raster). If `mmdc` is on PATH use `mmdc -i <…>.mmd -o <…>.png`; otherwise `npx -y @mermaid-js/mermaid-cli -i <…>.mmd -o <…>.png` (the binary *is* `mmdc` — do **not** add a `mmdc` sub-arg; and note macOS has no `timeout`). Register it once with `add-image-to-model`, then place it with `add-image-to-view` **beside/below** the flow, sized to be legible but not dominating. **Caption the two as complementary lenses, not a hierarchy of truth** — each labelled with the question it answers: caption the ArchiMate flow *"Performers & order — who acts, in what sequence"* and the image *"Message-level handshake — returns, branches, threading; read together with the flow."* The flow is the structural backbone (performers, order, data, the visible branch junction); the image carries the choreography ArchiMate cannot express. If `mmdc` is unavailable, still emit the `.mmd` (and/or a `diagrams/<scenario>.sequence.md`) and reference it from a Note on the view rather than dropping the choreography. State in the final report which scenarios had branches, how each was handled, and any complementary diagram(s) emitted.

### Phase 5 — Lay out and route (defer to the routing checklist)

The invariant build sequence (Phase 4) already lays out and routes each view. Two server resources are the **authority on the details — prefer them over ad-hoc tuning:**
- **`archimate://prompts/routing-preconditions-checklist`** — fetch before routing any non-trivial view; the routing pipeline cannot recover from missing preconditions (hub sizing, inter-element and inter-group spacing). On a `density_floor_reflow_required` refusal, surface the diagnosis and the consent-gated reflow — **do not loop the spacing tools or auto-reflow, and do not force past a sound refusal.**
- **`archimate://reference/archimate-view-patterns`** — the layout / aesthetic rules.

Supplementary notes (still useful, not superseded by the resources):
- **Conventional flat views (no recipe):** `auto-layout-and-route mode:"auto"` (ELK) gives excellent placement; grouped/swimlane views use `mode:"grouped"`.
- **Structure vs flow density:** structure views tolerate tight grouping; flow/behaviour views need generous spacing (**100px+**) so connections have routing corridors (≈24px routes badly, ≈124px routes excellently).
- **ELK diagonal terminals:** after `mode:"auto"`, run `auto-route-connections mode:"terminals-only"` to rectify diagonal terminal segments without disturbing the routed bodies (some rectifications are correctly vetoed when they'd add a crossing / terminate inside an element / zigzag). **`fair` caused *only* by `nonOrthogonalTerminals` is an accepted ELK outcome — don't force past it** (`force:true` trades clean terminals for new crossings); keep iterating only when a Tier-1/2 metric (overlaps, pass-throughs, crossings) is the limiter.
- **First, distinguish native-group laning from hub-nesting — the warning below is about only one of them.** *Native-group laning* (`add-group-to-view`; groups carry no connections of their own) is cheap, safe, and the recommended way to structure any non-trivial view — it has **none** of the hub penalty below. The penalty applies only to *nesting a high-fan-out element* (a hub with ≥6 connections) inside a container; do not let the hub warning deter you from group laning.
- **`connectionEdgeCoincidence` from a container-nested hub is FIXABLE — resize the hub, then re-route (re-routing alone is inert).** When a structure view nests children inside one container element and a hub (≥6 connections per `detect-hub-elements`) drives a `fair`/`poor` **routing** rating via `connectionEdgeCoincidence` (and `coincidentSegments`) while **layout** stays `excellent` and `corridorUtilisation`≈1.0, do **not** accept it as an engine cap — that premise is false. Resize the hub generously in **both** dimensions (≈+30w / +60h beyond the box default) with `update-view-object`, then `auto-route-connections`: the larger box physically pushes the corridor walls apart, `corridorUtilisation` drops, and the A* router gains the headroom to inset segments off box edges. *Verified live on two container-nested-hub views (Protocol, Model): fair/poor → good, `connectionEdgeCoincidence` 6→1 and 8→1, `corridorUtilisation` 1.0→0.18 / 0.73.* **The trap that hid this:** `hubPortQualityScore` may already read 1.0 — but that scores port **distribution**, which is orthogonal to corridor headroom, so a maxed hubPortQuality does **not** mean resize won't help routing. And re-routing **without** resizing reproduces the same edge-hugging paths (geometry unchanged → inert). Only accept-and-annotate if a *generous* resize genuinely fails to move the metric — and never shrink the container's contents below the onion's honest altitude to chase edge clearance.
- The router produces correct orthogonal paths; **layout density and grouping**, not the router, determine quality. **So default to grouped / nested structure views** (`add-group-to-view` lanes/bands, or element nesting via `parentViewObjectId`) for any non-trivial subsystem — a flat dense structure view is the single biggest routing-quality risk: it strands edges as long diagonal terminals (measured `nonOrthogonalTerminalCount` **6–19 on flat views vs ~0–1** once the same elements are grouped). Reserve flat layouts for small views (≲10 elements) and behaviour / flow.
- **Nesting pays only when the wiring stays *inside* the container — flatten a subsystem whose members each wire to *external* elements.** The grouped/nested default above assumes a subsystem's connections are mostly internal. When each nested child instead has several edges to elements *outside* its container, those edges hug the stacked children's faces and ELK inflates crossings (`connectionEdgeCoincidence` → `poor`, many crossings); a **flat** view (no element-container nesting) routes the same estate far cleaner. Rule of thumb: **nest when the wiring is internal, flatten when each member wires outward** — the onion-spine composition still pays on the landscape views where members sit together.
- **`grid` arrangement pads to a uniform cell — prefer `column`/`row` when child sizes are uneven.** `layout-within-group arrangement:"grid"` sizes *every* cell to the largest child, so one tall sub-container (e.g. a ~400px guard-chain) inflates every row to its height → an airy, over-tall view. When a group's children differ markedly in size, use `arrangement:"column"` or `"row"` (which pack to each child's own footprint) instead of `grid`.
- **Connection labels need horizontal room the auto-layout doesn't reserve.** ELK sizes spacing for *boxes*, not for edge-*label* width, so labelled edges crowd and overlap at default spacing. On any view whose edges carry labels: either **raise spacing** (`auto-layout-and-route spacing:≥80`, `direction:"RIGHT"` for flows) **or suppress labels** (`auto-connect-view showLabel:false`) and let the relationship type + a note carry the meaning. Label the few semantically-important edges, not all — and where a short parallel run still crowds its mid-segment labels, drop those labels rather than fight them.
- **Keep relationship labels short — a caption, not an inventory.** A long edge label (e.g. an enumerated collaborator list like *"hosts (EMF model, CommandStack, SWT)"*) bleeds across neighbouring boxes; and a long label anchored at a *source/target* terminal on a short first/last segment is exactly the bleed the layout assessor still under-counts (so a clean `labelOverlapCount` does **not** prove that case clean). Carry the relationship's *type* on the edge and push the enumerated detail into the source/target element's `documentation` or a Note — label the meaning, not the membership list.
- **Be sparing with Association edges**, especially on deployment/context views. A weak "opens/saves"-style association clutters more than it informs and routes awkwardly across nested containers — prefer nesting / realization and drop the low-value link.

### Phase 6 — Verify (close the loop; never assume success)
1. For each view, call `get-view-contents` and `assess-layout`; confirm objects landed, connections resolved, and the layout quality is acceptable. **Judge that from the per-dimension `ratingBreakdown`, not the single `overallRating` headline** — walk each dimension and explicitly dispose of every non-`pass` one (fix it, or record why it is accepted); never sign a view off on the headline alone, which hides exactly the dimension that is failing. A zero or absent count means *measured-clean* **only for a dimension that was actually evaluated** — so read the `assess-layout` `coverage` map, which reports **three** states per dimension (`checked` / `partial` / `not-checked`): treat **both `partial` and `not-checked`** as **unverified, not passed**. A `partial` dimension covers only some of its cases (e.g. a label grazing a junction, or a label on a short/tight segment) — verify it by eye or accept the gap knowingly; never read `partial` as clean. Fix outliers (overlaps, truncated labels, zig-zags), and **re-run `assess-layout` after every manual layout, resize, or reposition pass** — a label that fit pre-layout can clip once a box is resized or a node moved, and the metric only ever reflects the *current* geometry. **`assess-layout` is necessary but not sufficient — it under-counts label-on-element crowding on short/tight segments, where render is authoritative over the metric.** `export-view` and visually inspect **at least the index view, the densest view by element count, and any view `assess-layout` flags marginal** — a *floor, not a ceiling*: also render any view whose `ratingBreakdown` (or `coverage`) leaves a dimension unverified — then fix what the eye catches that the metric missed.

   **Terminal close-out gate (G11) — the render is authoritative, and annotation comes last.** Notes, legends, captions, images and glyphs are added *after* the structural layout was assessed, so the verified artifact is never the final one unless you re-verify — which is exactly how a clean view ships with a note overlapping an edge, a legend clipped, or a caption widened across a routing lane. Therefore, after **any** pass that adds, moves, resizes, or styles a view object — **notes and images included** — the **final** action on that view is, in order: (a) `assess-layout`, requiring `noteOverlapCount == 0`, `noteClipCount == 0`, and `connectionThroughNoteCount == 0` alongside the structural dimensions and the per-dimension `ratingBreakdown` all disposed; **and** (b) an `export-view` PNG you actually **look at**. No view is signed off on the metric alone — `assess-layout` under-counts a label grazing a note or junction and a connection skimming a note edge, so the eye is the backstop and the render wins any disagreement. Export at minimum the index view and every note-bearing or marginal view; a clean metric on an un-exported annotated view is **not** a pass. Fixing one view's overlap can introduce another's (a moved caption, a re-sized note) — so a fix re-arms this gate: re-assess and re-export the view you just touched. Collapsing redundant bendpoints re-anchors Middle labels, so it is a geometry step — run it **before** annotating (Phase 4 step 6), never after.
2. Spot-check a few elements with `get-element` / `get-relationships` to confirm types and connectivity, and that the **four evidence channels agree** on each: the `evidence` property, the `evidenceMark` glyph, the `Evidence:` documentation line, and the specialization (present for `documented`/`inferred`, absent for `code`). Fix any element where they disagree. For every `inferred` element, also confirm `inferenceType` is set and that any `structural` one carries a non-empty `evidenceSignal` (empty ⇒ it should be `speculative`). **Backfill the `documentation` prose's `Rationale` / `Caveat` lines now** that cross-element edges are known, holding the per-line grading (Rationale is `documented`-only or tagged `(inferred)`) — see *Level of detail → Document each element as prose*.
3. Confirm the glyph didn't push labels into truncation — `assess-layout` label-truncation stays clean (a single trailing glyph rarely truncates). If a label does truncate, fix it by spacing/width or the ASCII mark `[c]/[d]/[i]` — **not** by dropping channel 4; gate G4 keeps the cue on every name (see *Evidence marking* ch.4).
4. **Visual-language check:** any colour deviation from layer defaults encodes one documented meaning (keyed in the legend) and reads in greyscale; imagery is licence-cleared, legible, not oversized, and positioned `bottom-*` or `fill` so it never covers the element label (no `top-*` on labelled elements). Back off styling that adds noise rather than signal.
5. Confirm referential integrity: no orphaned view objects, no dangling references.
6. **Run the per-altitude completeness contract as the closing gate** (see its section): every level's anchors scanned, every candidate dispositioned, no content-bearing level with an all-absent ledger, and no significant element orphaned from a level-appropriate view (cross-check the `repoToArchi.level` view tags). Then **write, last and from the actual model state,** the machine-readable `repoToArchi.coverage.*` record and the condensed coverage prose into the model `documentation` field; emit the full disposition ledger in the final report.
7. **Reconcile cross-doc headline figures and refresh derived diagrams.** When a headline number appears in more than one doc (e.g. a tool/endpoint count in README *and* SECURITY.md), reconcile it against the code before stating it in the model; if they disagree, use the code and note the stale doc. Re-render any Mermaid `.mmd` to PNG rather than reusing a prior image unless you have verified it unchanged.

For every behaviour/flow view, state that an export-view spot-check confirms no junction renders oversized or with a connection label on its dark fill (see the junction rule in *Constraints & guardrails*).

## LEVEL OF DETAIL — model the significant, not the exhaustive

**Comprehensive ≠ complete.** A "full architecture & design" model captures every architecturally *significant* unit at a *consistent altitude* — not every class, method, or call. The target is the model a new architect needs to understand the system, not a transcription of the code. Effort scales with the number of significant units (usually a few dozen), **not** with file or class count — a 300-class repo and a 30-class repo can both land at ~10 subsystems.

**Hold a consistent altitude *within each level of the onion*.** The model spans multiple altitudes by design (L0 Context → L1 Landscape → L2 Component); the discipline is consistency *within* a level, not collapsing the model to one level.
- **The floor altitude** (the deepest level modelled) = the deployable(s) and their major internal subsystems (services, bounded contexts, packages with a distinct responsibility), the external systems/datastores they integrate, and the key data objects exchanged. One element per significant unit. Coarser levels (L1, then L0) aggregate these same units upward along the onion spine.
- **Consistent within a level** — on any one view, don't model one subsystem class-by-class and its peer as a single box. If you zoom into one, either zoom into its peers too or give the zoom its own dedicated (deeper) view.

**Significance test — derive candidates from structure, then score each (so the same codebase yields the same candidate set on any run, not a count that swings with the reader's mood).**

*Step 1 — enumerate candidates from the first structural anchor that yields a set within the altitude's element budget (~25–40/view):* (a) **deployment units** — one per Dockerfile / service manifest / published artifact / process entry point; else (b) **build targets** — one per module in the build graph (Maven module, Gradle subproject, npm/pnpm workspace, Cargo crate, Go module); else (c) **top-level source boundaries** — one per package/directory one level below the source root.

*Step 2 — promote-or-fold each candidate.* Give it its own element only if it scores **≥3 of 5**: (1) has its own deployable/runnable boundary (process, container, artifact, entry point); (2) is replaceable by a third party without rewriting its callers (a stable seam/interface); (3) owns persistent state or an external resource (datastore, queue, socket, file store); (4) is named in docs/README/config as a thing-in-itself, not just a class; (5) has a distinct failure mode an operator would care about. Score **<3 → fold** into the nearest candidate that passes.

**Every deviation from the Step-1 candidate set (a merge or a split) must cite its reason** in the owning element's `documentation`, so granularity is auditable rather than a matter of mood. This pins the *derivation*, not the number — a 30-class CLI and a 300-service monorepo still land at different counts (see "Comprehensive ≠ complete" above).

**This structural test sizes the *floor* (L2 / code) candidate set.** The **L0 and L1** candidate sets come from the **document** anchors named in the Phase 1 anchor scan, not from code structure — score them by the same "is this a thing-in-itself, named and bounded" spirit, grade them by their source (`documented`, or `inferred-structural` when reproducible from structure but unstated), and disposition every one through the completeness contract below. Generous enumeration, selective capture, honest discard.

**Fold in (do not model separately):** helper/util classes, DTOs and mappers, framework glue, config, getters — implementation detail of a unit already modelled. Mention them in the owning element's `documentation` if useful, not as their own boxes. **But fold honestly:** when one box stands in for a *large* family (dozens of DTOs, a whole command/handler set), name the cardinality (e.g. "Response DTOs (66 record contracts)") and, if the proliferation is itself an architectural concern, say so in the documentation — one honest box, never a silent "*a* data shape" that hides a known smell. **And a folded box grades `inferred-structural` by default, never `code` — decide this at create time.** The moment one element stands in for ≥2 classes, or carries a rolled-up `…Family` / `…Handlers` / `…Suite` / `…group` name, it is a *modelling abstraction over* the code, not a transcription of any single unit — so it is `inferred-structural` (name the folded members in `evidenceSignal`), not `code`. A class promoted 1:1 to its own element stays `code`; the **fold itself is the tell** for the downgrade. Grade it when you create it: a near-100%-`code` split is the red flag, and catching an over-claimed fold only at the Phase-6 weakest-link sweep is a near-miss, not the safety net working as intended.

**Zoom in where it matters.** Give an architecturally complex or risky subsystem its own **structure view one level deeper** (its internal parts), while the top-level view stays coarse. Most subsystems need no zoom. Likewise model only the **few key end-to-end scenarios** a newcomer must understand as behaviour views (typically 1–5: the primary request path, a critical async/event flow, an important failure or approval path) — not every method sequence.

**Two failure modes to avoid:**
- **Too coarse** — one box labelled "the application": true but useless.
- **Too fine** — one element per class: a class diagram, not architecture; it buries the design and bloats the model.

**Record the altitude at Phase 1.5** (the `repoToArchi.altitude` model property) and **restate it in the final report** — one source of truth — alongside any subsystem you deliberately zoomed into, so coverage is judgeable rather than mistaken for "everything."

### Document each element as prose — the `documentation` field is the HUMAN rail

A model whose elements carry only an `Evidence:` line generates a document that is all boxes and no narrative. After the `Evidence:` line (machine rail — stays *first*, see *Evidence marking*), write a few high-signal **labelled lines** so a document generated from this model reads as prose, not a list of boxes:

```
Evidence: <grade> — <source>          ← unchanged, machine rail, stays first

What: <one sentence — the element's kind/role in the system's own terms>
Responsibility: <1–2 sentences — what it does, from observed code (method/route/file names)>
Collaborators: <names it calls / is called by / depends on — element names, not prose>
Rationale: <why it exists / what decision it embodies>          [documented-grade only]
Caveat: <smell / risk / coupling / TODO / known limitation>     [omit if none observed]
```

Grade and source **per line**, and **fill only the lines the evidence earns — OMIT the rest** (a blank line beats a padded one):
- **What** — at the element's own grade, from the code's own naming; always present.
- **Responsibility** — `code`-grade; assert only behaviour *observable* in code (methods, routes, handlers), phrased as observation ("Validates UTF-8 at the HTTP boundary"), never motive. Terse for `inferred`; omit for `speculative`.
- **Collaborators** — `code`/`structural`-grade; real edges only (things that exist as relationships), using exact element names so a resumed search-before-create still matches. Omit if none.
- **Rationale — the provenance firewall line.** Allowed *only* when a doc states the why; tag the source inline (`per README#goals`). If the why is inferred, either omit it or write `Rationale (inferred): …` — **never a bare stated fact**. This is the one line that can launder an inference into fact, so it carries the strictest gate.
- **Caveat** — `code`-grade from an observed TODO / coupling / smell, `documented`-grade if a doc names the limitation; tag accordingly. Omit when nothing is observed — silence is honest, an invented caveat is not.

**Depth scales with grade — never uniform bloat.** A `code` element fills What + Responsibility + Collaborators cheaply; a `speculative` element carries What alone. Over-writing a thin element launders inference into fact — the very thing this contract exists to prevent. Fill the template **at create time** (Phase 3) so it is deterministic and resume-stable, and **backfill Rationale/Caveat in the Phase 6 pass** once cross-element edges are known.

**Enrich on the durable axis; pointer the volatile.** The model's primary reader is an agent that can follow the `Evidence:` pointer back to *fresh* source — so inlining a threshold value, a count, or an algorithm just mints a second copy with no CI, silently wrong on the next commit. Fill toward what the source *can't* cheaply express, and leave the rest a pointer. **Governing test:** *could an agent recover this fact by following the evidence pointer to the source? If yes → leave it a pointer; if no — it is the purpose, an invariant, or the reason-to-exist → inline it.*

| Inline (durable — source can't cheaply express) | Pointer only (volatile — repo owns it, has CI) |
|---|---|
| Purpose / why it exists, as a **code-observable role** (not a laundered motive — the Rationale firewall still holds) | Threshold *values* — name the concept ("a healthy parallel-gap floor"), never the number |
| Invariants & contracts ("pure geometry, no EMF/SWT"; "measurement-only, rating byte-identical") | Stage / dimension / LOC counts ("~20 stages", "4,400 LOC") |
| Role-in-collaboration as a **verb** ("straightens routed paths by removing redundant bendpoints", not "a path straightener") | Algorithm step-by-step / tier mechanics |
| Gotchas / failure-modes (an observed coupling, TODO, or smell) | Per-view findings / current metric readings |

This enriches the **What / Responsibility / Caveat** lines on the durable axis — it does **not** relax their grades (a `code` element still asserts only code-observable behaviour). **Budget: up to 3–5 durable content lines even for a keystone class** (What + why + invariant + gotcha + role) — the cap governs *durable* content only; volatile detail is banned outright regardless of budget. If you are about to write a number, threshold, or count, that is the signal it belongs behind the pointer — and where the `Evidence:` pointer is vague, sharpen the *pointer* (`…RoutingPipeline.java — see routing-pipeline.md §stages`) rather than pasting the section.

**Relationships get a lighter, two-line version:** the `Evidence:` line (unchanged) + one **Meaning** line ("what this dependency/composition represents, in the source's terms"); add a **Rationale** line only when a doc states *why* the link exists. Relationships are mostly self-describing by type + endpoints — a reader needs only the non-obvious "why this edge"; anything more is bloat.

## PER-ALTITUDE COMPLETENESS CONTRACT — every candidate accounted for, never invented

**The success test is not "how many elements / views" — it is: at *each* level of the onion the reader will open, has every *significant* unit the evidence supports been captured, in a level-appropriate view?** Completeness is judged against the *candidate set the evidence produces* (the Phase 1 anchor scan), never against an expectation of richness. A thin-evidence level that captures all 2 of its 2 candidates is **complete**; a rich-evidence level that captures 4 of 19 is **incomplete**. Both verdicts come from the same machine — and that is what severs "complete" from "padded".

**Gate 1 — anchor scan (emitted, not a thought).** Phase 1 already names, per altitude, the anchors scanned and the candidates they surface; this contract reads that census as an *artifact*, not a belief the agent self-certifies. **A level whose anchors were never scanned cannot be declared complete — "not scanned" ≠ "scanned and empty".** An unscanned-but-present anchor is itself a failure.

**Gate 2 — disposition every candidate (no silent drops).** For *every* candidate the scan surfaced, record exactly one falsifiable disposition:
- **captured** → which element, and which level-appropriate view it sits on (an element on **zero** views, or on no view at its own altitude, is *not* captured — it is orphaned);
- **consciously-folded** → into which parent element, and the one-line reason (folding is legitimate granularity management; *silent* folding is the defect — see *Level of detail*);
- **deemed-insignificant** → the reason (significance is a *filtering* disposition, **never** an exemption from being accounted for — a candidate quietly dropped as "not significant" is a silent drop wearing a respectable coat);
- **absent-for-cause** → no supporting evidence found, naming the anchors scanned that came up empty (the disposition that lets a genuinely thin level **pass honestly**).

This is the weakest-link grade (see *Evidence marking*) promoted from single elements to *coverage*. **An undispositioned candidate fails the contract.**

**Gate 3 — evidence-closure firewall (the anti-invention wall).** The admissible element set is **closed under evidence**: no element may appear on any canvas that does not trace to a scanned anchor with a stated grade (`code` / `documented` / `inferred-structural`). **`inferred-speculative` elements are never drawn** — list them as scan residue with a question. Because every captured L0/L1 element must carry its `source` citation, an *invented* element (no citation) is mechanically impossible to record as captured — that is the wall that keeps "abstract" (legitimate, doc-sourced) from sliding into "speculative" (hallucinated). There is **no minimum** element or view count; a level whose dispositions are all *absent-for-cause* over genuinely thin anchors is a **passing, stated** outcome.

**Gate 4 — generalised non-empty check (replaces the independent-mode-only check).** For any level whose anchors **contain content**, a disposition set with zero *captured* and zero *consciously-folded* (everything came back *absent-for-cause* despite present evidence) is a **contract failure — re-scan before finishing**. The former independent-mode "non-empty invariant source set yielding zero Motivation elements is a contract failure" is exactly this rule applied to one level; it is now general across the onion, and is the gate that catches the under-harvest where present `SECURITY.md` / ADR sources produce zero conceptual elements.

**Two distinct, both-passing outcomes** — so a reader can tell them apart: **complete given evidence** (anchors scanned ✓, every candidate dispositioned ✓, ≥1 captured) and **empty because the evidence is genuinely thin** (anchors scanned ✓, every candidate dispositioned ✓, all absent-for-cause). The only **red** states are an unscanned anchor or an undispositioned candidate. *Richness never enters the verdict.*

**Where the ledger lives — split by audience, no duplication of purpose:**
- **Full disposition ledger** (every candidate → disposition + citation) → the **final report** (and optionally a sidecar file in the run artifacts). It is build-time QA evidence; it does **not** belong in the `.archimate` model, where it would bloat what the reader sees.
- **Machine-readable coverage record** → model properties `repoToArchi.coverage.*` (e.g. `L0.candidates`, `L0.captured`, `L0.anchors`, `L1.captured`, `L2.captured`, `lastRun`, alongside `repoToArchi.onion` / `altitude` / `docMode`). This is what the **next run diffs against** for resumability; it survives view deletion (a Note does not) and is queryable. **Write it last, derived from the actual end-of-run model state — never from mid-run intention — so it can never disagree with the model.**
- **Condensed human-readable coverage statement** → the **model `documentation` (root) field**, as prose a consumer can choose to open ("covers Business/App/Tech at L1, App/Tech at L2; Motivation is L0-only, sourced from the architecture brief; evidence: N code / N documented / N inferred").
- **Short confidence line** → the **Start Here** view (reader-facing — tells the reader the homework was done without showing the homework).

**Subsystem-granularity views — a cluster of collaborators earns a view, and the title must match it.** The candidate/aspect gates above prove every *unit* is accounted for; they do not guarantee a *subsystem* is legible. Add one rule: **a distinct subsystem — a cluster of 3+ collaborating classes — earns its own view.** Not every class does (leaf classes live *inside* views); but a subsystem described **only in a parent component's prose** is a *missing view*, not an adequate substitute — prose enumerating four collaborators is the smell that a view is absent, not evidence one is unnecessary. Two guards keep this from becoming padding:
- **Title honesty.** A view's title must match its contents — a view titled for a scope it does not contain (e.g. "Layout & Routing" holding zero layout classes) is a defect: re-title it, or add the missing content.
- **Lens fits the shape, and the view must earn it.** Pick the lens the subsystem's structure demands — a **Flow** view for a genuinely sequential pipeline (shape carries stage order), a **collaboration / Components** view for a cluster with feedback or fan-in/out (shape carries the relationships). Don't force two different subsystem shapes into one view to save a view; equally, a view that degenerates to N disconnected boxes is not warranted — cut it, or find the relationship (a feedback / oracle edge) that makes it a subsystem.

## ARCHITECTURE-ASPECT COVERAGE — two orthogonal axes (depicted vs evaluated)

The completeness contract above proves every *candidate unit* was accounted for. It is blind to whole **aspects** that have no unit in the scan — which is how a real information model can vanish into one folded box and still "pass". Close that blind spot with a second, aspect-level sweep along **two orthogonal axes** — **representation** (did we *depict* this facet?) and **design/analysis** (did we *evaluate* the architecture through this lens?). They are independent: *depicted-but-unevaluated* is the normal state of a reverse-engineered model.

**Disposition grammar (both axes).** Each row resolves to exactly one **falsifiable** disposition. A no-coverage disposition MUST name the **negative search** that produced it; `N/A`, "considered", and silence are not dispositions. **A disposition lacking its evidence field is INCOMPLETE, not a pass — the persisted property, not the prose, is the gate.** With no search tool (`repoToArchi.tooling.search = none`) an unverifiable row is `UNVERIFIABLE`, never a fabricated "found 0".

**Axis 1 — Representation (ArchiMate viewpoints).** For each, record `BUILT` (name the view) · `DEFERRED-CANDIDATE` (the repo evidences it but it was folded or out-of-altitude — surface it for the owner with a one-line "what it would contain and why") · `N-A-because` (one line):
*Information Structure · Application Cooperation · Application Usage/Behaviour · Technology & Deployment · Security / Trust-boundary · Motivation · Layered.*
**A folded high-cardinality family defaults to `DEFERRED-CANDIDATE`, never a silent fold — cardinality is a reason to GROUP, never to HIDE** (a "Response DTOs (66 records)" box is a deferred *Information Structure* view candidate, not a closed matter). Any viewpoint with real repo evidence marked `N-A` is a contradiction — re-disposition it.

**Axis 2 — Design / analysis lenses (evaluate; report, never grade).** These assess the architecture; their output lives in the **final report's *Architecture-analysis observations & gaps* section and the close-out pick-list — NOT as model elements** (do not mint speculative Motivation/Requirement elements for unevidenced NFRs; the sole exception is an NFR a doc genuinely states, which earns a real Motivation element graded `documented`). Steps:
1. **Detect repo-class facets — multi-label and additive.** A repo can be several at once (this very server is an Eclipse *plugin* **and** an *HTTP service* **and** a *CLI*). Detect zero-or-more facets, each backed by an anchor (`plugin.xml` / `Bundle-SymbolicName` → plugin; Jetty / servlet / route / `@RestController` → http-service; `main()` + arg-parser → cli; library packaging → library; …) and **union** their expectation vectors — a lens is *expected-present* if **any** detected facet expects it. A single-label classifier would mislabel a hybrid; never use one. (Catalogue, per-facet expectation vectors, and pinned search terms are in *Aspect-coverage catalogue* below.)
2. **Disposition each lens:**
   - **`PRESENT`** — cite the constituting artefact and grade it. A **design pattern** (layering / facade / BFF / ports-and-adapters) is graded at most **`inferred-structural`** and MUST cite ≥2 structural anchors **and** a named **falsifier** (the single observation that would refute it); a found counter-example → `PARTIAL/VIOLATED` ("layering with 1 leak — cite it"). A pattern claim without anchors + falsifier is rejected, not graded — never graded `code`.
   - **`WARRANTED-BUT-ABSENT`** — the repo shows the signal but you didn't model it; **only** when the lens is *expected-present* for a detected facet; cite the anchors. → becomes a *breadth* option in the close-out pick-list.
   - **`NOT-EVIDENCED`** — *optional / expected-absent* lens, found empty; record the named negative search; **not** a pick-list item — roll up to one report line ("N lenses scanned expected-absent: …"). This gate keeps reverse-engineering's many legitimate absences (NFRs, SLAs born later in design→build) from becoming a litany.
   - **`UNVERIFIABLE`** — no search tool.
   Quality attributes follow **ISO/IEC 25010** (functional suitability, performance efficiency, security, reliability, maintainability, portability, …): note which have *evidence* (a retry policy, an auth boundary, a cache, a stated budget) and which are not evidenced — **never score or rank them.**

**Persist as exploded properties (re-parseable, resumable) — never one delimited string** (search terms contain `,` / `;` / `=` and corrupt a split-parser): `repoToArchi.coverage.aspects.<aspect>.axis` / `.disposition` / `.searched` / `.found` / `.anchor` / `.falsifier` / `.date`. **Read existing `repoToArchi.coverage.aspects.*` before re-searching** so dispositions don't flap across runs, and use the **pinned** per-lens search terms in *Aspect-coverage catalogue* (below) so `found=N` is reproducible. Surface the dispositions in-session at the close-out checkpoint — the pick-list is a *projection* of these properties, not a parallel hand-kept list.

For element-type edge cases (Component vs Service, Process vs Function, Node vs Component) defer to `archimate://reference/archimate-layers`; for valid relationships defer to `archimate://reference/archimate-relationships`. Where they disagree with the rows below, the resources win.

`evidence=code` means observed directly in source/build/infra. `evidence=documented` means stated explicitly in the repo's prose (README/`/docs`/ADRs) — the team's own words. `evidence=inferred` means deduced — **mark it**, and tag it `structural` or `speculative` (see *Evidence marking*). When a concept is both stated *and* visible in code, prefer `documented` for narrative concepts (goals, roles, processes) and `code` for structural ones (components, data, nodes).

> **The Evidence column below is the *strongest-link* hint — downgrade it by the weakest-link rule.** `code` is correct only for a thing you can literally point at: a class, module, dependency, node, or build artifact. The moment a row's element is a **capability abstraction you draw *over* code** — an Application **Service**, **Function**, **Collaboration**, a handler-cluster grouping, a layer/subsystem boundary not itself a single named artifact — it is **`inferred` (usually `structural`)**, not `code`, because it is a modelling decision, not a transcription. ## EVIDENCE MARKING (mandatory)

**Grade by the weakest link, not the strongest.** The grade reflects the *most fragile* inference in the chain from source artifact to the element on the canvas — never the fact that you read *some* code nearby. A class, module, dependency, node, or build artifact you can point at is `code`. An **abstraction you drew *over* code** — a service boundary, a facade, a layering, a capability grouping, an Application Service/Function — is **`inferred`, not `code`**: it is a modelling decision, not a transcription.

**Inferred splits in two — carry the split as a property, never a new glyph (keep the three glyphs ● ◐ ○):**
- **`inferenceType=structural`** — high-confidence and *reproducible*: a competent second engineer, given only the same code and no architecture doc, would reconstruct it. Earns this **only if** you can name the design pattern/convention that forces it **and** the code signal that instances it (the fan-in that makes a hub, the interface everything routes through, the single coordinator fronting N collaborators) — record that in **`evidenceSignal`**.
- **`inferenceType=speculative`** — needs knowledge outside the repo (team, history, market, intent); most motivation "why" deductions. **An empty `evidenceSignal` means it is *not* structural — demote it to speculative.** This gate is what stops "structural" from becoming a licence to launder a guess as near-fact.

Record evidence in **four coordinated channels** so it is queryable, searchable, *and* visible on the canvas without cluttering or overflowing element boxes. The property is the single source of truth; the other channels render or restate it.

**1. Property (canonical machine record — always).**
Every element gets a property **`evidence`** = `code` | `documented` | `inferred`, plus a companion **`evidenceMark`** glyph: `●` = code, `◐` = documented, `○` = inferred (filled = more grounded). Add **`source`** pointing at the file/dir/doc that justified it (e.g. `pom.xml`, `src/orders/`, `README#goals`). **For every `inferred` element also set `inferenceType` = `structural` | `speculative`, and for `structural` a non-empty `evidenceSignal`** naming the code fact that forces the inference. Set these at create time via `create-element` / `bulk-mutate`.

**2. Documentation field (human-readable + searchable — always).**
Append one line to each element's `documentation`: `Evidence: <value> — <source>` (e.g. `Evidence: documented — README#goals`). This shows in Archi's Properties panel and tooltip, and `search-elements` matches documentation text — so a reviewer can pull "all inferred elements" with one search. The `Evidence:` line stays *first*; the human-rail prose that follows it (What / Responsibility / Collaborators / Rationale / Caveat) is graded **per line** — see *Level of detail → Document each element as prose*.

**3. Specialization stereotype (idiomatic on-canvas marker for the concepts that need scrutiny).**
Apply a `create-specialization` stereotype **«documented»** or **«inferred»** to those elements. **Leave `code` elements unspecialized** — absence of a stereotype means `code`, which keeps the majority of boxes clean. The stereotype is queryable via `get-specialization-usage`. Two constraints to plan for (both confirmed in practice):
- **ArchiMate profiles are type-bound, so each evidence stereotype multiplies per concept type.** «documented» on a Goal, a BusinessRole, and a Requirement is *three* separate profiles, not one — `list-specializations` will show several «documented»/«inferred» entries. This is normal; don't try to force a single shared profile.
- **Each element has only ONE primary specialization slot**, so the evidence stereotype *competes* with any domain stereotype (e.g. «microservice», «database»). Priority rule: give `code` elements their **domain** stereotype (the slot is free — code carries no evidence stereotype); for `documented`/`inferred` elements the **evidence** stereotype takes the slot, and the domain meaning falls back to the type + name. If you'd rather always keep the slot for domain stereotypes, treat channel 3 as optional and rely on channels 1, 2 and 4 — the property, documentation line and glyph already carry evidence on their own.

**4. Label expression (compact at-a-glance cue — expected by default; this is gate G4).**
After an element is placed on a view, set its `labelExpression` via `update-view-object` to `${name} ${property:evidenceMark}` — on **every** element view-object, so a reviewer sees provenance on the names without opening the Properties panel. This renders just the **single glyph** after the name, so it never overflows a normal box and `assess-layout`'s label-truncation check stays clean. **Do not** render the full word here. The only licensed degradation is a *rendering* failure, never an opt-out: if the deployment shows the literal `${...}` or the glyph font renders poorly, fall back to the ASCII marks `[c]` / `[d]` / `[i]` — still applied to every object. Skipping the glyph to lean on the stereotype + legend is **not** a substitute: the stereotype is a competing primary-specialization slot (channel 3, which `documented`/`inferred` elements may already spend, and which `code` elements deliberately leave empty) and the legend is one note off to the side — neither puts the cue on the name, which is the thing a human reviewer scans for. *Worked example — channel-3 (stereotype) priority:* a `code` Tool-handler class takes its **«Tool Handler»** domain stereotype; a `documented` subsystem takes the **«documented»** evidence stereotype; a plain `code` element that needs neither takes **no stereotype at all** (channel 3 left empty by design — the channel-4 glyph still carries its provenance).

**Legend placement — every view is self-decoding.** A reader often lands on a view by deep link, not via the index, so the glyphs must decode *where they stand*. Host the full legend on the index view, **and** append the one-line key to **every** view's note as its last line — it costs one line and makes each view independent. Where a view uses a **notation substitution** (see *Constraints & guardrails*), key it in the same note (e.g. "OR-branch shown as a Junction · directed Association = component→data access · Composition = component exposes its interface"). Keep each glance-legend to one lean line:

```
Legend: ● code · ◐ documented (doc-ref) · ○ inferred — structural | speculative.  No «stereotype» = code-grounded.
```

**Sizing the note (gate G10 — do this or the text clips).** When you call `add-note-to-view` — and any `update-view-object` that sets a note box — **omit the `height` parameter entirely**. The server auto-fits a note's height to its wrapped text (real glyph measurement, capped at ~600 px) *only when `height` is not supplied*; passing an explicit height takes the fixed-size branch and **clips the text**. You MAY set a fixed `width` (e.g. `720`) for uniform-width legends — that doesn't defeat the auto-fit. Keep copy lean so the note stays under the ~600 px cap. **Placement: pass `position:below-content`, never `above-content`** — a below-content note rides under the content as it grows, whereas an `above-content` note's `y` is stamped once and is silently invalidated when a container later grows upward (the note lands on the elements below). This is the *Annotate last* build-time rule (Phase 4 step 7); G11 (Phase 6) is the close-out backstop. <!-- Do NOT re-add an explicit note height here: it disables the server's text-fit and clips the legend. Set width only. -->

Note typography is pinnable for determinism — `add-note-to-view` / `update-view-object` accept `fontName`, `fontSize`, `fontStyle`, and `get-view-contents` reads them back, so a note's text size needn't be at the mercy of user defaults. (Set `fontSize` if you want repeatable rendering; no specific size is mandated here.)

This keeps the model honest *and* legible: a reviewer can query `evidence` programmatically, search the documentation, read the stereotype, or just glance at the glyph — and verified structure (`code`), stated intent (`documented`), and deductions (`inferred`) never blur together. (On a large model the legend lives once on the index view — see *Legend placement* above — rather than repeated on every diagram.)

### Verify drawn dependencies against ground truth — not only the docs

Relationships derived from architecture docs or naming can diverge from the code (drift, inverted direction, invented serving edges): a *doc-faithful* model is not necessarily *code-true*. Give every drawn **dependency** edge (`Serving` / `Realization` / `Access` and other cross-element dependencies) a **`verification`** property recording how its existence **and direction** were confirmed, at the strongest tier the environment offers (see the Phase-0 tooling probe):
- **`index`** — confirmed against a code-intelligence / call-graph index.
- **`grep`** — confirmed by a textual reference search proving the source symbol actually **references** the target (an import + a call-site, *not* a name-similarity match); record a representative `file:line`.
- **`unverified`** — from docs / diagrams / naming only; **listed on the final report's *Unverified edges* line.**

**Stratify:** direction-sensitive (`Serving` / `Access`), inferred, and architectural-**spine** edges MUST reach at least `grep` before you assert them as code-true; if they can't, they ship `unverified` and are flagged, not hidden. **Report the denominator** (e.g. `edges: 41 index / 12 grep / 6 unverified`) so a reader sees the provenance profile at a glance, not just a green tick. With `repoToArchi.tooling.search = none` you cannot run the search that would falsify an edge — mark such edges `unverified`; never imply a search you didn't run.

## VISUAL LANGUAGE — colour, icons & imagery (principles, applied by judgment)

Colour and imagery are communication tools, not decoration. There is no fixed scheme to follow — for each view, ask one question first: **what is this view trying to communicate, and does a styling choice make that easier to grasp?** Style only when the answer is yes. Tools: `update-view-object` (`fillColor`, `lineColor`, `fontColor`, `opacity`, `lineWidth`, `lineStyle`, `gradient`, font fields), `add-image-to-model` / `add-image-to-view` / `list-model-images`, and `imagePath` on an element.

### Colour — principles
- **Default is the baseline language.** Archi already colours by layer (Business/Application/Technology/Motivation). Keep those defaults *unless a deviation communicates something the defaults cannot* — then deviate deliberately, not decoratively.
- **One meaning per view.** Within a single view, colour should encode exactly one dimension (e.g. subsystem, internal-vs-external, criticality, lifecycle/deprecation, change-impact). Never let colour mean two things on the same diagram; the same colour must mean the same thing throughout that view.
- **Signal economy — colour the few, not the many.** If everything is coloured, nothing stands out. Leave most elements default and spend colour on what carries the view's message, so the eye goes there first.
- **Containers recede, children advance — differentiate nesting on lightness, never on hue.** A container painted the *same* fill as its children reads as one flat blob (the recurring "parent and children all green" complaint). Keep the container's layer hue — hue *is* the layer signal, so never grey-out a container (that throws the layer information away) — but push its **value**: container fill ≈ the child fill blended ~75% toward white (a pale wash that still names the layer, e.g. `#EAF3F8` Application, `#FFF6E6` Business, `#EAF6EA` Technology), plus a **1–2px outline a few steps *darker* than the child hue** to draw the boundary, and the container title **one step larger and semibold**, top/left-aligned (not centred under its children). A doubly-nested container takes the wash *and* the outline so two containment levels read without a legend. Recede via **lightness, not opacity** — transparency muddies colour and breaks contrast; keep opacity at 100%.
- **Label contrast is non-negotiable — every label clears ~4.5:1 against the fill it sits on.** If a fill is darker than ~50% lightness, flip its label (`fontColor`) to white. This kills the whole "dark fill swallows the text" class — the black-junction-eats-its-label artefact among them.
- **Colour reinforces, never carries alone.** Pair any colour signal with label, shape, grouping, or the evidence glyph/stereotype so the view still reads when printed greyscale or seen by a colour-blind reader. Use a muted, accessible palette with strong text contrast; let `deriveLineColor` keep borders harmonious. Reserve strong warm/red for genuine warnings (deprecated, risk) — don't spend it casually.
- **Consistency across the model.** If a hue means "Payments" or "external system" in one view, reuse it in every view. Maintain one implicit colour key for the whole model.
- **Document any deviation.** When you depart from the layer defaults, state the colour key in that view's legend note so the meaning is explicit, never guessed. (Evidence is already carried by the glyph + stereotype — don't also spend fill-colour on it unless a specific view genuinely benefits.)

### Icons & imagery — principles
- **ArchiMate type icons are the baseline; never obscure them.** Custom imagery augments the notation, it doesn't replace it.
- **Use an image only where recognition beats reading.** The high-value case is vendor/technology logos on Technology elements (datastores, brokers, runtimes, cloud services) so landscape and deployment views are scannable at a glance. Elsewhere, the type icon usually wins.
- **Earn the file cost.** Images embed into the model and bloat it. Register once with `add-image-to-model` and reuse via `list-model-images` across views; prefer a small curated set; keep images small; don't icon-ify elements that don't need it.
- **Sourcing — the web is fair game, licensing is not optional.** If your environment has web access, you may search the web for relevant logos/icons (otherwise use a local asset folder, or skip imagery). Prefer official brand/press-kit assets or permissively-licensed / public-domain images; respect each vendor's trademark usage guidelines, honour attribution requirements, and avoid paywalled, watermarked, or unclear-licence images. Remote fetches are size-bounded by the server. If no asset clears licensing, **skip the image rather than use a questionable one** — the type icon alone is fine.
- **Placement — never obscure the label.** The element label renders in the **top band**, and Archi's *default* `imagePosition` (`top-left/centre/right`) sits right on top of it. Set `imagePosition` to a **`bottom-*`** anchor for a corner logo, or **`fill`** for a subtle background watermark — never a `top-*` position on a labelled element. Use `showIcon` (`if-no-image` / `always` / `never`) so the ArchiMate type icon and your custom image don't crowd the same corner.
- **Mind the rendering caveats.** Specialization icons can render oversized, and some font/gradient styling is ignored on image visuals. Verify on the view (`export-view` / `assess-layout`) and back off if imagery harms legibility.
- **Don't double-encode.** If a «database» specialization already says "datastore," a logo may be redundant — pick the single cue that communicates best for the view's audience.

### Match the audience
A stakeholder landscape view and a developer structure view want different things from colour and imagery. Let the view's purpose and reader decide — detail for engineers, clarity and recognition for stakeholders. When unsure, prefer restraint: an under-styled model is readable; an over-styled one is noise.

## CONSTRAINTS & GUARDRAILS

- **Names match the domain.** Use the codebase's own terms; don't invent grandiose labels.
- **Be conservative with inference.** A thin, defensible model beats a broad, speculative one. If Strategy/Motivation evidence is absent, omit those layers rather than fabricate them.
- **Architecture clarity outranks ArchiMate purity — within two non-negotiables.** Deviate from the standard whenever a non-standard use communicates the intended architecture message more clearly to a consumer who may not know ArchiMate (e.g. swimlanes-by-nesting for a process flow, an OR-branch drawn as a Junction, a directed Association meaning "reads from"). **(1) Never blur provenance (gate G13)** — a creative rendering must never make a `documented`/`inferred` concept look like a `code`-mined fact; the evidence grade is sacred. **(2) Key every *meaning-bearing* deviation** — if your usage would make a reader applying standard ArchiMate semantics *misread* a concept or relationship, record the substitution on **both rails** (below). Purely *presentational* choices (spacing, nesting-for-grouping, colour) need no key — don't legend-spam.
- **Provenance and deviations ride two rails — a machine rail and a human rail.** The same fact is recorded twice, on purpose, for two audiences: the **machine rail** is an element/relationship **property** (queryable, survives export, read by tools and the next run); the **human rail** is the **view legend line** plus the **documentation** field (read by a person at the canvas). This is one doctrine behind several rules here — evidence marking, deviation keying, and the coverage record all follow it; it is not redundancy to be trimmed.
- **Bind the onion's levels.** When an `onion = stack` model spans altitudes, the same element shown at L0/L1/L2 must be linked by a durable decomposition (Composition/Aggregation, or nesting) — the relationship type is your call, the **binding is mandatory**, so the model navigates as one onion (see *Phase 4 — the onion's spine*).
- **Idempotent & resumable.** Re-running against the same model must not create duplicates — reconcile against existing content first (`get-or-create-element`, search before create). Use stable, code-derived names so a resumed run matches existing elements, and re-query IDs after any context compaction rather than reusing remembered ones — **especially for unnamed objects (notes, images, junctions, groups), matched by content/geometry, never by batch position** (gate G12; see *Working mode*).
- **Batch writes** with `bulk-mutate` and `$N.id` back-references; keep batches per-subsystem so they are reviewable and the diagnostics are legible.
- **Respect sound refusals** from density/precondition checks — adjust layout, don't force.
- **Decide-and-log by default; ask only when being wrong is expensive.** On a judgment call, **decide and log it** (record the choice + reasoning + confidence in the disposition ledger) — *unless* all three hold: the choice is costly to reverse after the model is built, you genuinely lack evidence to choose between materially different options, and guessing wrong wastes significant work. Then **ask** — but batch questions to the close-out checkpoint, except a single question that changes the whole model's shape (e.g. "one service or three bounded contexts?"), which you ask before building. More than ~5 open questions means you are under-deciding — push the reversible ones back to decide-and-log. Throughput pressure is never a reason to skip a significant unit, nor to default to a cheap flat layout (see *Phase 4 step 0*).
- **Never silently drop** something you couldn't model; list it in the final report.
- **Stay read-only until Phase 3** — analyse fully before the first mutation.
- **Trace why→what.** Connect Motivation/Business elements to the Application/Technology that realises or serves them (Realization / Serving / Influence) wherever docs, code, or a *structural* inference supports it — the motivation/business layers must not float disconnected from the structure they explain. Surface this on the motivation and/or context view.
- **Junctions, folders & `&` literals.** Create OR/AND junctions with `type:"Junction"` — there is no `OrJunction`/`AndJunction` EClass (the AND/OR distinction is a junction attribute; name each outgoing branch on its Triggering/Flow). **Keep junctions tiny — set `width`/`height` ≈ 14×14 when you add one to a view; never leave the 120×55 add-default.** Archi scales a junction's solid (dark/black) fill to its bounds, so a 120×55 junction renders as a big dark oval — a large target for a passing connection label to land on and be swallowed; a genuinely tiny junction is a small dot that branch labels naturally clear, and that small solid fill is *correct* ArchiMate (do **not** recolour it merely to decorate). **A junction's *name* is never rendered on the canvas** — Archi has never drawn junction names (forum topic 331), so a name is invisible model metadata: it is neither the cause nor the cure of any "black junction, unreadable text" artefact. That artefact is *always* a *connection label landing on the junction* whose dark fill swallows it — so carry the branch meaning on the outgoing-edge labels, kept clear of the junction geometry, never as a node-style label on the junction itself. On 5.7 there is no channel to *move* a label off its own endpoint (Label Offset is 5.10), so in the rare case a tiny junction still cannot clear a label, fall back to a **hollow junction** (thin dark outline, white fill) so the overlapping label stays legible — the fallback for an unavoidable overlap, not the default. **Close-out self-check (gate G9 — every behaviour/flow view): export-view and look — no junction may render oversized, and no connection label may sit on a junction's fill** (assess-layout's `labelOverlapCount` under-counts a label grazing a junction, so trust the render); fix any before declaring the draft ready. **Do not pass a layer-subfolder `folderId` for a Junction** — Archi then refuses to save ("object is in wrong folder type"); let it default to the *Other* folder, or `move-to-folder` it there. **Never HTML-escape names/labels** — write a literal `&`, not `&amp;` (Archi renders the literal `&amp;`).
