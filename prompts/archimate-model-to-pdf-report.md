# Prompt — Generate a PDF Architecture Report from an Archi model

> **How to use:** Open an agent session (Claude Code, or any agent) that is connected to the
> **Archi MCP Server** with a model loaded, then paste everything below the line into the chat.
> The prompt is model-agnostic — it works for any ArchiMate model exposed over the MCP.
> It **pauses once** to let you confirm the view sequence / table of contents before rendering.
>
> **Optional:** if the model was generated by a prompt, paste that prompt (or its file path) when you
> launch — it will be recorded verbatim in Appendix C for provenance. See *Optional Inputs* below.
>
> Renders best with **WeasyPrint** (true page-number margin boxes) — auto-detected and preferred if
> installed; otherwise falls back to any Chromium browser (Chrome / Edge) headless print-to-PDF.

---

## ROLE

You are a technical documentation engineer producing a polished, print-ready **PDF architecture
report** from a live ArchiMate model, read **exclusively** through the **Archi MCP Server** tools.
You never invent architecture content: every fact, diagram, and description comes from the model.
Where the model is silent (e.g. an element has no documentation), you say so plainly rather than
fabricate. The finished PDF must look professionally typeset: cover page, table of contents,
headings, captioned figures, tables, bold/italic emphasis, layer colour accents, and a running
footer carrying provenance.

## OPTIONAL INPUTS

The user may supply any of these when launching the prompt; each is optional and the report
degrades gracefully when absent:

- **Generating prompt** — if the model was produced by prompting an agent (e.g. a reverse-engineering
  or greenfield-modelling prompt), the user may paste that prompt, or give a file path to it. When
  provided, include it verbatim in **Appendix C** and mark the model's *generation method* as
  "prompt-generated" in the provenance block. If the user does not provide it, also check the model's
  own `properties` for a stored copy (keys matching `prompt|generatingPrompt|sourcePrompt|generation`);
  use that if present. If neither exists, omit Appendix C and record the generation method as *"not recorded."*
- **Page size** — `A4` (default) or `Letter`.
- **Output directory** — defaults to `./archi-report/<model-slug>/`.

## HARD RULES

1. **Read-only.** Use only *query* MCP tools (`get-model-info`, `get-folder-tree`, `get-views`,
   `get-view-contents`, `get-element`, `get-relationships`, `export-view`, `list-model-images`).
   Do **not** call any mutating tool (`create-*`, `update-*`, `add-*`, `bulk-mutate`, `layout-*`,
   `auto-connect-*`, `clear-view`, `set-*`). This report must not alter the model.
2. **Provenance honesty.** The MCP field `modelVersion` is a *session mutation counter*, **not** the
   model's saved version or file date. Never present it as a version. Build provenance from the
   model name/purpose, any version/date/author found in **model properties**, and the
   **report generation timestamp** (get it via `date -u '+%Y-%m-%d %H:%M UTC'`). Label the session
   counter, if shown at all, as an internal "snapshot marker."
3. **One approval gate.** After discovery you MUST present the proposed view order + TOC and wait
   for the user to approve or reorder. Do not render before approval.
4. **Self-contained output.** Embed every diagram in the HTML as a base64 `data:` URI so the report
   renders identically across all PDF toolchains and needs no sibling asset files.
5. **Faithful counts.** Element/relationship/view counts in the report must match `get-model-info`.
   Reconcile before rendering; if they differ, explain why (e.g. elements not placed on any view).

## WORKFLOW

### Phase 0 — Preflight & toolchain detection

1. Confirm the MCP is live and a model is loaded: call `get-model-info`.
   - If it fails or returns no model, STOP and tell the user to load a model in Archi and confirm
     the MCP connection.
2. Establish a working directory for assets/output:
   `mkdir -p ./archi-report/<model-slug>` (slug = model name, lowercased, non-alphanumerics → `-`).
3. Detect an available PDF toolchain by probing, in this **preference order**, and record the winner:
   ```bash
   for t in weasyprint prince wkhtmltopdf pandoc; do command -v "$t" && break; done
   command -v chromium google-chrome chrome 2>/dev/null
   ls "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" 2>/dev/null
   ls "/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge" 2>/dev/null
   ```
   Preference: **weasyprint** → **prince** → **Chromium-family headless** (chrome / chromium / edge)
   → **wkhtmltopdf** → **pandoc + LaTeX**. See "Rendering" for the exact command per tool.
   - If **none** is available, STOP before rendering and offer: `pip install weasyprint`
     (best) or use any installed Chromium browser. Do not silently produce only HTML without saying so.

### Phase 1 — Model overview & provenance harvest

1. From `get-model-info` capture: `name`, `purpose`, `elementCount`, `relationshipCount`,
   `viewCount`, `specializationCount`, `elementTypeDistribution`, `relationshipTypeDistribution`,
   `layerDistribution`, and the model **`properties`** map.
2. Scan `properties` (case-insensitively) for provenance keys — e.g. `version`, `date`,
   `last modified`, `author`, `owner`, `status`, `release`. Whatever exists goes in the provenance block.
3. Record the report generation timestamp (`date -u`).
4. Resolve the **generating prompt** (optional): use the user-supplied text/file if given; else scan
   model `properties` for a stored copy (see Optional Inputs). Set *generation method* accordingly
   ("prompt-generated" / "not recorded") for the provenance block, and hold the prompt text for Appendix C.

### Phase 2 — Structure discovery & optimal view sequence

1. Call `get-folder-tree` (Views/Diagrams folder) and `get-views` to enumerate **every** view with:
   `id`, `name`, `viewpointType`, `folderPath`, `documentation`, `properties`.
2. Compute the **optimal reading sequence** with this generic heuristic (state your reasoning briefly):
   1. **Respect the modeller's folder order first** — `folderPath` encodes intended narrative; keep
      views grouped by folder, folders in their tree order.
   2. **Front-load orientation views** — any view whose name or viewpoint implies a big picture
      (matches `overview|landscape|total|layered|context|introduction|motivation|strategy`) leads
      its group, to orient the reader before detail.
   3. **Within a group, order by ArchiMate abstraction**, most-abstract → most-concrete:
      *Motivation → Strategy → Business → Application → Technology → Physical → Implementation & Migration → Other/Composite.*
      Infer a view's bucket from its `viewpointType`; if generic ("Total"/none), infer from the
      dominant layer of its elements (peek `get-view-contents` if needed).
   4. Stable-sort so ties keep folder/alphabetical order.
3. **APPROVAL GATE** — present a numbered proposed Table of Contents (view name · viewpoint · folder),
   plus the planned appendices, and ask the user to approve or reorder. **Wait.** Proceed only on approval.

### Phase 3 — Content harvest (per view, in approved order)

For each view:
1. `export-view` → **PNG**, `inline: false`, `outputDirectory: ./archi-report/<slug>/assets`,
   at a generous scale for print crispness. Capture the returned `filePath`, `width`, `height`.
   - If a view fails to render, note it and continue (placeholder caption "diagram unavailable").
2. `get-view-contents` → elements (each carries `documentation` + `properties`), relationships,
   `groups`, `notes`, `connections`.
3. Accumulate a global **element catalog**: keyed by element `id`, storing name, type,
   specialization, layer, documentation, properties, and the set of views it appears in.
4. Convert each PNG to a base64 `data:image/png;base64,...` URI (`base64 -i <file>`), for embedding.

### Phase 4 — Compose the HTML document

Generate a single self-contained `report.html` (structure below), using the **design system** further
down. Then render it to `report.pdf` with the detected toolchain.

**Document structure**

1. **Cover page** — model name (large), subtitle "Architecture Report", the provenance block
   (see Rule 2), and a line "Generated from the live Archi model via the Archi MCP Server."
2. **Document control** — a provenance table: Model, Purpose, Version/Date/Author (from properties,
   or *"not recorded in model"*), **Generation method** (prompt-generated → "see Appendix C" / not
   recorded), Report generated (timestamp), Views documented (N), Elements (N), Relationships (N).
3. **Executive summary** — the model `purpose` as prose; a metrics strip (elements, relationships,
   views, specializations); a **layer distribution table** (layer · count · % ) rendered with layer
   colour accents; a viewpoint-coverage line.
4. **Table of contents** — the approved view order + appendices, with section numbers.
5. **View sections** (approved order). Each view = one `<section class="view">`:
   - `<h2>` "N. <view name>"; a **viewpoint badge** + folder-path breadcrumb underneath.
   - View `documentation` as prose (italicise a *"No view documentation recorded."* fallback).
   - The diagram: `<figure>` with the embedded PNG and a **numbered caption**
     *"Figure N — <view name>"* (italic caption). Keep figure + caption together (no page break inside).
   - **Elements in this view** — a table: Name (**bold**) · Type (*italic*) · Layer (colour dot) ·
     Documentation (first ~200 chars, "… (see catalog)" if truncated). Layer-tint the row's left edge.
   - **Notes / annotations** — bullet the text of any `notes`.
   - **View properties** — a small key/value table if `properties` is non-empty; else omit.
6. **Appendix A — Element catalog** (comprehensive). Group by ArchiMate layer (in abstraction order);
   within a layer, alphabetical. Per element: name (**bold**, with layer colour accent), type +
   specialization (*italic*), full `documentation` (or *"No documentation recorded."*), a properties
   table if any, and *"Appears in: view1, view2, …"* cross-reference. This is the heart of a
   comprehensive report — do not abbreviate documentation here.
   **For 100% coverage**, don't rely only on elements harvested from views — also sweep
   `search-elements` with `query:""` (paginate via `_meta.cursor`) to pick up elements that exist in
   the model but aren't placed on any diagram, and mark those *"Appears in: — not placed on any view."*
   Reconcile the catalog count against `get-model-info.elementCount`.
7. **Appendix B — Relationship register** (optional but include): a table Source → Type → Target,
   sorted by source name. For **100% coverage**, sweep `search-relationships` with `query:""`,
   `fields:"full"` (paginate via `_meta.cursor`) — `fields:"full"` returns resolved `sourceName`/
   `targetName`, so off-view endpoints still render by name. Reconcile against
   `get-model-info.relationshipCount`. (View-only harvesting from `get-view-contents` will miss any
   relationship not drawn on a diagram.)
8. **Appendix C — Model generation prompt** (include *only* if a generating prompt was resolved in
   Phase 1). Render the prompt **verbatim** inside a `<pre class="prompt">` block (preserve whitespace,
   do not paraphrase or re-wrap). Precede it with a short line stating the source ("supplied by user" /
   "recorded in model property `<key>`") and, if known, the tool/agent that ran it. This lets a reader
   reproduce or audit how the model was generated.
9. **Colophon** — tool + MCP note, generation timestamp, and the "snapshot marker" if you choose to show it.

**Running footer (every page):** a fixed footer element — `Model · Version/Date · Report generated <ts>`.
(True "Page X of Y" requires weasyprint/prince margin boxes; on Chromium the fixed footer still
repeats on every page, just without a live page number. That's acceptable.)

### Phase 5 — Render & QA

1. Render `report.html` → `report.pdf` (see Rendering).
2. QA checklist — verify and report:
   - PDF exists, non-trivial size, page count.
   - Every approved view has a figure (or an explicit "unavailable" note).
   - Provenance block present and correct; `modelVersion` **not** mislabelled as a version.
   - Report counts reconcile with `get-model-info`.
   - No broken/empty images; TOC matches sections.
3. Report the absolute output path, page count, and a one-line manifest (views documented / elements
   catalogued / relationships listed).

## DESIGN SYSTEM (embed as a `<style>` block in the HTML `<head>`)

Goal: clean, corporate, readable. A4 default (swap to Letter if the user prefers). Serif body for
readability, sans headings, generous whitespace, subtle layer colour accents, no gaudy borders.

```css
:root{
  --ink:#1a1d21; --muted:#5b636b; --line:#d9dee3; --bg-alt:#f6f8fa; --accent:#2f5d8a;
  /* ArchiMate layer accents */
  --motivation:#B39DDB; --strategy:#E7C79A; --business:#F2E4A6;
  --application:#9FD3E8; --technology:#A9DCB4; --physical:#8FC7A0;
  --implementation:#F3C1A0; --other:#C4CBD2;
}
@page{ size:A4; margin:20mm 18mm 22mm 18mm; }
*{ box-sizing:border-box; }
body{ font:11pt/1.5 "Georgia","Times New Roman",serif; color:var(--ink); margin:0; }
h1,h2,h3,h4,.sans{ font-family:"Helvetica Neue",Arial,sans-serif; color:var(--accent); line-height:1.2; }
h1{ font-size:30pt; } h2{ font-size:19pt; border-bottom:2px solid var(--line); padding-bottom:4pt; margin-top:0; }
h3{ font-size:14pt; } h4{ font-size:12pt; color:var(--muted); }
a{ color:var(--accent); text-decoration:none; }
em{ color:var(--muted); }

/* Cover */
.cover{ height:257mm; display:flex; flex-direction:column; justify-content:center; page-break-after:always; }
.cover .title{ font-size:34pt; } .cover .subtitle{ font-size:16pt; color:var(--muted); margin-top:4pt; }
.provenance{ margin-top:24pt; border-left:4px solid var(--accent); padding:8pt 14pt; background:var(--bg-alt); }
.provenance div{ margin:2pt 0; }

/* Views + figures */
section.view{ page-break-before:always; }
figure{ margin:14pt 0; text-align:center; page-break-inside:avoid; }

figcaption{ font-style:italic; color:var(--muted); font-size:10pt; margin-top:6pt; }
.badge{ display:inline-block; font:9pt/1 sans-serif; background:var(--accent); color:#fff;
        padding:3pt 8pt; border-radius:10px; }
.breadcrumb{ color:var(--muted); font-size:9pt; margin-left:8pt; }

/* Tables — CRITICAL: prevent right-margin overflow.
   Auto table-layout lets a long unbreakable token (a package path, a long
   element name like AgentAuthoredCompoundCommand) widen a column until the
   whole table runs off the page and cells clip. So: use table-layout:fixed
   with an explicit <colgroup> on any wide (3–4 column) table, and let cells
   break long words. Give the ArchiMate *type* column enough width (~28%) so
   "ApplicationComponent" — the most repeated value in any model — fits on one
   line. Use overflow-wrap (breaks only when needed), NOT word-break (which
   splits mid-word unnecessarily). Keep the table font ~9pt. */
table{ width:100%; border-collapse:collapse; font-size:9pt; margin:10pt 0; page-break-inside:auto; }
table.fixed{ table-layout:fixed; }   /* + <colgroup><col style="width:…"> per column */
th{ text-align:left; background:var(--bg-alt); border-bottom:2px solid var(--line); padding:5pt 7pt; overflow-wrap:break-word; }
td{ border-bottom:1px solid var(--line); padding:5pt 7pt; vertical-align:top; overflow-wrap:break-word; }
tr{ page-break-inside:avoid; }
tbody tr:nth-child(even){ background:#fbfcfd; }
/* Element table columns that survived testing: Name 20% · Type 28% · Layer 14% · Description 38%.
   Relationship register: Source 30% · Type 16% · Target 30% · Label 24%. */
.name{ font-weight:bold; } .type{ font-style:italic; color:var(--muted); }

/* Layer accents — apply .layer-<x> to a row/card */
.dot{ display:inline-block; width:9px; height:9px; border-radius:50%; margin-right:5px; vertical-align:middle; }
.layer-Motivation   { border-left:4px solid var(--motivation); }   .dot.Motivation{background:var(--motivation);}
.layer-Strategy     { border-left:4px solid var(--strategy); }     .dot.Strategy{background:var(--strategy);}
.layer-Business     { border-left:4px solid var(--business); }     .dot.Business{background:var(--business);}
.layer-Application  { border-left:4px solid var(--application); }  .dot.Application{background:var(--application);}

.cat-item{ padding:6pt 0 6pt 10pt; margin:6pt 0; page-break-inside:avoid; }

/* Running footer — repeats on every printed page in Chromium & paged engines */

              color:var(--muted); border-top:1px solid var(--line); padding-top:3pt;
              display:flex; justify-content:space-between; }
/* weasyprint / prince page numbers (ignored by Chromium) */
@media print{ .pageno::after{ content:counter(page) " / " counter(pages); } }
```

Add the footer once near the top of `<body>`:
`<div class="page-footer"><span>{model} · {version-or-date}</span><span>Report generated {ts} · <span class="pageno"></span></span></div>`

## RENDERING (use the toolchain detected in Phase 0)

```bash
# 1. weasyprint (BEST — real page numbers, margin boxes)
weasyprint ./archi-report/<slug>/report.html ./archi-report/<slug>/report.pdf

# 2. prince
prince ./archi-report/<slug>/report.html -o ./archi-report/<slug>/report.pdf

# 3. Chromium family (Chrome / Chromium / Microsoft Edge) — repeats fixed footer, no live page #
"<chromium-binary>" --headless=new --disable-gpu --no-pdf-header-footer \
  --print-to-pdf="./archi-report/<slug>/report.pdf" \
  "file://$(pwd)/archi-report/<slug>/report.html"
# macOS Edge binary: "/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge"

# 4. wkhtmltopdf
wkhtmltopdf --enable-local-file-access ./archi-report/<slug>/report.html ./archi-report/<slug>/report.pdf

# 5. pandoc + LaTeX (last resort; weakest layout control)
pandoc report.md -o report.pdf --pdf-engine=xelatex
```

Because all diagrams are embedded as base64 `data:` URIs, no `--allow-file-access` image flags are
needed and the HTML is fully portable.

## OUTPUT

Deliver `./archi-report/<model-slug>/report.pdf` and report its absolute path, page count, and the
manifest (views documented · elements catalogued · relationships listed · toolchain used). Keep the
intermediate `report.html` alongside it so the user can tweak styling and re-render without re-querying.
