# Changelog

## v1.9.0 (2026-09-07)

> Everything below is stated relative to **v1.8.0**; intermediate states that existed only during the v1.9 cycle are folded into the entry describing the shipped behaviour.

Response-honesty release — making a mutating tool's answer match what the model actually holds. The headline is a **cross-tool invariant**: a mutating tool must report *effective* state (what persisted, after Archi's own auto-fit and cascades) and never echo the values the caller asked for, enforced by a contract test and a committed gap registry that fails the build when a registered tool is classified nowhere. Applying it closed a family of related defects: the geometry, ancestors and anchored children a placement or layout pass actually moved are now on the wire (`effectiveBounds`, `resizedAncestors`, `resizedGroups`, `movedObjects`, `nestedContainersFitted`), a connection mutated inside a bulk call reports the state it actually holds (`effectiveConnection`), a renamed entity reports the name it ends up with (`entityName`), and a value that is only *projected* — inside an open batch, or awaiting approval — is labelled as a projection instead of masquerading as state. The same pass fixed why those reports were wrong so often: **a prepare that read the live model while later-executing queued commands had already changed it**. A batch can now create a view, create an element, place one in the other, address a container it created a moment earlier, anchor to an object that does not exist yet, and have every parent-fit cascade measured against one shared same-batch geometry. Integrity guards that ran only at prepare time — folder cycles, view-hierarchy and layer placement, specialization usage, and the container a placement targets — now **re-check at execute time** and decline with a named reason, closing silent data loss on the batch, bulk and approval paths. The human approval gate gains the blast radius on the card, the refusal's own reason instead of a generic guess, a refusal when the cascade has outgrown what was reviewed, and a card that finally **describes the whole write it is asking you to authorise** — every parameter the approval will apply disclosed, and the card's own sentence naming the aspects that will change rather than one of them, both held by a contract test over all 42 proposal sites; the deletion family gains real cascade counts, cascades sketch and canvas views instead of destroying them uncounted, and stops undo restoring siblings to the wrong position. On the layout side `layout-within-group` gains **`recursiveChildren`** for multi-level nested inventories, `auto-layout-and-route`'s grouped mode lays out the whole subtree instead of one level, `auto-connect-view` gains a **`relationshipIds`** allow-list, `auto-route-connections` can hide the labels that have nowhere to go (**`labelPolicy`**, off by default) and reports a full re-route that increases crossings, `auto-layout-and-route` says **why** its quality loop stopped, and `assess-layout` learns to see overlay-icon collisions and cross-branch overlaps — and, just as importantly, to stop claiming coverage it does not have. Alongside that, an **ArchiMate `Grouping` is now treated everywhere as the container it renders as**: Archi draws two different objects as containers, and every layout, routing, discovery and assessment pass recognised only the native view group — so the one-`Grouping`-per-zone shape this server's own guidance prescribes was skipped by the arrangement tools, rejected outright by three of them, miscounted by `get-view-contents`, routed around as a solid obstacle, and certified clean by detectors that had never examined it. The assessor also learns where a title is actually drawn, reading each object's own horizontal *and* vertical title placement instead of assuming centred-and-top, and stops certifying a title it never measured. New objects gain the palette's own title alignment. `add-image-to-model` gains batch import. The `prompts/` library gains its second ready-to-use agent prompt: where `repo-to-archimate-model.md` *builds* a model from a code repository, the new one *documents* one — turning any open Archi model into a print-ready **PDF architecture report** generated entirely over the read-only query tools. The reference library also becomes reachable from clients that do not expose MCP resource reads to the model: the same 14 bodies are now published as resource templates and through a new `get-guidance` tool, taking the surface to **70 tools** and **14 resources**.

### Response honesty

- **A mutating tool must report what the model holds, not what the caller asked for — and that is now enforced.** Archi silently auto-fits a container to its children, so a requested `width`/`height`/`x`/`y` may not survive the write; a `success` response that echoes the request while the model diverged is a correctness defect, because the client is an agent that cannot see the canvas and will build its next call on the wrong number. A contract test over every registered tool now requires each to classify exactly once — read-only, covered by an oracle, or a known gap with a stated reason — and **a tool classified nowhere fails the build**. Two rulings are baked in: **a count or a flag is not effective state** (`resizedCount: 3` leaves an agent unable to say where anything went), and **batched and proposal modes discharge the invariant by labelling, not by value** — nothing is effective in those modes by construction, so the entity sits under `preview` beside a `batch` or `proposal` sibling and never at the top level of `result`.
- **The geometry a placement or layout pass actually landed is now on the wire, per operation.** Every `bulk-mutate` operation carries `effectiveBounds` re-read after the write, plus `resizedAncestors` (the containers a placement grew, with their new rectangles) and `movedObjects` (the anchored children a resize or move displaced). Deletions on the bulk path — which returned a null entity type and no cascade counts at all — now carry the standalone tool's own deletion result verbatim, so the two paths cannot drift apart again. Folder and specialization CRUD responses derive their reported names from what was written, so a normalized or trimmed value is visible to the caller.
- **`add-to-view` with `autoConnect` no longer draws a line from an object to the container it just nested inside, and both auto-connect passes now name what they declined.** On a view, nesting already expresses containment, so a connection between a child and its container leaves the box and re-enters it — the self-pass-through `assess-layout` reports. `auto-connect-view` has declined that pair since it learned to see it; its sibling, which scans the same relationships while placing, drew it — on exactly the nested shape this server's own layout guidance prescribes, so placing a function inside its owning component created the defect the assessor exists to catch. **This is a behaviour change**: a nested `add-to-view` with `autoConnect: true` now leaves that connection undrawn. The model relationship is untouched, and the response names the pair under **`skippedDueToNesting`** — the sibling's spelling, carrying both view-object ids and the relationship id — so an agent that wants the line draws it with `add-connection-to-view`. A flat placement is unaffected and serializes exactly as it did. The same response gains **`skippedByCap`**, naming the connections the fifty-connection cap dropped: `skippedAutoConnections` counted them and named none, and a count of dropped work is something an agent can neither draw nor ignore. The count is kept and is now exactly the size of the list beside it. Finally, `auto-connect-view`'s **approval card** carried those suppressed pairs as a bare integer — on the one surface a human authorises from, the pairs collapsed to a number — and now carries the pairs themselves, omitted entirely when nothing was declined.
- **A placement now names the container it landed in — on every path that places something.** A nested object's `x`/`y` are relative to its immediate parent's top-left corner, so a response reporting a rectangle and not its origin was a frame with no origin: the client is an agent that cannot see the canvas, and *30 from the left of what* was the one question it could not answer. `add-to-view` and `update-view-object` now carry **`parentViewObjectId`**, the same key `get-view-contents` already publishes, and every `bulk-mutate` operation on a view object carries it per operation, re-read from live containment after the whole call has been applied. Two sibling paths were worse than silent and are corrected with it: `add-group-to-view` reported a hardcoded `null` for **every** group it nested, which a client reads as *this group sits on the view*, and `add-note-to-view` reported whatever the request had asked for under a name that reads as an outcome. The value is taken from the resolved container, never from the request — a request names a parent as a reference still to be resolved, and one that resolved to a container the caller did not intend is exactly the case the field exists to expose, so echoing the request there would repeat the caller's own mistake back as confirmation. Measured on a live run, that is not hypothetical: two positional back-references landed two components inside the wrong siblings, nothing rejected them because both nestings are legal ArchiMate, and they surfaced two tool calls later as an unrelated detector's boundary count with nothing left to attribute them to. Absent, as before, for an object that sits on the view itself, so a top-level placement serializes exactly as it did.
- **A connection created or restyled inside `bulk-mutate` now reports the state it actually holds.** The per-operation entry named the relationship type and nothing else, so batching cost you every connection fact the standalone tools give you. Each operation on a view connection now carries `effectiveConnection` — the same report the single-tool caller gets, read *after* the whole call has been applied. That ordering matters most for anchor points: they are absolute canvas centres derived from the endpoints' live geometry, so a later operation that moves an endpoint changes them without ever naming the connection. Absent, as before, wherever nothing was written.
- **Five view passes that moved things silently now say what they moved.** `update-view-object` names the objects it moved and the containers it grew; `layout-within-group` returns `resizedAncestors` / `ancestorsResized` upward and `nestedContainersFitted` downward, with `groupResized` sourced from a measured change rather than the caller's `autoResize` request, so a repeated layout that changes nothing honestly returns `false` — and it now also returns **`ancestorPropagation`**, because the upward half's count was honest and still undecodable (see below); `adjust-view-spacing` reports the groups it grew underneath itself; `resize-elements-to-fit` reports both the groups it grew and the objects it displaced; and `add-to-view` reports the containers it grew to clear an icon corner — a reservation that grows the icon-bearing parent *and* its grandparent group, neither of which the response used to name.
- **A true count that could not be decoded is now decodable.** Continuing the bullet above: `layout-within-group`'s `ancestorsResized: 0` was honest and useless, because the same zero is produced by five different situations that ask for different actions — and the published description filled that gap by naming the *wrong* exclusion. It disclosed that the upward pass stops at a non-native ancestor, while the exclusion that actually fired on the measured call was that the pass never *starts* from one: name an ArchiMate-element container as the target and nothing above it is touched. `ancestorPropagation` is a stable kebab-case code plus a short phrase, resolved beside the walk from the object the walk stopped on rather than re-derived afterwards by re-reading the parent chain. It is **not** conditional on the count being zero, because the count does not partition the reasons in either direction: `propagated` alone guarantees a positive count, five codes always report zero, and `stopped-at-non-native-ancestor` and `depth-cap-reached` each arrive with either. Those two are the only ones that leave work undone, so a **positive** count there is the most misleading number the response can hold — the exact consequence the old description asserted with no way to observe it. `nextSteps` names the remedy for all three codes that leave work undone. The scoping itself is unchanged and deliberate, and is now recorded as such beside its opposite: the sibling `arrange-groups` **widened** what counts as a container because the caller names the object there, while this pass traverses ancestors the caller never named, so it **discloses** instead of widening. `adjust-view-spacing`, which drives the same pass under the same restriction, states the restriction in its description rather than gaining a second reason-code surface.
- **A count that was never measured no longer reads as a measurement.** An ancestor whose rectangle did not change is no longer counted or listed, and `delete-relationship`'s two structural zeros are pinned as *correct* rather than left ambiguous. The wire is now checked directly, because a response map built key by key can compute a field and never send it: a **path-parity axis** on the contract test compares standalone and bulk leaf field names for every oracle-covered tool reachable through `bulk-mutate`, so a newly bulk-reachable tool must register or fail.
- **A bulk `update-relationship` or `update-element` reports what the concept now holds.** A bulk `update-relationship` reads a full semantic-attribute bundle — `accessType`, `associationDirected`, `influenceStrength` — and told the caller nothing about what any of them became, because the post-dispatch pass branched on exactly two live types and an ArchiMate relationship is neither. Each operation now carries **`effectiveRelationship`**, and `update-element` carries **`effectiveElement`**: a re-read of the concept after the whole compound has been dispatched, composed from the same readers the single-tool response uses, so a subtype that cannot hold an attribute omits it here exactly as it does there. Measured on a live model: an operation that requested `"+"` reports `"+++"`, because a later operation in the same call changed it — a prepare-time projection would have reported `"++"` and an echo would have reported `"+"`. The report is keyed on the resolved entity's type and gated on the entry already describing its entity, so it strengthens a report rather than inventing one.
- **A prepared folder, model or move is described instead of coming back anonymous.** The per-operation mapping had no branch for a folder, for the model, or for a move, so `create-folder`, `update-folder`, `update-model` and `move-to-folder` each returned an anonymous success — no `entityType`, no `entityName`, nothing an agent could believe without re-querying. A folder rename was invisible in the very response that confirmed it. All four now report, and because a folder and the model both resolve by id and are nameable, the post-dispatch name refresh reaches them unchanged — a stale prepared name is corrected to the live one. `update-model`'s prepare needed correcting first: it handed the mapper a live read taken *before* its own command runs, so a queued or awaiting-approval rename would have previewed the name it was about to replace — a confident wrong value in the one mode where nothing can correct it. Naming a move's subject also opens the concept report for it, so a moved element or relationship carries `effectiveElement` / `effectiveRelationship`, whose exact type refines the coarser type a move can report.
- **A bulk call that has not run no longer reports a success verdict.** A `bulk-mutate` queued into an open batch, or parked awaiting approval, executes nothing — so its skip reasons were necessarily empty and `allSucceeded` computed `true` for operations that could still decline at commit, and the enclosing batch went on to report the very decline the bulk response had called a success. The verdict is now **omitted** in those two modes, the gate every other outcome field in that response already uses.
- **A `bulk-mutate` operation names its entity's type in one vocabulary, whichever tool produced the row.** `entityType` is now the **Archi type name** everywhere — the spelling the concept operations already used — so an agent that keys dedup, filtering or branching off it stops silently missing rows, and the human approval card, which renders this same field as the row *type*, stops showing two names for one thing. Five tools change what they put on the wire: `clear-view` (was `view`), `set-view-label-expression` (was `DiagramModel`), `delete-view` (was `View`) and a `move-to-folder` of a view (was `View`) all now report `ArchimateDiagramModel`; `remove-from-view` reports `DiagramModelArchimateObject` / `DiagramModelGroup` / `DiagramModelNote` / `DiagramModelArchimateConnection` in place of four lowercase tokens, two of which (`group`, `note`) collided head-on with the names the *adjacent* rows already gave the same objects. `move-to-folder` also stops flattening what it moved: a moved relationship reports its exact type (`AssociationRelationship`, not `Relationship`), and a moved **sketch** or **canvas** view reports `SketchModel` / `CanvasModel` rather than being filed under an ArchiMate view's name — a distinction the coarse noun could not make. `delete-view`'s own `type` field changes with it, for the same reason and to the same value. One exception is deliberate and stays: a specialization reports `Specialization:<conceptType>`, because an Archi specialization's identity is the concept type it binds. **The tools' own published fields are unchanged** — `move-to-folder`'s `objectType` and `remove-from-view`'s `removedObjectType` keep their coarse nouns, which are the right word in a human sentence and which callers branch on; the translation happens in the bulk projection. `move-to-folder`'s `elementType` is now populated for every kind moved, not only elements, which is what carries the precise type. No deprecation window applies: `entityType`'s vocabulary was never published, so nothing could have been written against the old spellings on purpose.

### Same-batch composition

- **A batch can now build on what it has already queued.** Every defect in this group has one root cause: a `prepare` read the live model while commands queued earlier in the same batch had not executed yet. The fix is uniform — resolve against what the batch has queued, and where a value can only be known at commit time, resolve it there. Inside one `begin-batch` / `end-batch` window you can now **create a view and add objects to it**, **create an element and place it on a view**, **update a view object the same batch created**, **use a container the same batch created as a `parentId`** (with the mode check inside the session lock, so concurrent sessions cannot interleave), **anchor to an object the batch has queued but not yet written**, and address any of the above from `bulk-mutate` running inside the batch. An id that genuinely exists nowhere still reports as not found, inside a batch exactly as outside one.
- **Every cascade in a batch is measured against one same-batch geometry.** Two independently-queued cascades used to size a shared grandparent against the live model and emit competing absolute resizes, so the second silently discarded the first. The parent-fit cascade now reads a queue-derived bounds map, so it also cascades through groups the batch created, through queued ancestors, and through a back-referenced child move — three paths that each stopped one level short. Queue a container at `900x1200`, route the same view in the same batch, and after commit it still holds `900x1200`.
- **`apply-positions` and the ELK layout pass now measure a shared container once per call, not once per entry.** Both prepared every position against a *fresh* pending-bounds map, so two positions landing in the same group each measured that group at its pre-call size and each emitted its own **absolute** resize for it. All of them execute in one compound, so the last one won on all four dimensions and every earlier demand was discarded — silently, since the call reports success either way. Move one child right and another child down in a single call and the group grew on one axis only; which axis depended on the order the entries happened to arrive in. Both tools now thread one map through the whole call, seeded from what the open batch has already queued, so each position fits the container against what the same call has already decided about it and the last resize is the largest rather than merely the latest. Two entries that need `610` of width and `460` of height now leave the group at `610x460` in either order. The same map closes three further gaps on this path: a group an earlier queued operation grew is no longer shrunk back, the ancestor walk no longer stops at the first group the batch created but has not attached — leaving every ancestor above it unmeasured — and an object the batch anchored to something the call repositions now follows it. In the ELK pass the effect reaches one dimension further: the layout emits a container before its children, so a child re-measuring the container against its pre-pass size emitted a resize carrying the container's **stale** `x`/`y`, which executed afterwards and reverted the placement the layout had just computed for it.
- **A group that many positions grow is resized once per call, not once per entry that grew it.** The same shared map that fixed *which* rectangle a container ends at also settles *how many commands* say so. Each position that outgrew its container used to append its own absolute resize to the compound, so a call replaying a saved layout emitted one resize per entry and all but the last executed only to be overwritten — at the `apply-positions` operation cap that is **10,000 commands where 1 says the same thing**, measured. The resizes are now folded per group and committed once, after the positions, so the compound the model executes and a human approves is the size of the work actually being done. Reported counts are unchanged — `totalOperations` remains the sum of the positions and connections updated, which is what it always described — and the wall time of the call did not move either, which is stated as measured rather than assumed: the cost at that scale is in Archi's own execution of the positions, not in the redundant resizes.

- **An anchor is resolved at execute time, against post-batch bounds.** An anchor whose target was unresolvable at prepare used to be accepted and silently not applied, so one null field meant two different things. Anchor targets are re-resolved when the command runs, landing against the target's final position rather than a snapshot any other queued writer could invalidate.
- **`bulk-mutate`'s `$N.id` back-reference now addresses a group the same call created — as an update target, not only as a parent.** Two finders answered one question — *did this call already create the object this id names?* — and only one looked in the map groups are tracked in, so the identical `$N.id` resolved as a `parentViewObjectId` and failed as a `viewObjectId`. A group can now be created and re-sized without ending the call; widening that path also made `text` reachable on it, exposing a group rename that was accepted, reported as succeeded and **silently discarded**. Separately, **nesting a `bulk-mutate` inside an open `begin-batch` is a supported composition**, not a misuse. The nested call is queued into the batch like any other operation, and an id that batch has queued is addressable inside it on **every tool that places something on a view** — `add-to-view`, `add-group-to-view`, `add-note-to-view`, `add-image-to-view` and `add-view-reference-to-view`, in the view placed on, the parent nested into and the element or referenced view being placed — as well as an `update-view-object` or `update-view-connection` target, and all four of `add-connection-to-view`'s ids — relationship, view and both endpoints — whether or not that operation also carries a `$N.id` back-reference of its own, so **creating a relationship and connecting it to something the batch queued now works in a single nested call**. One arm used to refuse such an id outright while two siblings resolved it silently; the placement arms filled the very slots their single-tool entries already passed a queued value into, so the same id resolved when the tool was called directly and reported not-found through a nested bulk; and a back-reference anywhere in a connection operation routed it to a prepare that read committed containment only, so the identical endpoint resolved or did not depending on whether an unrelated `$N.id` appeared beside it. Resolving a relationship out of the queue did not cost the endpoint check: the skip that lets a relationship the same call created through — nothing knows its ends yet — is now told apart from one an enclosing batch queued, whose ends are read off the create that will connect them, so a mismatch is still rejected and the error still names the ends the server resolved rather than reporting that the relationship connects nothing. The rule is now uniform across placement, and it governs *addressability* rather than visibility, so `add-to-view`'s long-standing read of the queue for parent-fit is untouched. A queued parent still has to belong to the view the operation names: it coalesces in above the destined-view check rather than beside it, so the cross-view rejection a committed parent gets is the one a queued parent gets. Tools that update, delete or re-file a concept still report a queued id as not found — on those the single-tool call inside the same batch is equally blind, because both callers share one prepare — and a `$N.id` naming an object the same call created still wins over the batch's queue.
- **A batch can now draw a view end to end.** Four further tools resolved their ids out of committed containment only, so the script an agent actually runs — create a view, place two elements, connect them, lay the result out — failed at the first id the batch had just handed it. `add-connection-to-view` now resolves **all four** of the ids it takes (both endpoints, the relationship, and the view), since closing any subset leaves the tool unusable in a batch for the next reason along; `apply-view-layout` resolves **all three** of its (the view it checks before either loop runs, each positioned view object, each connection); `add-view-reference-to-view` resolves the *referenced* view as well as the host, both inside a batch and — by a separate route, since a bulk call has no queue — from a `bulk-mutate` back-reference; and `update-view-connection` resolves a connection the same batch added, whose id `add-connection-to-view` hands back at prepare time although the connection joins its endpoints only at commit. Every existing message survives: a genuinely absent id still reports which entry failed and why, a queued endpoint still narrows to an ArchiMate view object so a queued group or note named as an end fails as it always did, and a missing *host* view stays distinguishable from a missing *referenced* one. A queued relationship is connected to nothing until commit, so the element-match validation reads its ends off the create that will connect them.
- **A queued endpoint is scoped to the view it lands on.** The queue fallback matched an id against every object the batch had queued on *any* view, while the live lookup it stands in for searches one view's containment — so a batch could queue an object for view B, name it as an endpoint of a connection being drawn on view A, and be given it, committing a connection whose two ends sit on different diagrams. The live path has never been able to express that and Archi has no way to draw it. Because a queued object carries its destination in the queue rather than in its container, the check climbs that destination, preferring a queued parent and falling back to a live one — which is what lets an object queued *inside a queued group* still resolve for the view that group is going to.
- **A second update no longer discards the first's bendpoints.** Two updates on the same connection in one batch or one `bulk-mutate` call — the first supplying bendpoints, the second only a label or styling change — committed with the first call's bendpoints **gone**, though nothing had asked for them to be cleared. It is the one defect in this area that loses work rather than refusing it. The bendpoint write was the only one of the command's four fields that was unconditional: the styling-only update snapshotted the bendpoints it could see at prepare time, before the first command had run, and wrote that snapshot back at execute over what the first command had just written. Bendpoints are now gated like the other three fields, on a signal the prepare has always computed and had nowhere to put — `null` for *the caller supplied none*, an empty list for *clear*, two states that had become indistinguishable by the time the command was built. Fixed at the command rather than per path, because all three deferred routes share it and a projection would have reached only the batch one.
- **A partial re-edit no longer reverts the fields it did not mention.** Editing the same object twice in one batch — once for style, once for position — used to revert the untouched geometry to its prepare-time snapshot. Each edit now applies only what it names.

### Integrity guards on deferred paths

- **Guards that only ran at prepare time now re-check at execute time, and decline instead of corrupting.** A precondition checked when a command is *built* is worthless on a deferred path, because a sibling operation queued in the same batch can invalidate it before the command *runs*. Three guard families moved into `execute()`, which makes them path-agnostic across the batch, bulk-immediate and bulk-approval paths, each declining with a skip reason that surfaces in the batch summary and in `skippedOperations`. **`move-to-folder`**: the circular-reference guard — a two-move pair could form a containment cycle and leave three folders unreachable from the model root, silently and with nothing thrown — plus the view-hierarchy and folder-layer guards its description had promised universally. **`delete-specialization`**: the in-use guard is re-read at execute, an unauthorised profile is declined rather than wiped, and `force=true` is honoured when the specialization is attached later in the same batch. **`delete-folder`**: a queued delete no longer destroys contents that arrived after it was prepared, and a declined *nested* folder is no longer defeated by its own ancestor's flat cascade.
- **A create or placement whose container left the model mid-request is declined, not orphaned.** `create-view`, `create-folder` and `clone-view` resolve a target folder at prepare and create into it later, so a folder deleted by an earlier operation in the same request left the new object unreachable from the model root — really created, gone on reload, reported as success. `add-to-view` is guarded the same way against a container an earlier operation removed, as is a view-nesting `parentId` belonging to a *different* view. The connections a placement draws for itself are covered too: `add-to-view` with `autoConnect` and `auto-connect-view` both scan the view at prepare, so a preceding `remove-from-view` could leave a connection joined to a detached endpoint.
- **A queued or awaiting-approval response now keeps the measurement and rescopes the remedy, instead of asserting a write that has not happened — or saying nothing at all.** Approval mode discarded a tool's `nextSteps` outright: `formatMutationResponse` short-circuited to a proposal response that took no `nextSteps` argument, so the remedy sentence a caller needs vanished for every mutating tool and every structured warning code. Batch mode had the mirror defect in two shapes — `layout-within-group` returned before all five of its conditional steps, so a queued call learned nothing about an overflow, a recursive arrangement or an ancestor left too small for what the call grew inside it; and `auto-route-connections` did the opposite and worse, reusing four applied-arm sentences verbatim on its batch branch, so one response carried both "The new paths were applied anyway. Undo to restore the previous paths" and "Mutation queued as operation #1 in current batch". Nothing had been applied, and an agent obeying the first reverts whichever command is really on top of the stack. Six tools now compose each disclosure once and vary only the recovery clause: `undo` once applied, `end-batch` (or `end-batch rollback:true`) while queued, and **no tool at all** while awaiting approval, where the agent can neither approve nor reject its own change. The evidence is never withdrawn with the remedy — a queued re-route still counted its crossings, and they are still reported with the connection, note and container ids beside them. The approval arm's three fixed lines are unchanged and still come first; disclosures are appended on a separate parameter and the immediate arm's present-tense list is **never** forwarded there. The rule is written down in `docs/mutation-model.md` and guarded, so the seventh tool is born with it. The three spacing tools are deliberately untouched: measured on the shipped source, none of them consults the approval gate at all, so an approval-tense sentence for them would be unreachable — pinned, with a positive control, so that adding a gate to one fails the build and says what it owes.
- **Eight more tools now disclose on their deferred arms, and two of them are told to withhold a number rather than re-tense it.** The six tools of the entry above left eight conditional builders still returning early on a queued call and still having their list discarded on the approval arm, so `add-to-view`'s auto-connect cap, `remove-from-view`'s cascade count, `optimize-group-order`'s crossing reduction, `update-view-connection`'s four outcome branches, `adjust-view-spacing`'s coincident-segment remedy and both specialization tools' guidance reached only a caller whose write had already landed. They now compose each disclosure once and vary the tense and the recovery, on the same seam. **Two tools are deliberately quieter, and the axis is the command rather than the field.** `clear-view` re-walks the view inside `execute()` and empties whatever it then finds, so its three prepare-time counts describe a different model than the one it will clear — inside an open batch, everything queued between the two walks is invisible to the first and removed by the second. Its deferred arms therefore **omit** the counts and say why, rather than restating them in the future tense, which would be a fabricated measurement rather than a rescoped remedy; what they keep is the clause that survives every arm, that the underlying model objects are untouched, plus the warning that a placement queued behind the clear is removed by it. `add-to-view` splits its two deferred arms over one field: a queued call enqueues the prepared command verbatim, so the reported view-object id is the one that lands, while a stored proposal keeps a rebuild handle and constructs a **different** object with a **new** id when the human approves — so the approval wording names no id and says where to read the real one. Two conditional branches are proven unreachable on a deferred arm rather than given wording there: `optimize-group-order`'s already-optimal step and `create-specialization`'s already-existed step are each selected by a value produced only on a path that returns above both the approval gate and the queue, pinned against the real accessor with positive controls. The published rule in `docs/mutation-model.md` gains the clause that decides all of this — a deferred arm may state as measured only what the command it queued will actually do — and the guard now requires it. `adjust-view-spacing` joins the spacing census as a fourth member with one deferred arm, not two: it consults no approval gate at all. Finally, `SpecializationHandler` was the only handler in the tree whose batched arms did not name `get-batch-status`; all three now do.
- **`bulk-mutate` no longer reports a skipped destructive operation as done.** A skipped delete came back as `action: "deleted"` with `allSucceeded: true`; the result now carries `skippedOperations` and flips `allSucceeded`, and the field reaches the JSON rather than stopping at the typed record.
- **`auto-route-connections` no longer calls a re-route "worse" when all it measured was the crossing count.** On the applied arm, a full re-route that raised edge crossings said *"this re-route is worse than the geometry it replaced"* in `structuredWarnings` and *"the view was better before the call"* in `nextSteps`. The signal behind both sentences holds **two integers** — the crossing count before and the crossing count after — and nothing else: not `interiorTerminations`, not cross-element pass-throughs, not the composite rating, not the view. Its method signature is the proof. Edge crossings are also the **last** of the thirteen metrics that composite weights, below the pass-throughs, interior terminations and coincident segments a full re-route most often clears — so the warning fires on the bottom-ranked metric while blind to the ones that actually move the rating. Measured on a live model, that is not a theoretical gap: one re-route took edge crossings from 14 to 20 while taking interior terminations from 4 to 0 and cross-element pass-throughs from 1 to 0, and the view's own overall rating from `poor` to `fair`. **Obeying the warning would have restored `poor`.** Both published sentences now state what was measured and what the recovery costs — *"Routing increased edge crossings from 6 to 17. The new paths were still applied. Crossings alone do not determine layout quality — a routed view can score worse here and still read better overall; review the view before deciding, and if you do want the previous geometry back, undo reverts the whole routing pass, not just the crossings."* — and the `nextSteps` half carries the same two clauses, so one response no longer answers the same question two ways. The code's own documentation made the broadest version of the claim, that this is *"the only signal that answers 'did this call make the view worse than it was?'"*, and now states the metric-scoped question it can answer. This **supersedes the wording of the entry that introduced the warning**, further down these notes, which described it as reporting "a full re-route that makes a view worse": it reports a full re-route that raises the view's crossing count, which is a narrower thing. What the signal detects, when it fires, and its `inputWasRouted` gate are all unchanged. **`remediationTool` is deliberately unchanged and still reads `undo` on the applied arm** — the tool does recover that call, and what was wrong was the message asserting the recovery was *warranted*, not the field naming it. A caller reading only the structured field still gets `undo` with no qualification; what changed is that the message beside it no longer claims the view is worse. The queued and awaiting-approval arms are untouched byte for byte and keep the future-tense form of the same claim, which is a known residue and a deliberate one: freezing them is what proves this change reached only the arm it was aimed at.

### Deletion, undo & the approval gate

- **`delete-view` reports the cascade it performs.** `viewConnectionsRemoved` and `viewReferencesRemoved` were constructed as literal zeros. Both are now measured — connections by a recursive, de-duplicated walk (a connection nested inside a group was invisible), external placeholders by the same single scan the cascade itself uses, so the count cannot drift from the behaviour. The other four fields are unchanged and correct as they stand, and the description's false "no cascade counts are reported" sentence is gone.
- **`delete-view` disconnects the placeholders it cascades out of surviving views.** Cascade-removing a placeholder from another view never called `disconnect()`, and because those views survive, a connection attached to it could be left dangling — a diagram connection is EMF-contained by its source, so one whose source left while its target survived left an unresolved reference behind on save/reload. Cascaded placeholders are now disconnected, and reconnected on undo.
- **`delete-folder`'s force cascade counts a contained view's own blast radius.** The view arm folds a directly-contained view's external placeholders and connections into the force totals, mirroring the element and relationship arms. A suspected order-dependent over-report was falsified: every external placeholder points at exactly one deleted view and always ceases to exist, so the prepare-time sum is order-invariant.
- **`delete-folder` cascades sketch and canvas views instead of removing them uncounted.** `ISketchModel` and `ICanvasModel` are siblings of `IArchimateDiagramModel`, not subtypes, so the cascade arm's type test skipped them: the view was removed with its folder but never went through the view cascade, leaving its placeholders behind. The arm is widened to the `IDiagramModel` supertype, and the description's stale "sketch and canvas views are not counted" caveat is removed.
- **Undo restores a deleted sibling to its original position.** Every prepare captured a sibling *index* for undo, which any co-queued operation that inserted or removed a sibling in the same folder invalidated, so a multi-delete batch undid to the wrong order. Four commands now share a successor-anchor helper that restores relative to a surviving neighbour.
- **Undo of a redundant or overlapping batch no longer throws.** Two delete commands targeting the same object each captured their re-insertion anchor at construction, so reverse-order undo re-added the target twice into an EMF unique containment list and threw. Fixed at the command layer for views, relationships, elements and specializations.
- **The approval card now shows the blast radius, the real reason, and which kind of gate it is.** `delete-view` and `delete-folder` proposed a change carrying only the target id and a null effect description, so the person deciding saw none of the cascade counts the agent was given; both now build the same `(cascade: N view connections, 1 view reference)` string the relationship path already produced. A structured domain refusal raised while rebuilding a proposal is surfaced verbatim instead of being replaced by the generic "a targeted object was changed or removed" — so a folder that has gained contents reports `FOLDER_NOT_EMPTY` with its own `force: true` remedy — and **Approve All** reports that same reason when it halts, instead of a sentence it invented. Fourteen proposals (the layout, routing and bulk passes) store the compound that was already reviewed rather than re-preparing at approve time; that freeze is deliberate, and all fourteen cards now say so, so the human knows whether Approve means *do this* or *work out what to do now*.
- **A proposal whose target was queued when it was made is now vetted for staleness.** Such a proposal was approved with **no staleness comparison at all**: the propose-time snapshot resolved targets through committed containment, a queued target resolved to nothing, and a snapshot that fingerprinted nothing is treated as fresh. So if the batch then committed — making the object real and editable — and the human edited it while the card was still on screen, approving overwrote that edit silently. The window is not hypothetical: it opens at commit and lasts as long as the human takes to read the card, with the object on the canvas throughout. Targets are now resolved against containment and, failing that, against the session's own open batch, on **both** sides of the window — splitting them is how one side comes to see a removal the other never saw, since a proposal can be approved while the batch is still open. The queued object is fingerprinted rather than recorded as a placeholder, which keeps the removed-object message honest.
- **An approval whose cascade outgrew the card is refused.** The card is built from the propose-time DTO while the command that runs is rebuilt against the current model at approve, and the existing staleness guard fingerprints a target's own attributes — which a folder gaining contents does not change. So a folder proposed for force-delete while holding two elements vetted as fresh after three more were dragged in, and five were deleted against a card that said two. `approveProposal` now compares the reviewed cascade counts against what the rebuilt command would remove, and refuses when they disagree, naming both numbers.

- **A gated card now discloses every parameter the approval will write.** An approval card is built from a proposal's `proposedChanges` map, and that map is the only description of the pending write anyone gets: it travels verbatim onto the wire, where any agent reads it back through `list-pending-approvals`, and verbatim into the card's `Technical details` disclosure. Eleven tools accepted parameters they never put into it — 22 in all, plus the two frozen-family parameters that change *what* gets applied rather than how it was computed (`force` on both `auto-route-connections` sites, `wrapFit` on `resize-elements-to-fit`) — so a human approving a gated write was approving a change the card had not described. All eleven are closed. `recede` is the one deliberate asymmetry: it is disclosed by the container-visuals path alone, because it is read by one command wrapped at two prepare sites, and disclosing it anywhere else would announce a styling change the write never makes. Under-disclosing hides a write; over-disclosing invents one. The durable half is the contract, not the eleven fixes: this family had been closed once before, tool by tool, with nothing holding it, and the next omission surfaced thirty days later by accident. A contract test now parses every proposal site and requires each to be **complete** or to carry a registry line naming the exact parameters it exempts — a site registered for one reason does not blanket-exempt the rest of its card — and it asserts it found all **42** sites before asserting anything about their contents, because a parser that matches nothing reads exactly like a clean scan. It parses source only, so unlike its effective-state sibling it runs in the headless lane and guards every commit.
- **A card names the aspects the approval will actually change, not one of them.** Three prose fields named a single aspect while the method behind them wrote far more: `update-view-object` announced every call as *"Update view object bounds for …"* and validated it as *"View object bounds ready for update"*, while the same method writes text, a label expression, styling, image parameters and four anchor fields; `update-view-connection` announced and validated **bendpoints** while its method also writes styling, label visibility and label position. The card's visible row reads that sentence and not the map, so a caller renaming a box was announced to the approving human as *moving* it, and a restyle was validated as a reroute. All three are now derived from the same `proposedChanges` map the card carries, so a field that reaches the map is named and one the map omits cannot be — keyed on the **map's keys** rather than the parameter names, since a collaborator keyed on parameter names would compile, pass its own unit tests and silently never fire. `bendpointCount` and `absoluteBendpointCount` fold to one "bendpoints" aspect (a polyline is one decision, exactly as the four anchor keys fold to "anchoring"), bounds-only and bendpoint-only calls keep their previous wording byte for byte, and a call that discloses nothing degrades to neutral rather than claiming a change.

### ArchiMate Grouping as a container

- **The group-layout family positions an ArchiMate `Grouping`, not only a native view group.** Archi renders two different objects as a container: a *native view group* (`add-group-to-view`) and an ArchiMate **`Grouping`** element (`add-to-view`) — and the shipped technology and deployment recipes tell an agent to build the second. Seven layout tools each open-coded "collect this view's top-level groups" against the native type alone, so a `Grouping` was never collected. Two of the three failure modes were worse than a skip: `arrange-groups` on a mixed view positioned the native groups, silently skipped every `Grouping` and reported success — `groupsPositioned: 4` while fifteen containers stayed stacked at the origin — while `auto-layout-and-route` (grouped mode), `adjust-view-spacing` and `optimize-group-order` **rejected such a view outright**, each stating it had no groups, a confident falsehood about a canvas full of populated containers that a client which cannot see it has no way to contradict. Ten collection sites now share one predicate. Three passes had also hard-coded the native group's 24 px label band as their child start offset; an element container reserves **46 px**, so widening the collection alone would have laid a `Grouping`'s first row of children under its own title.
- **`arrange-groups` reports where each container landed, not just how many moved.** A count alone is what let a run that skipped fifteen containers read as a success. **`positionedContainers`** now gives each container's id and the rectangle it actually holds, read back from the model after the arrangement is applied. Its `groupIds` hint also stops directing callers to the `get-view-contents` `groups` bucket, which structurally cannot contain a `Grouping` id, and a nested `Grouping` is now denied as *not top-level* rather than *not found*.
- **`arrange-groups` accounts for every direct child of the view, and the accounting is a build-enforced invariant.** The tool carried three counters — `groupsPositioned`, `standaloneElementsPlaced`, `skippedContainers` — with **nothing to sum against**, so none of them could contradict another and a shortfall was undetectable from the response by construction: `groupsPositioned: 8` was unfalsifiable on a view holding nine containers. Naming the skipped *containers* closed only half of it; a top-level element that is **childless** and reaches fewer than two arranged containers belonged to no bucket at all, and a real conversion run reported a clean container diff while **seven loose elements sat stacked at the origin**, overlapping the container they were drawn beside, with nothing in the response naming one of them. The response now declares **`topLevelObjects`** — the view's direct-child count, always serialized — and **`unhandled`**, which names everything the other three buckets did not claim, notes, images and view references included: excluding a class of object from the denominator before counting is exactly the move that produced the gap one level up. Each entry carries `viewObjectId`, `name`, `elementType` and a short `reason` leading with a stable code (`not-requested`, `not-an-archimate-element`, `lane-not-run`, `insufficient-connections`, `type-not-lane-eligible`) so the list is filterable without parsing prose. `unhandled` is computed as a **residual** over `view.getChildren()` rather than as a fifth predicate, so it cannot drift from the population it completes — and because that makes the arithmetic true by construction, the invariant test asserts over **ids**: the four buckets must be pairwise disjoint and their union must equal the view's children. That assertion immediately caught a latent double-report — a populated `Node` wired to two arranged containers satisfies both the skipped-container predicate and the standalone lane, so it would have been counted twice *and* described as "left where it is" after the lane moved it; the lane now wins, and the skipped list excludes anything this call placed. The whole report is read from the view rather than from the write, so unlike the effective geometry it is populated and correct on a queued or proposed call. Which containers are arranged is unchanged — pinned by a geometry comparison across grid, row, column, topology, topology-with-columns and `groupIds`-restricted calls.
- **`arrange-groups` arranges a container you name in `groupIds`, whatever its element type.** The tool arranges a native view group and an ArchiMate `Grouping`, and deliberately declines a plain element acting as a container — a `Node` typing a cloud region is a host, not a zone, and arranging every such element by default was measured across the corpus at 2103 containers on 254 views, sweeping capability decomposition trees in as if they were deployment zones. But that narrowness is a **default**, and the caller passing an id has already overridden it with information the tool does not have: it can see the canvas, and `skippedContainers` has just told it which object was left standing. Naming a container's `viewObjectId` in `groupIds` now arranges it alongside the zones, counts it in `groupsPositioned`, returns its rectangle in `positionedContainers` and removes it from `skippedContainers` — so the report that says what was left standing has become the argument of the next call rather than an affordance nothing points at. Any **direct child of the view that can hold children** is admissible; a note, an image and a view reference are not, and are refused with `apply-positions` named as the remedy. **Omitting `groupIds` leaves every view arranged exactly as before**, pinned by the existing geometry comparison across six call shapes, so reflow risk is nil by construction. Two effects follow on the opt-in call only, both correct: the named container's descendants enter the topology weight matrix, so the zones may be ordered differently, and the density-aware `spacing` default may resolve to a different value. One latent defect had to be closed with it — the standalone lane excluded arrangement targets by asking the shared *default* predicate, which a per-call opt-in does not change, so a named `Node` host wired to two arranged zones received an update command from the arrangement **and a second from the lane** in the same compound; the lane's ran later, so it silently won and the arrangement the caller asked for was discarded, with the object counted in two buckets at once. Reproduced before fixing at bucket-sum 4 against a denominator of 3.
- **`arrange-groups` tells a wrong `groupIds` entry apart from the others instead of denying all of them.** A correct, current view-object id for a populated top-level container the caller could see came back as *"Group not found in view"* with `VIEW_OBJECT_NOT_FOUND` and a hint sending the caller to re-read a listing that would show the object — a denial of something on the canvas, and a wasted next call. The refusals are now specific and each names a remedy the agent can execute: an id that matches nothing in the model is the only `VIEW_OBJECT_NOT_FOUND` and says *unknown id*; a **model concept id** passed where the view-object id belongs says so; an object **drawn on another view** names the view it belongs to; a container **nested inside a container this tool arranges** keeps today's *not top-level* message and now points at `layout-within-group` (a container drawn inside a HOST is a later and separate ruling — see the outermost-container entry below, which makes that shape admissible); a top-level **note, image or view reference** is refused as *not a container*, with `apply-positions` / `update-view-object` named; and the view's own id and a **connection** id are each named for what they are rather than swept into the concept case. Collapsing these would not merely be vague, it would be false — a model concept belongs to no view, so telling it that it "belongs to another view" is a lie. The empty-target refusal stops advising *"add a container to the view first"* on a view that already holds one the caller can now name.

- **A connection that terminates on an arranged container now counts toward the standalone lane's threshold.** The lane places a top-level `Node`, `Device`, `Path` or `CommunicationNetwork` that reaches at least two of the arranged containers, and it resolved every connection endpoint through the element-to-container map alone. That map holds a container's **children** and never the container's own id, so a connection drawn to the container *box* resolved to nothing. Measured on a live technology view: a `CommunicationNetwork` associated with an on-prem zone **and** with a cloud-region `Node` the caller had named in `groupIds` came back under `unhandled` reading *"insufficient-connections: connected to fewer than two arranged containers"* — a confident, wrong diagnostic, whose only corrective is to add a second association the model does not want. The predicate was the defect, and the shape it could not see is the shape the technology-deployment recipe prescribes on the same page: build each infrastructure node as a container box, then associate the **nodes** to the network rather than linking them to each other. **A connection now reaches a container both when it terminates on an element inside it and when it terminates on the container's own box** — a native group, an ArchiMate `Grouping`, or a host admitted for one call through `groupIds` alike — and two connections to the same container still count once. Endpoints that do not count are unchanged and now enumerated with them: an element inside a container this call is not arranging, a loose top-level peer, and the candidate itself on a connection that loops back. A container nested inside an arranged one counts for its outermost arranged ancestor, and a note drawn inside a zone counts as being inside the zone. **Elements previously reported `insufficient-connections` may now be lane-placed**, so a view holding this shape will arrange differently. `auto-layout-and-route` with `mode: "grouped"` decides the endpoint question with the same predicate and therefore inherits the change — and it carries **no `unhandled` bucket**, so it will begin moving elements it used to leave in place with no field in which to say so; its placement is the only observable it has. The two tools are **not** interchangeable on this shape, and the difference is the arranged set rather than the predicate: grouped mode takes no `groupIds`, so it arranges only the default containers, and a candidate that reaches its second container only through a named host is placed by `arrange-groups` and left standing by grouped mode. Views where no candidate has a connection terminating on an arranged container are byte-identical.
- **`arrange-groups` stops telling a caller to add connections when no connection would help.** With a single container arranged there is no gap between containers for the lane to reserve, so nothing can be placed there however many connections an element has — yet such an element was returned as a connection near-miss, sending the caller to add one that changes nothing. That outcome now has its own code, `no-inter-container-gap`, decided **before** the connection count for exactly that reason. The six codes are single-sourced on the DTO that carries the field and the guard over the served tool description iterates that enumeration, so a seventh code documented on no surface fails the build — the previous guard was a hard-coded list of the five codes that existed when it was written, and would have stayed green while the sixth shipped undocumented.

- **`get-view-contents` counts both container kinds in every format.** The discovery step those layout tools' own descriptions name as the first call of a grouped-view workflow counted only native groups, because a native group arrives in the `groups()` bucket while a `Grouping` arrives among the elements. Measured on a live model: `format: "tree"` reported `topLevelGroups: 4` where `arrange-groups` then positioned 6 — and on a view whose top level holds only `Grouping` containers the stats scored **0** while the guidance said *"Use `layout-flat-view` for flat views (no groups)"*, in the same payload whose `tree` array listed all three populated containers. All three group stats now count both kinds; every container node carries **`isGroup: true`** at any depth in `tree` and in `graph`; and `format: "summary"` counts both under its `Containers: N groups` clause. Three repairs ride with it: a group nested inside an *element* container is now attached to the tree (it was counted but unreachable by walking), a marked container always emits `childCount`/`children` so both kinds share one node shape, and `ungroupedElements` excludes containers — a container is what loose elements are placed *into*, not one of them. The `nextSteps` gate keys off `topLevelGroups` rather than the widened total, so *"containers exist but none at top level"* is now reachable and says so, rather than recommending the top-level family as if it had default targets there — and, since a top-level element acting as a container can be arranged by naming it, that branch and the flat-view branch beside it both point at `groupIds` instead of writing the tools off. `groups()` is deliberately unchanged, so `exclude: ['groups']` still behaves as before, and a populated `ApplicationComponent` stays uncounted — a host is not a zone.
- **`assess-layout` sees a `Grouping` as the container it renders as.** On the one-zone-per-`Grouping` shape the technology and deployment guidance prescribes, the assessor answered `hasGroups: false` for a canvas full of populated zones, counted the transparent zone rectangle as a connection pass-through and as a label overlap, and reported a **certified zero** from `labelOnGroup` whose detector had skipped every zone it declared itself to have examined — so one label over one zone was simultaneously a false positive in `labelOverlaps` and a false negative in `labelOnGroup`, violating in both directions the division of labour those two dimensions describe. Detectors that reason about what the canvas *shows* now read a container flag sourced from the same predicate the arrangement family uses — `hasGroups`, alignment participation, corridor walls, hub detection, pass-throughs, image-vs-connection, label overlaps, label-position exhaustion, `labelOnGroup`, own-endpoint overlap fractions, note containment, the coincident diagnostic, the stacked-position pre-route warning and virtual container bounds. Detectors that reason about *measurement* or *vocabulary* deliberately keep the narrower native-group flag — a `Grouping` carries a measured label width where a native group does not, and `get-view-contents` reports the two in different buckets, so widening that flag would have regressed both. Native-group behaviour is unchanged, pinned by building every fixture twice with byte-identical geometry and requiring the two responses to agree.
- **Connections stop detouring around a `Grouping`.** Three sites built the router's input from the native-group flag alone — two excluded a group from the obstacle list outright, one routed it into the soft `groupBoundaries` clearance list — so a `Grouping` matched none of them and fell through into **obstacles**, a solid impassable rectangle. A connection between two zones therefore detoured around every third zone lying between them, where the identical native-group view routed straight through. Measured on a three-zone corridor whose middle zone is clear at the connection's height: the native route holds its own height (vertical deviation 0), the `Grouping` route deviated **203 px over four bendpoints**. Both `auto-route-connections` and `auto-layout-and-route` reach this. The endpoints' own ancestor zone was already excluded by id, so the defect bit third-party zones only — which is the shape the guidance produces at scale. Each site keeps its existing native-group treatment and merely admits the second kind, and the label-position optimiser's obstacle list moves with them, so no two passes are left disagreeing about one rectangle.
- **Two overlapping `Grouping` zones no longer suppress the nudge pass.** `auto-route-connections` skips its nudge pass when a sibling overlap is detected, because degenerate element geometry can crash the re-routing pipeline. That scan excluded native groups but not `Grouping`s, so two zones whose rectangles overlap withheld a pass the view qualified for, purely on the basis of which container kind the author happened to use — and zones commonly abut or overlap slightly while the elements inside them do nothing degenerate. Both detectors move together, so the pair named in the published `AUTO_NUDGE_SKIPPED_SIBLING_OVERLAP` warning is always the pair that triggered it.

- **What counts as a container is now published as one table, and the two claims that over-reached are corrected.** The layout tools do not all answer "is this a container?" the same way, and until now nothing said so: the routing-preconditions checklist told agents that **every tool named in it** treats the two container kinds alike, and `docs/layout-engine.md` said **the whole layout family** does — while the same document's own `layout-within-group` section, four sections above, described the opposite ruling and called the asymmetry deliberate. A census measured every container-ness predicate in the codebase from source: **seven answers**, of which the canonical `TopLevelGroupTargets.isTarget` and five deliberate variations are correct by design — a narrower one for the upward ancestor re-fit (which *discloses* per call via `ancestorPropagation` rather than widening), a wider one for the downward `layout-within-group` recursion, a per-call `groupIds` override, a type-name copy above the model layer where EMF may not be imported, and the DTO shaping that deliberately files a `Grouping` among the elements. All seven are now published in `docs/layout-engine.md` under **What counts as a container**, keyed by the symbol that owns each one, with why each differs — and the parity statements in the checklist, the recipe library, the accessor javadoc and the `arrange-groups` section are each scoped to the **arrangement family**, which genuinely does treat them alike. The true and load-bearing half is kept intact: a view built from `Grouping` zones is still a fully supported grouped view. A build-fired guard now holds the table and the definition sites together in both directions — every predicate present, and no deliberately-excluded styling or parent-eligibility site admitted — anchored to the table's own region rather than the file, because the document names some of those symbols hundreds of lines away for unrelated reasons.
- **`resize-elements-to-fit` sizes elements to their labels and treats a `Grouping` as a zone.** The target walk collects every element view-object, and an ArchiMate `Grouping` is one — so the tool that this server's own recipes tell an agent to reach for, on views this server's own recipes tell an agent to build out of `Grouping` zones, sized those zones as though they were labelled boxes. With children a zone landed in the parent pass, whose width was re-fitted to `max(label, children) + padding` with no floor at the current width: measured, **400×300 → 160×300**, the height saved only by an explicit never-shrink guard. With **no** children it was not a parent at all, fell to the leaf pass and was sized to its own name on **both** axes — measured **400×300 → 120×55**, which is the element default and the label-independent floor. Excluding a `Grouping` from the walk would have been the obvious fix and the wrong one: the checklist, the assessor's `boundaryViolationCount` remedy and three of the accessor's own `nextSteps` all name this tool as the way to close a child that has grown outside its parent, and that remedy works precisely because a `Grouping` is collected. **Growth is kept and shrinkage removed.** A `Grouping` is now grow-only on both axes, its width following its children rather than its label, and a childless one is not sized at all — which is exactly the treatment a native view group in the same position gets. What the response says about it follows the caller's own question: a zone named in `elementIds` is disclosed in **`skippedContainers`** with an actionable reason, and a zone the walk merely found is left unmentioned, because a count cannot say why one object was skipped and an entry per untouched zone would bury the elements the caller did ask about. Non-`Grouping` elements are untouched by the change — a childless component is still sized to its label, a populated one still fitted to its children, each pinned separately.
- **A published claim that a native view group is “never touched” by that tool is retracted — it was false.** Three surfaces said it. Every target the tool resizes goes through the parent-fit cascade, and that cascade acts on native view groups **only**, growing one around a child the pass just widened: measured, a native group at **400×300 came back 450×325**, already reported in `resizedGroups`. The accurate statement, now on every surface that carried the old one, is that a native view group is never **collected as a target** — the walk descends through it to reach the elements inside — and is still grown by the cascade on overflow. The build-fired surface guard pins the retraction on each of the four documents rather than on one.
- **One container-ness question is recorded as open rather than glossed.** `topLevelGroupOf` and the `arrange-groups` counting route share the canonical predicate and still disagree about *which* container is top-level for an object nested inside a non-container host, so one view can report two values for one field name on that shape. It predates the `Grouping` widening, and is published as an open question: whichever definition wins has to win in both routes, which is a decision about what a zone is rather than a defect in one walk. **Superseded — the question is settled; see the entry below.**

- **Top-level now means the outermost container wherever it sits, and `arrange-groups` arranges containers it never used to touch. This is a visible behaviour change.** The open question recorded above is closed, and it turned out to be sharper than it was filed: the divergence was not *between* two tools but *inside* each spacing tool, four lines apart. `apply-group-spacing-recommendations` and `apply-spacing-recommendations` read the view's own children to decide whether two containers exist and walked the whole containment chain to count the connections between them — so on a view whose zones are `Grouping` elements drawn inside a `Node` typing a cloud region, one response carried `interGroupConnectionCount: 1` and `isConnected: true` beside `noChangeReason: "view has fewer than 2 top-level groups"`, and a `currentInterGroupSpacing` that had never been measured. Two mutually exclusive facts in one envelope, which a client that cannot see the canvas has no way to contradict. `arrange-groups` was worse than wrong on the same shape: it **refused** the view with *"No top-level groups found"*, and the remedy it published — name a top-level container in `groupIds` — could not be executed for the object that needed it, because naming the nested zone was itself refused. **The outermost qualifying container wins, and it wins in every route.** `TopLevelGroupTargets.collectOutermost` is that definition asked downward and `topLevelGroupOf` the same walk asked upward; one private traversal now serves both, and the separate flattening route `arrange-groups` summed its own inter-container count through is deleted rather than migrated — its answer was reproduced, number for number, on four shapes before it was removed. **Seeing widened across the family; positioning did not.** A nested zone's coordinates are stored relative to its host, so it cannot join a canvas grid: `arrange-groups` arranges each host's zones **in that host's own coordinate space** and reports them in a new **`nestedContainersArranged`**, each entry carrying the landed rectangle read back after the write plus the `hostViewObjectId` those coordinates are measured from. That field sits **outside** the four-bucket identity — `groupsPositioned + standaloneElementsPlaced + skippedContainers + unhandled` still equals the view's direct-child count exactly, because a nested container is not one of those and folding it in would make a published equality arithmetically false on precisely the views the field exists for. A host too small for the arrangement is declined whole rather than half-filled: the parent-fit cascade grows native view groups and a host that is an ArchiMate element is not one, so there is no honest way to make room. The host itself is still listed in `skippedContainers` — it did not move — with a reason saying the containers inside it were arranged and where to read them, because widening a target set without widening the disclosure is the silent-shortfall failure mode this family was written to close. `groupIds` accepts such a container and restricts the arrangement inside its host to the ids named; a container that is a **member** of another arrangement target keeps its refusal verbatim, since it moves with the target holding it. `optimize-group-order`, `adjust-view-spacing` and `auto-layout-and-route mode: "grouped"` widened their **refusal wording** only. Each still gates and positions on the view's own containers — a nested zone is neither counted into the set they act on nor moved by them — but none of them may any longer describe a canvas full of populated zones as having no groups: all three now share one refusal that reports how many containers the view holds, says they are drawn inside a host, and points at `arrange-groups`. Widening their counting, gating and positioning is separate work. `get-view-contents` keeps `topLevelGroups`/`nestedGroups` meaning where a container is **drawn**: that split is a genuine distinction for a discovery surface, so the published equality between `topLevelGroups` and `groupsPositioned` is now qualified to say exactly when it holds rather than being redefined under every recipe that reads it. **A view holding no container inside a host is arranged byte-identically**, pinned as an element-for-element equality between the two collectors across twenty-one fixtures — the widening only ever reaches deeper than the view's own children when a non-target container stands in the way.
- **The three spacing tools now decline a corridor they cannot widen, instead of recommending a delta they can never apply. This is a visible behaviour change on three served tools.** The entry above widened those tools' *seeing* and deliberately left their *positioning* with `arrange-groups` — which opened a seam: `apply-group-spacing-recommendations` and `apply-spacing-recommendations` gated on the outermost containers while the step they apply, `adjust-view-spacing`, still acted on the view's own children. On a view whose zones are `Grouping` elements drawn inside a `Node` typing a cloud region the gate was satisfied and the positioning step's own guard was not, so the tool began work it structurally could not finish: it published `interGroupDelta: 50` — a real number, measured between two zones inside the host, for a corridor it positions nothing in — and on the applied path attributed the resulting no-op to canvas density, offering a consent-gated structural reflow for a problem the view does not have. `apply-element-spacing-recommendations` had no such mismatch and told the same view a different falsehood: *view has no groups; spacing recommendation not applicable on flat views*, about a canvas holding two populated zones. All three now short-circuit above the density certificate with a zero delta and one shared sentence that counts the view's containers, says where they are drawn, and names `arrange-groups` — which was measured actually arranging them, in the host's own space, rather than merely cited. The reason maps to `structural_no_change_containers_not_positioned_by_this_tool`, a new entry inside the published `structural_no_change_<reason>` branch; **the taxonomy still has ten branches**. It outranks both the dry-run label, because a preview promising what the applied path cannot deliver is the same defect one step earlier, and the already-met reason, because that sentence implies a corridor was measured which this tool could have widened. A view holding a single hosted zone keeps the more actionable *fewer than 2 top-level groups*, and a view whose only container is an empty box on the canvas keeps its existing wording — nothing on it is drawn inside a host. **The same seam had a second, quieter half.** Where a view holds populated containers on the canvas *and* more inside a host, the gate measured whichever frame held the most, so a view with two canvas zones 60px apart and three hosted zones 30px apart published 30 as its corridor while the step would have widened the one that is 60. Both numbers are real and they describe different corridors. The gates now measure the frame their own step acts in whenever that step has a corridor there, and decline when it has not — they never narrow to a frame too small to measure in, which would put a placeholder in a field that reads as a measured pixel count.
- **A published sentence about which connections the density-aware default counts had both its cases the wrong way round.** `arrange-groups`' not-connected reason said no connection ran *directly between the arranged containers* and added, parenthetically, that connections between their nested children were *not counted here*. Measured on the two fixtures that separate the cases — two zones with one child each and one child-to-child connection, and the same two zones with one box-to-box connection — the route counts the first and not the second, which is both halves inverted. A container is never inside itself, so a connection drawn between two container boxes resolves to no container at either end. Nothing pinned the sentence, so it had been shipping as a truth-telling fix that told the caller to add exactly the connection which could not move the branch and to leave alone the one that would. Recomposed rather than edited, and pinned to both measurements.

### Title placement on new objects

- **A new `Grouping`, native group or note carries Archi's own title alignment.** Archi's diagram factory stamps a type's UI-provider defaults onto every object created from the palette. This server builds objects straight from the EMF factory, which stamps nothing, so those three types came out **centre** where a hand-drawn one is **left** — on a 400 px box, the difference between a title starting a few pixels from the edge and one sitting ~170 px away. An agent produced a canvas a human would not have, and could not discover it without rendering. Exactly three types diverge and exactly three are stamped: connections, images and view references are already born holding what their own providers would write. Ordering is the contract — the default is stamped before the no-styling early return, so an unstyled object still matches the palette, and the caller's own `textAlignment` is applied afterwards, so an explicit request always wins. **The parity is scoped, and the schema says so:** a *plain ArchiMate element*'s default is derived by Archi from a user preference, so on a host where that preference was changed the palette stamps it and this server does not. The three stamped types are unaffected, their providers returning a hardcoded value on any host. Not following the preference is deliberate: doing so would make output depend on the host the server runs against, and would break the guarantee that a plain element comes back unstyled.
- **`clone-view` keeps a cloned object's vertical title placement.** `textAlignment` was copied and `textPosition` was not, so cloning a view silently reset every object's title band to TOP — while the copying method's own documentation already claimed it handled both, which is why an audit of it would not have caught the gap. The two travel together at the render: alignment places the title's glyph run horizontally and position selects the band it sits in, so a copy carrying one and dropping the other relocates the title while appearing to preserve styling. Both now travel in one place rather than at call sites that can drift apart. An image is exempt, having no title band. **One gap is disclosed rather than left silent:** `bulk-mutate` carries no styling field in its per-operation result, so a bulk placement of one of the three defaulting types gets no signal that it now holds a left-aligned title. That is pre-existing and uniform across every styling field, but this is the first change to make it hide a materially new one.

### Layout & routing

- **An element dragged clear of the container it is nested in is a real obstacle again, and the two detectors that disagreed about it now agree.** The per-connection obstacle set exempts an endpoint's own ancestors and descendants because a connection terminating on an endpoint cannot avoid what lies between that endpoint's boundary and its centre. Membership was selected on `parentId` alone, and Archi lets a user drag a nested child clear of its parent — `parentId` says one thing while the rectangles say another, which is the entire reason `assess-layout` reports `boundaryViolationCount`. So a descendant sitting **anywhere on the canvas** was exempt from the obstacle set of any connection terminating on one of its ancestors: measured on a two-endpoint fixture, the obstacle set came back empty, the connection reported `routed=1 failed=0`, and the drawn path ran straight through a 200x150 element while `assess-layout`, one class away, was already naming that same element as escaped from its parent. Both ancestry families are now **filtered by geometry** after the ancestry walk: a node whose rectangle is fully disjoint from the endpoint's stays in the obstacle set. On the measured fixture the connection still routes — it now detours below the element instead of through it. **Depth, stated honestly:** at depth 1 the hole pre-existed (the previous direct-children rule matched on `parentId` with no geometry either); at depth 2 and deeper it was introduced when the descendant walk became transitive, which is when a drifted grandchild stopped being an obstacle. **Partial overlap keeps the exemption, deliberately:** a child a few pixels over its parent's edge is still between that parent and the connection's terminus, and "any overflow means obstacle" would make a populated container unroutable again — the exact defect the transitive rule was added to close. The predicate is the package's existing strict-overlap AABB test, compared once against the endpoint rather than per link up the chain. **`assess-layout`'s published rating can move, and its blast radius is exactly bounded:** the assessor's pass-through and label-overlap dimensions build their exclusion sets from this same helper, and the change is a provable no-op on any view where `boundaryViolationCount` is zero — every child fully inside its parent implies, inductively, every descendant fully inside the endpoint and therefore overlapping it. So a rating can only move on a view `assess-layout` was already reporting as broken, and it moves toward what the boundary detector was already saying; the existing assessor corpus (24 classes, 1302 tests) showed no movement at all. Separately, the router's upward walk had **no cycle guard** while the assessor's copy had carried one all along: on a hand-built parent cycle it did not throw or fail, it hung. It now terminates on the same visited-set idiom, and the assessor's copy is deleted in favour of the shared one, leaving a single definition of each ancestry family.

- **A connection terminating on a populated container is routed instead of being reported unroutable.** The per-connection obstacle set exempts an endpoint's own surrounding hierarchy, and that duty was transitive in one direction only: every ancestor was excluded, but only *direct* children were. A node nested two levels inside an endpoint therefore stayed in that endpoint's own obstacle list — and on the node-as-container shape this server's own technology-and-deployment guidance tells an agent to build, the target's centre routinely lies inside exactly such a node. The A\* search found no path to a point it was simultaneously told to route around, and reported `element_crossing` naming the endpoint's own grandchild. **The consequence was lost work, not a misleading line in a report:** in default (non-force) mode only *routed* connections have a command emitted, so the failed connection kept whatever bendpoints it already had; the same phantom failure is what gates the auto-nudge pass, which **moves elements**, and what triggers the corridor re-route stage. An agent that cannot see the canvas has no way to tell a phantom failure from a real one — in the run that surfaced this, it believed the report and deleted the connection from the view. Both ancestry families are now transitive, at all four sites that build one of these sets: the router's obstacle list, the terminals-only obstacle veto (where a phantom obstacle **reverted** a legitimate rectification), and the two label-exclusion sets, whose optimizer contract had promised descendants all along. **The exemption is scoped to the endpoints and nothing else moved:** an unrelated element on the direct path is still an obstacle, and a connection that merely passes *through* a nested hierarchy while terminating elsewhere still routes around every level of it. Containers are unaffected — a native group and an ArchiMate `Grouping` never enter the obstacle list at all, so this bites element nesting only. The assessor's own descendant walk, which had been correct all along, now shares the one definition rather than being a second copy of it.
- **Five layout and spacing passes that were silently re-sizing leaf elements now name them.** These passes write a *full rectangle* to every child, not just an origin — and in a grid that rectangle is the child's **cell**, so a leaf sharing a column with a container that fitted wide is stretched to that column's width. The behaviour is not new; what was missing is that nothing on the wire disclosed it. The responses carried move counts and container geometry (`elementsRepositioned`, `nestedContainersFitted`, `resizedAncestors`, `resizedGroups`), and a caller reading them would reasonably conclude that elements had *moved*. On a live view a 120 px element landed at **2230 px** while the response said only that 69 elements had been "repositioned" — a count of moves that silently also covers re-sizes is a report of neither, and the caller cannot see the canvas to catch it. **`resizedElements`** — the field `resize-elements-to-fit` already carried — is now returned by `layout-within-group`, `layout-flat-view`, `adjust-view-spacing`, `auto-layout-and-route` and `optimize-group-order`, naming each child whose size actually changed with the rectangle it ended at, so the next call is not planned against a width this one already replaced.

  It is an observation, not an echo — a child re-written to the size it already had does not appear — and it reports **size alone**, so a child that only moved is not in it. On the nesting passes it is disjoint from `nestedContainersFitted` by construction (the two are the arms of one branch on whether the walk descended into the child), which means a container left in place at the depth cap and then stretched by its column is named here rather than nowhere. Omitted from JSON when empty; in proposal mode the count rides as `elementsResized`. The disclosure is **not** conditional on `autoWidth` or `recursiveChildren` — leaving either unset never opted out of the re-sizing, and an earlier caveat pinned to `autoWidth` invited exactly the "does not apply to me" reading that let an 800 px dead band through. Back-compatible constructors delegate with an empty list throughout, so a response built through one names no resized child, exactly as before the field existed.

- **The terminal-anchoring wrap stops discarding straightening it never broke.** The four path-straightening passes that run at the end of every full re-route each snapshot the path, mutate it, and roll the whole pass back if a terminal bendpoint is not sitting on its element's face line afterwards. That test read the **post-state only**, so a path that arrived at the passes with a terminal already off its face line failed it no matter what the mutation did — including mutations that never touched a terminal. Every one of the four passes was therefore disabled on exactly those routes, and the effect compounds: measured over six routing fixtures, 17 of 170 connections arrive that way and each one lost all four passes. The rule is now a **delta**: a mutation is rejected only if it moves a terminal *off a face line that terminal was on beforehand*. The two ends are judged **independently**, which is the part that is easy to get wrong — the shared predicate conjoins them, so comparing that conjunction before and after would leave the target end unguarded on any route whose source arrived off-face, and a mutation dragging the target off its face line would commit unchallenged; two connections in the fixture corpus do exactly that. A second rule covers what the flip rule cannot see. Comparing face-line membership at the terminal position does not check that the point sitting there is still the *same* point, so on a route that arrived off-face a pass could rewrite that terminal, push it further off, or delete it and let the next bend inherit the attachment. Two of the four passes are therefore also barred from moving a terminal that arrived off-face — the two whose write range can reach one and which nothing else bounds. The other two are exempt for reasons that are properties of the code rather than policy choices: one deletes a point only when it is exactly collinear with its neighbours, so a terminal it removes lay on the line the connection was already drawn along and the picture does not change; the other is already confined to the route interior by an existing guard. Both exempting properties are pinned by test, so relaxing either fails the build instead of quietly widening the rule. Rejection on structural grounds is unchanged and unconditional. Legitimate rollbacks are untouched — 102 of them across the corpus before and after. The measured effect on routing quality is **small and honestly small**: two redundant bendpoints removed and two diagonal terminal segments straightened across six fixtures, with zigzag, lateral-jog, redundant-bendpoint, hub-port-quality, anchor-drift and overall-rating counts byte-identical everywhere. This is a correctness fix, not a visible routing improvement.
- **The disclosed exception is now closed: the coincident-segment offset pass stops letting the other end veto.** The fifth wrap site kept the post-state-only rule when the other four moved to the delta rule, and that was published as a deliberate exception rather than an omission. It has now been converted, and the sharp end of the defect turned out not to be the one the exception described. The shared predicate answers for **both** terminals at once, while the offset pass only ever establishes that the segment it just moved reaches **one** of them — so an offset that touched the source end was rolled back because the *target* end was off its face line, a terminal at the far end of the route that this mutation could not reach and had not touched. The end that was moved is now judged on its own, and an end the offset never touched cannot veto it. Measured over the fixture corpus: **9 such rollbacks**, every one of them at the second of the two call sites and none at the first, and every one with the same shape — the touched terminal moving *along* its own face line while the untouched one was off its face. Because this site's write range can reach a terminal with nothing else bounding it, it also gains the **pin**: a terminal that arrived off its face line is not relocated at all. That keeps the existing division of labour intact — this pass declines to move a terminal, and the stage after it separates the corridor by inserting a bend while leaving the terminal exactly where it was. **No structural arm was added**, because this site's frame is unaugmented and its mutation cannot change the path length, so the condition could never fire. The effect is **small and mixed**, and is reported as such. The routing fixture corpus is six files but **five distinct views** — two of them are the same 26-element, 30-connection view under different ids, which every census here confirmed by returning byte-identical rows for the pair. Across those five: seven routes change their final geometry; one fixture's coincident-segment count falls 10 → 9 and its hub-port quality doubles; edge crossings fall on two fixtures and **rise by one** on a third; one fixture gains a redundant bendpoint; two fixtures are byte-identical; and no fixture's overall rating moves. Legitimate rollbacks are untouched. All five sites now share one rollback policy in one place, not merely one predicate. **One check in the family is still a whole-path comparison and stays that way on purpose:** the reconciliation stage never moves a terminal, so its verdict must be invariant and a change of verdict signals a bug rather than a policy decision — the pipeline documentation names it as the remaining exception rather than leaving a reader to notice the asymmetry.

- **`auto-route-connections` now names the notes its routes were applied through.** A note is deliberately excluded from the router's obstacle set — notes are often large, and treating one as solid would over-constrain routing — so a connection **will** be routed straight through a note sitting in its corridor. That much was already published in the tool's description. What was missing was *which* note: a description is transmitted once, at schema time, and can only say that a crossing is possible, never that one happened. An agent that had just routed a view and wanted to know whether it had laid a line across the legend had to issue a second call to a different tool, `assess-layout`, which answered with a count whose ids were recoverable only from prose — `violatorIds` has no `connectionThroughNote` key. The response now carries **`CONNECTION_ROUTED_THROUGH_NOTE`**, naming every (connection, note) pair, with the crossed note ids in `remediationViolatorIds` and a matching `nextSteps` entry. **The router's behaviour is unchanged** — this is a disclosure, not a new avoidance rule, and deliberately not a `violations` entry: nothing was broken, and that channel's only reason code speaks about a crossed *element*, which a note is not. Cardinality is stated rather than left to be inferred: exactly **one entry per call**, listing every pair with the pair count in the message and never truncated, so a caller comparing it against `assess-layout`'s per-pair `connectionThroughNoteCount` reads agreement rather than a phantom mismatch. The two are not the same population and the message says so: they share one geometry and agree pair-for-pair on what the call routed, but the metric is a **whole-view** figure that also counts connections the call did not route and element **images**, so a higher count there is not a disagreement. The remedy is `update-view-object` on the **note**, explicitly *not* `undo` — the route is not the thing that is wrong, and undoing discards a good route while leaving the note where it was — together with the fixed-point fact that moving a note changes the routes around it, so the result has to be re-assessed rather than assumed. The two detectors share one geometry (the perimeter clip and inward inset now in `GeometryUtils`) precisely so they cannot drift: the router's own obstacle geometry expands rectangles outward by its margin rather than shrinking them inward by the inset, a difference of twice the constant on every side, and a tool reporting "I crossed a note" beside a metric reporting a clean view would tell a caller one of its two instruments was wrong without telling it which. Reported on every path — immediate, queued in a batch, and awaiting approval — since a deferred call still computes the routes its projection is made of; and on every strategy and mode that applies a route, `clear` and `terminals-only` included. `clear` matters more than it looks: removing every bendpoint leaves a straight centre-to-centre line with no pathfinder left to steer it, so clearing makes a note crossing **more** likely, not less. The disclosure is also taken **after** the auto-nudge pass rather than before it, because that pass merges freshly-routed paths and rewrites the bendpoints of connections whose endpoints it moved — a check taken earlier would describe geometry the same call then replaces. Alongside it, the obstacle policy itself is written down for the first time: the pipeline builds three obstacle lists and they **disagree about notes on purpose**, a note being empty air to the pathfinder and a solid rectangle to everything measuring the space around a settled path (edge nudging, coincident-segment offsets, label clearance, hub-perimeter routing). The parameter documentation throughout `model/routing/` said "all element rectangles on the view" at twenty sites; nineteen of them are fed the unified list, which holds notes, images and view references, and now say so.
- **`auto-route-connections` and `auto-layout-and-route` can hide the labels that have nowhere to go — opt-in, and they name every one they hid.** On a dense flow view a handful of connection labels collide at *every* candidate position, and `labelPosition` only relocates the problem. The router already knew which ones and threw the answer away — the label optimizer scored all three positions per connection and kept only the winner. That per-connection verdict is now retained, and `labelPolicy: "auto-hide-on-collision"` acts on it: exactly the unplaceable labels are hidden, every placeable one stays visible, and the response lists each hide under **`hiddenLabels`** by `connectionId` with a reason — never truncated, so each is auditable and reversible with `update-view-connection(showLabel: true)`. **It is off by default**, so omitting `labelPolicy` leaves label visibility byte-identical. A label the caller hid themselves is never overridden nor claimed as a policy hide; the hides ride the routing pass's own compound, so one undo reverts them with the routes; and an approval card names the labels the proposal will hide. A label counts as unplaceable only when *every* position carries a collision the engine cannot escape, and a Middle label the Label Offset can still lift clear is *not* unplaceable. On `auto-layout-and-route` the policy is honoured where a routing pass runs — grouped mode, and flat mode with a `targetRating`; flat mode *without* a target never invokes the label optimizer, so it **rejects** the parameter with a remedy rather than silently doing nothing.
- **`layout-within-group` gains `recursiveChildren` for multi-level nesting, and reports what each level became.** The pass was single-level, so an inventory nested three deep — functions in components in domains, or region → availability zone → node → artifact — needed hand-computed coordinates. With `recursiveChildren` set, descendants are arranged post-order in one atomic command with a single undo, every descendant container the pass re-fitted is reported in **`nestedContainersFitted`** (id plus landed rectangle, the downward counterpart of `resizedAncestors`), and the depth cap is a response flag rather than a log line. Under the recursive descent each grid column is sized from its own widest member instead of from the widest element in the whole grid, so one over-wide descendant no longer inflates its siblings, their container, and that container's siblings a level up; columns still line up across rows, and the non-recursive default is unchanged.
- **`auto-layout-and-route` grouped mode lays out the whole subtree, not one level.** `mode: "grouped"` treated every direct child of a top-level group as a leaf: a child with children of its own was sized from its *own label text* and never descended into, so its contents kept their old coordinates and escaped the box just shrunk around them. Each top-level group is now delegated to the same post-order recursion `recursiveChildren` drives, which sizes a container from its contents and reserves its title band. `elementsRepositioned` counts every descendant the pass moved rather than only direct children, each re-fitted nested container is reported with the rectangle it landed at, and inter-group arrangement measures the fitted rectangle rather than the pre-descent one.
- **`auto-connect-view` gains a `relationshipIds` allow-list.** Filtering by relationship *type* could not express a curated slice — a strict producer → hub → consumer cut had to fall back to seventeen individual `add-connection-to-view` calls to exclude same-type reverse flows. The optional array is AND-composed with the existing `elementIds` and `relationshipTypes` filters; an unknown id fails fast with `RELATIONSHIP_NOT_FOUND` **before any mutation**, while a valid-but-undrawable id keeps the existing silent skip.
- **`auto-route-connections` reports a full re-route that makes a view worse.** The existing crossings warning compares against a *straight-line topology estimate*, never against the view's own before-state, so it cannot fire at all on a view with no straight-line crossings — a 2 → 8 regression was silent and a 6 → 17 regression fired with the wrong diagnosis. A new `AUTO_ROUTE_CROSSINGS_REGRESSED` structured warning names both counts and points at `mode: "terminals-only"`, which already refuses crossing-adding rectifications. It is **gated on the input having been routed**, so a first-time route is never advised to undo a good result, and its `remediationTool` names the recovery for the arm the call took — `undo` once the re-route has been applied, `end-batch` while it is queued, and no tool while it awaits a human's decision.
- **`auto-route-connections` no longer counts an element that ended where it started as nudged.** The `autoNudge` loop runs up to two iterations and sums each element's actual displacement, and a sum of zero was published like any other: the element appeared in `nudgedElements` with `deltaX: 0, deltaY: 0` and `nextSteps` announced *"1 element(s) were automatically nudged to resolve pass-throughs"* — while the **same response** still listed the connection that move was meant to unblock in `failed` and repeated the identical move in `recommendations`. The next call reproduced it verbatim, because the geometry really had ended unchanged. The reported list now names only elements that ended somewhere new, and every surface built on it agrees: the array, the nudge count in `nextSteps`, the approval card and the undo label. Filtering alone would have been the worse bug, so the outcome is disclosed by a new **`AUTO_NUDGE_NET_ZERO`** structured warning carrying each element's id in `remediationViolatorIds`. It **states what was observed and refuses to name a mechanism**: two things produce a zero — a move a later iteration reversed, and a move the clamp that keeps a nested child clear of its parent's title band absorbed on its only iteration — and the summed deltas cannot tell them apart, so claiming the loop oscillated would be false whenever the clamp was the cause. `remediationTool` is a spacing lever rather than `auto-route-connections`: both causes are properties of the geometry the tool was handed, so re-running it recomputes the same recommendation and reproduces the same zero. The map that drives applied geometry is untouched — only the report is split — so what the model ends up holding is unchanged. One consequence is disclosed rather than hidden: the parent-fit cascade is grow-only, so a group grown for a move that was later reversed is not shrunk back and can outlive the nudge that grew it, and the `resizedGroups` next step now says those groups were resized *to fit their contents* instead of *to contain nudged elements*, which would have asserted a nudge the same response no longer reports.
- **The "some connection IDs were not found" step no longer fires for unrelated warnings.** That next step was gated on the free-text warning list being non-empty, and eight producers write to that list — so seven raised a false claim about connection ids alongside a true warning. It is now gated on a `CONNECTION_NOT_FOUND` structured code whose `remediationViolatorIds` names exactly which ids were missing.
- **A nudged child is held clear of its parent's title band.** `auto-route-connections(autoNudge)` floored a nested child at the container padding on both axes, so a routing lift could move a child into the parent's title strip — trading a cosmetic routing defect for the critical parent-label finding the assessor vetoes the layout rating on. The floor is now the container title band, and it never exceeds the child's own pre-nudge position, so the clamp can only shorten an upward move. The whole-model sweep carries a `contextualPartialDimensions` key per view — the names, not the 38-entry map, which would have multiplied the payload and destroyed the one cheap overview call the sweep exists to be — always present, with an empty list as the positive measured statement *nothing was left unexamined here*, and its drill-in step gated on the sweep having actually found one. **Nothing about any rating changes**, and the degenerate path is deliberately unchanged: its base line already abstains rather than certifying.
- **A detected glyph-over-title collision is now named in the prose the agent reads, on all three surfaces that report it.** `ownIconOverLabelCount` was measured, published as a field and declared `checked` in `coverage` — and then said nothing anywhere an agent actually reads. It reached none of `generateSuggestions`' arguments, so it was structurally incapable of producing a suggestion; `nextSteps` had no branch on it; and the whole-model sweep (`scope: "all-views"`) left it out of the per-view summary while carrying the equally informational `cousinOverlapCount`. The single-object path had the rule right all along, carrying its findings into the prose under a comment reading *a defect suppressed from the rating AND absent from the prose is invisible*; a one-object view disclosed the collision while a seventy-nine-node view carrying seventeen of them did not. The count now produces a suggestion naming the number and the remedy, a `nextStep` emitted **above** the rating switch (the metric moves no rating, so a view carrying it typically rates `excellent`, and both that arm and the default arm contribute nothing — a step placed inside the switch would be swallowed on exactly the ratings it reaches), and a `ownIconOverLabelCount` key in the whole-model sweep's per-view summary, with the sweep's own `nextSteps` naming a non-zero count as a reason to drill in whatever the rating says. **Nothing about the rating changes**: the count still enters no breakdown, still moves no tier, still falls to the uncounted arm of the quality loop's metric lookup and can still never be named as a limiting factor. Informational governs the *number*, not the *prose* — the policy `anchorDrift` and `lateralJogReversal` already followed.
- **The alignment remedy now says the fix is per view object.** The served remedy read *"change the element's `textAlignment` or `verticalTextAlignment`"*, which reads as a property of the model element — so an agent applies it once and takes the model to be clean. Both alignments are stored on the **view object**, so an element shown on four views carries four independent alignments. This is not hypothetical: on a live run the correction was applied on three views, the result generalised to the model, and a fourth view was still colliding on the same element. The tool description, each finding's own description, `docs/layout-engine.md` and `docs/glossary.md` now all state the scope and that the correction must be repeated on every view showing the element.
- **`assess-layout` now answers the hub-sizing question *before* anything has been routed.** Sizing a hub for its connection fan-out is cheap on a freshly placed view and expensive afterwards: resizing it later invalidates every route already computed against the old perimeter — a measured run paid 23 anchor drifts and two undos for that order. The metric that was supposed to warn about it, `hubPortQualityScore`, cannot: on a view with no stored routing no element face carries the four terminals its guard needs, so it returns a vacuous `1.0` and a 13-connection hub at 120×55 rates `pass`. The response now carries an **`unsizedHubs`** block naming every element whose connection count is above the fan-out gate and whose box is below the floor for that count, each row carrying the element and view-object ids, the name, the connection count, the box it has and the box it needs — typed fields, not a count standing in for them, because a count is an index into data the caller does not have. The requirement is an **absolute floor** (`300 + 10 × max(0, count − 7)` wide, `250 + 8 × max(0, count − 7)` tall) and deliberately **not** `detect-hub-elements`' sizing suggestion, which grows off the element's *current* size and so re-fires on an element that has just been sized correctly — a precondition built on it would report every hub as unmet forever. An element at or above both floors is simply absent. The block feeds no rating: no breakdown entry, no tier, no coverage row, and every rating on the reference corpus is byte-identical. Its connection count comes from the same walk `detect-hub-elements` publishes, so the two tools cannot hand an agent two different numbers for one element; the counting rule — both endpoints per ArchiMate connection, a self-loop twice, plain diagram connections never — is now stated in `docs/layout-engine.md`.
- **A view held at `fair` by hub-port quality is no longer capped in silence.** The rating gives the metric four bands and caps the view's routing tier for **both** `fair` and `poor`, but every remedy keyed off it fired only below the `poor` edge — so the whole quarter-wide interval `[0.5, 0.75)` was a region in which the tool marked a view down and said nothing about why or what to do. The assessor's own suggestion, `assess-layout`'s hub next-step and the after-snapshot hub step on all three spacing tools now speak across the entire capping region, and the `violatorIds.hubPortLowQuality` set the suggestion points at widens with them, so that pointer resolves wherever the remedy fires. The boundary is **exclusive** against 0.75: a score of exactly 0.75 is rated `good`, takes no tier, and is an ordinary value rather than a corner case — two of the seven corpus fixtures sit exactly there, and an inclusive comparison would have turned the fix into a false-positive generator. All three now read one band function rather than a repeated literal, so the band a view is placed in and the remedy it is offered cannot drift apart again. The quality loops' own predicates are deliberately **not** widened: they decide which candidate iteration `auto-layout-and-route` and the spacing tools *commit*, and moving them would change the geometry written to the model rather than what the response says.
- **The three annotation-placement tools now say when the rectangle they are placing lands on a live route.** The published ordering rule — place annotations *after* `auto-route-connections` — is necessary and demonstrably not sufficient: after routing is exactly when there are corridors to land in, and a measured run obeyed the rule and still took four crossings on one view. So the gap was never weaker guidance; it was that a rule transmitted once at schema time cannot say whether **this** rectangle is on a route. `add-note-to-view`, `add-view-reference-to-view` and `add-image-to-view` now measure the resolved rectangle against the routes on the view and return an **`ANNOTATION_PLACED_IN_ROUTED_CORRIDOR`** structured warning naming every connection it crosses, with the connection ids in `remediationViolatorIds` and a remedy that moves the annotation rather than the routes. **The severity differs by tool and the message says which applies**: a note lands in the informational `connectionThroughNoteCount`, while a view-reference or a standalone image is an ordinary layout node to the assessor and lands in the **rated** `connectionPassThroughs`, which can drive a view to `poor` — the two tools the note-scoped guidance never covered are the damaging ones. The warning rides on the response **entity**, so it survives the approval arm, which discards `nextSteps` wholesale and replaces them with three fixed approval lines; it is projected on `bulk-mutate` operations too, because a disclosure present on one entry point and absent on its sibling makes its absence uninformative on both. On a queued call it states its own basis rather than abstaining — the routes it read are real current state, and what it cannot promise is that a sibling command still in the queue will not move an endpoint first. The measurement reuses `ConnectionThroughNoteDetector` at the assessor's own pass-through inset, so the warning and the assessment cannot disagree about what counts as a crossing.

- **The two halves of `assess-layout`'s diagonal-terminal population are now typed counts with their own violator lists, and each half's remedy is scoped to its own connections.** On a view carrying both kinds, `suggestions[]` held two entries opening with the identical clause and no shared denominator, so an agent could not tell two halves of one population from two unrelated findings, nor either half's number from the total reported beside it — and the split reached the wire *only* as those two strings, since a single undifferentiated `nonOrthogonalTerminals` violator key covered the whole population. The remedies also worked against each other: one warned that a full re-route would likely increase crossings, while the other invited a re-route that, with no way to name a subset, was necessarily view-wide and would reach the connections the first was protecting. The response now carries `zeroBendpointNonOrthogonalTerminalCount` and `routedNonOrthogonalTerminalCount` beside the unchanged `nonOrthogonalTerminalCount` they sum to — publishing all three, rather than two and leaving the client to subtract, because making the reader do the arithmetic to discover a partition exists is the same defect one step removed — plus `nonOrthogonalTerminalsZeroBendpoint` and `nonOrthogonalTerminalsRouted` violator keys. The pre-existing `nonOrthogonalTerminals` key keeps its whole-population meaning and contents: it is named in two served descriptions and a published table, so narrowing it would break existing consumers. Each suggestion entry now states which half it is, the total it is a half of, the violator key carrying its ids, and that `includeViolatorIds` must be true to receive them; the routed half's remedy names `connectionIds`, which confines an `auto-route-connections` call to that half and leaves every other connection's bendpoints untouched, so the conflict is resolved by scope rather than by softening either warning. **The routed half is now measured rather than subtracted, and that fixed a real misattribution.** It was computed as the total minus the zero-bendpoint count, but the zero-bendpoint count was only ever incremented in the source-terminal branch; the source and target branches guard against *different* rectangles, so a connection drawn as a straight line between two element centres can be suppressed on the source side and flagged on the target side. Such a connection was filed in the routed half — sending an agent to re-route a route that does not exist. Each flagged connection is now assigned to exactly one of two disjoint id sets at the moment it is flagged, in both branches, and both counts are derived from those sets. No rating moves: the zero-bendpoint count feeds suggestion text only and is not an input to the rating computation, which continues to read the unchanged total — verified by measuring every rating surface on one mixed fixture before and after the change.
- **The assessor tests a title where Archi actually draws it.** `ownIconOverLabel` modelled every title as horizontally **centred** and anchored at the object's **top** edge. Archi does neither unconditionally: its figure hands the title control a single layout cell whose two alignments come from the object's own `textAlignment` and `textPosition` — both of which this server publishes as writable parameters, so a left-aligned or foot-anchored title is reachable through this server exactly as through the UI. Measured on a 400 px box, a LEFT-aligned title's ink begins **4.6 px** from the left edge where the centred model placed it **169 px** away: invented collisions and missed ones in equal measure. Against a foot-anchored title the top model failed in both directions at once — a real collision at the foot went unreported, and a top-anchored icon was blamed for burying a title that was not there. The horizontal run is now positioned per alignment, using Archi's own 4 px text-control margin and the existing 16 px type-icon reservation rather than fitted constants; the vertical band is anchored per position (TOP at the cell top, CENTRE at `top + (cellHeight − bandHeight) / 2`, BOTTOM at `cellBottom − bandHeight`). Verified at the render on Archi 5.10 to the tenth of a pixel across eight probed cases, single-line and wrapped. TOP stays byte-identical, and an unrecognised alignment or position degrades to the EMF default rather than throwing. The finding's description now names the vertical position as well, since on a vertically-caused overlap the alignment plays no part and the remedy pointed at the wrong axis.
- **A title the assessor never measured is no longer certified clean.** `ownIconOverLabel`'s abstention asked whether the node was a native *group*, which answered only the case the detector was first written against: a `Grouping`, or a plain element whose label measurement threw, arrives with the same zero label width and no group flag, and was reported as examined and clean without ever being compared with anything. The gate is now about **measurement, not kind**. Geometry that is not a number abstains for the same reason — positivity tests cannot express that condition, since `NaN <= 0` is false, so a non-finite width walked past the guard and returned a rectangle whose own coordinates were `NaN`, and nothing downstream noticed because every overlap comparison is also false against `NaN`. The two non-finite values fail in opposite directions, so both are checked: `NaN` suppresses a finding, while an infinite width survives a `min()` and would fabricate one. Both coverage consumers are pinned with a mandatory negative control, so the fix cannot degrade into a permanent `partial` that tells an agent as little as the false all-clear did.
- **`labelOnGroup` tests the band a container actually renders — wrapped, and clipped to the figure.** The detector tested a fixed single-line 20 px band, justified by "groups carry no measured label width". That was true of the native group it was written for and went stale the moment the detector was widened to admit every container — in the direction that hides defects, because a `Grouping` *is* measured. An SVG export of a wrap-titled `Grouping` put the second title row's ink **29 px** below the box top, where a connection label collided with the container's own name and was never flagged. The band now comes from the shared estimator, which doubles 20 → 40 px exactly when the title is too wide for its box. That exposed the opposite error: a thin swim-lane `Grouping` (250×30 with a long title) doubles to a band extending **10 px below its own bottom edge**, so a label belonging to whatever sits underneath was reported as overlapping *this* container's title. Archi clips a figure's contents to the figure, so the band is now clipped to the object's own height in the one place all three consumers read — and a container with no **usable** height (zero, negative or non-finite) has no title band at all, so no label can be on it. A native group is unaffected throughout: carrying no measured label width, it cannot take the estimator's multi-line branch.
- **`assess-layout` sees overlay icons colliding across a container and its child.** The sibling-overlap detector buckets objects by parent, so an ancestor/descendant pair is structurally unreachable — a container's corner icon overlapping a nested child's own corner icon reported `imageSiblingOverlapCount: 0` while the two glyphs visibly overlapped. A new informational `overlayIconCollisionCount` / `overlayIconCollisionDescriptions` walks the containment chain upward (so each pair counts once), excludes `fill` images, and declares itself in the coverage map. **Zero rating impact** pending live calibration, per the convention for new detectors.
- **Cross-branch overlaps are named, and the boundary count is real.** `overlapCount` is a *same-parent* count, so a collision between two objects in different branches was reported through their **containers** rather than the objects themselves — nothing rating-affecting was hidden, but the attribution was useless for a fix. A new informational `cousinOverlapCount` / `cousinOverlaps` names every pair of differently-parented, non-nested objects whose rectangles intersect, counted in the same pass, with its own violator key. Separately, `boundaryViolations` is a *capped description list*, and the rating, the Tier-1L regression veto and the iteration loop all read its size as the count — so a fourfold boundary regression compared `10 > 10` and did not veto. A true uncapped `boundaryViolationCount` is now wired to all four consumers. No rating moves.
- **`assess-layout` claims coverage only where a detector actually examined the object.** The v1.8 coverage map made "checked and clean" distinguishable from "never looked" — but three dimensions declared `checked` while their detectors were skipping the very objects in question, which is the false all-clear the map exists to remove. **`labelTruncations`** is now permanently `partial` (a visual group's title is never measured and the node is discarded before any box arithmetic runs, as is an element whose label measurement failed — so a zero certifies only that every *measured* element label fits, and a done-gate must render-verify group titles); **`edgeCoincidence`** is now permanently `partial` (the detector classifies each segment as horizontal or vertical and skips everything else, so a diagonal segment is never compared against an element edge); and **`parentLabelObscured`** downgrades *contextually* on any run carrying a parent whose title band was never measured — that parent still gets a verdict, but its band is sized as a single line however long the title is, so a wrapped second row goes untested. Counts, descriptions and every rating are untouched: this corrects what the map claims, not what the detectors find.
- **A degenerate view declares its coverage, and runs the detectors that can run.** A view holding at most one object short-circuited before the assessor ran and returned an **empty** coverage map, so a consumer could not tell a dimension that cannot apply from one never evaluated — while four suppressed detections, two of them rating-bearing, read as zeros no detector produced. Such a view now runs `offCanvas`, `labelTruncations`, `ownIconOverLabel` and `noteClip` where they are computable on a single object, reports the findings beside the counts and suggestions, and declares every dimension honestly: `not-applicable` only where the failure mode structurally needs two or more objects, `not-checked` everywhere else — and a dimension leaves `not-checked` only where the detector genuinely examined something, so a lone unmeasurable note or a lone group still reports `not-checked`. The view still does **not** rate: spacing and alignment return an explicit no-data sentinel below two objects, and feeding those to the rating would score a pristine one-object view `fair` on both axes for having nothing to compare against.
- **`assess-layout` no longer reports image defects in space where nothing is drawn.** Archi **clips** an element's image to the element box — an image larger than its element is cut off at the box edge, never drawn outside it, confirmed on both the custom-image and specialization-icon paths. The estimated image rectangle was anchored at the requested corner using the image's **natural** pixel dimensions and returned unclamped, so for an oversized image it covered pixels that never render. Every metric derived from it now uses the clipped rectangle, which **removes false positives**: a connection routed through an oversized icon's phantom overhang was flagged as an image crossing and **demoted `routingRating` from `excellent` to `good`**, and `imageSiblingOverlapCount` stops counting a sibling an icon only "reached" through the overhang. The clamp corrects the origin as well as the extent, because a right- or centre-anchored oversized image places its origin outside the element box. Images at or below their element's size are unaffected. This supersedes the v1.8 note below describing the tested image rectangle as one that "can overhang the element box".
- **The off-face terminal hug now affects the routing rating.** `offFaceParallelTerminalCount` shipped in v1.8 as informational, so a view with a real face-hug could still read `good` at the headline. It is now a rating entry capped at `fair` on binary presence — ratio-bucketing was rejected because a low-ratio hug would still read `good` and defeat the point. It is deliberately **not** carved out of the de-noised headline: a layout-bound hug is a real, actionable defect, not an accepted cosmetic.
- **`assess-layout` reports two route defects that survive a geometry change.** Both are informational — they appear in the response and leave the rating byte-identical — because each names a condition no existing dimension could see rather than a new way to fail. **`anchorDriftCount`** / `anchorDriftDescriptions` flags a connection whose stored route no longer matches the geometry it was computed for: every bendpoint is stored twice, once relative to the source centre and once relative to the target centre, and both describe the same point at the moment the route was written, so moving or resizing an endpoint afterwards leaves the two reconstructions disagreeing by however far the element travelled. The measured drift is reported per axis rather than as a flag, so an agent can act on the size of the move. No shape-based dimension can see this and none ever could — the collector blends the two reconstructions into the single polyline every detector is handed, so the disagreement is *structurally* invisible rather than under-tuned. The remedy names **re-routing** and deliberately does not name the straightener: the stored shape was correct when it was written, so it is not a shape defect. The floor is 1 px, derived from what the two-offset representation can represent rather than fitted to the largest drift any model happened to show. **`lateralJogReversalCount`** / `lateralJogReversalDescriptions` flags a connection that doubles back through a sidestep too narrow to be routing around anything — a four-point window whose two outer arms run in opposite directions along one axis, separated by a perpendicular jog of at most 8 px — and reports the four coordinates of each window. It is distinct from `zigzagCount` rather than a looser version of it: a zigzag reversal needs three points sharing one axis, and the sidestep puts the two arms on parallel lines, so no triple in the window shares an axis.

### Connection geometry as rendered

- **A connection's absolute bendpoints are reported in the frame Archi draws them in.** Archi stores each bendpoint twice, as an offset from the source centre and as an offset from the target centre, and a response has to blend the two. It blended them at a flat one half. The renderer does not: it weights bendpoint `i` of `n` at `(i + 1) / (n + 1)`, and the midpoint is only the special case `n = 1`. While the two reconstructions agree — true of every path this server's router writes, which derives both offsets from one absolute point — the weight makes no difference. Once an endpoint moves or is resized they disagree, and the drawn polyline is **sheared** rather than displaced: each point is pushed off the halfway position by `(weight − 0.5) × drift`, furthest at the first and last bendpoints and least in the middle. The old response reported the unsheared midpoint, a point drawn at no index at all, which at drift values measured on live views (30.5 px, 49.5 px) is a 10–20 px error on a four-bendpoint connection. Every single-bendpoint connection is unmoved. The interpolation is carried in integer arithmetic with a single division, which keeps the absolute → relative → absolute round trip lossless at every weight; evaluating the same weight in floating point lands a whole pixel low on 1.89% of bendpoints whose two reconstructions agree exactly. Element centres stay truncated to whole pixels, because that is the reference point the renderer's own anchor uses. The `AbsoluteBendpointDto` documentation now states outright that the value is **derived, not read**, and that while drift is non-zero no single coordinate is one the model holds on either axis.
- **The layout assessor measures the polyline Archi renders, not a flat average of two.** The same blend fed all 21 detectors that read a connection's path, so while a connection was drifted the detectors were reasoning about a line no reader sees — and the shear is largest at exactly the two terminal bendpoints the terminal-geometry dimensions judge. The collector now blends at the renderer's weight. Its centres stay **untruncated**, unlike the response surface's: the drift is read off them immediately before the blend, and rounding them would quantise away the sub-pixel disagreement `anchorDriftCount` exists to report. The published bound on how far the same bendpoint can differ between `assess-layout` and `get-view-contents` is corrected with the arithmetic: a response now divides once by `n + 1` rather than by two, so the real bound is `0.5 + n/(n + 1)` — 1.0 px at one bendpoint, 1.3 at four, approaching but never reaching 1.5 — where the description had said one pixel.
- **The label optimiser scores clearances in the coordinate system it thought it was using.** The pass built each connection's path by reading a stored bendpoint's start offsets and using them as canvas points. Those are offsets from the source centre, not coordinates, so every path point was displaced by the whole source centre — hundreds of pixels for any element away from the canvas origin — while the element rectangles the path is scored against are built from absolute bounds. The two were in different coordinate systems, so every clearance computed between them was meaningless. The path is now reconstructed the way an absolute bendpoint is recovered everywhere else.
- **A connection reports the element face it is actually drawn leaving and entering.** `get-view-contents` and the connection mutation responses now carry **`sourceRenderFace`** and **`targetRenderFace`** — one of `top`, `bottom`, `left` or `right`. This was not derivable from anything else in the payload: `sourceAnchor` and `targetAnchor` are the element centres the renderer aims *from*, and a stored bendpoint is a waypoint it aims *at*, so neither is the point where the line meets the box. That point is computed at paint time by a connection anchor, from the element's own untruncated bounds, and the server now derives the same thing. On a default installation every ArchiMate element figure gets Archi's orthogonal anchor — the preference defaults on, and the one edit part that opts out is used only by the Junction — which bands the reference point against the element's unexpanded box on each axis and resolves the nine band pairs to four faces, four corners and one interior case. **The field is null, and so omitted, whenever a face cannot be established, and absence never means "no face".** Seven distinct conditions produce it: the attachment is a corner, on two face lines at once; the reference lands inside the box; the figure's rounded corner puts the attachment on an arc — not a corner case, since a non-zero corner dimension is the *default* figure of twenty ArchiMate types; the element has no size; the endpoint is a Junction, which anchors on an ellipse; the endpoint is a `Grouping` on its alternate figure, whose fallback anchor is shifted by figure state the model does not carry; or the two anchor algorithms Archi can be configured with would name different faces. Two further declines were added rather than guessed at: the derivation requires **both endpoints to resolve to the same view**, so a connection created in the same batch as its endpoints cannot fall through to the wrong arm and publish a face the view does not render; and on a negative coordinate, where the response's truncating division and the renderer's `floor` can differ by a pixel and so land in different bands, it declines rather than picking one. Because the styling overlay that four call sites used to apply by re-listing a connection's fields silently truncated anything the builder derived beyond each site's own arity, the face was being dropped on all three prepare paths and on the bulk projection; one overlay that names no components replaces all four, so it cannot drop a field again.

### Images

- **`add-image-to-model` imports a batch in one call.** Importing a set of icons cost one call per icon. The tool now accepts an **`images`** array, capped at the same limit `bulk-mutate` uses so the two cannot drift apart, and reports every entry that landed with its archive path *and the caller's request index* — with failures removed, result position and request index diverge, and only the index maps a path back to the file asked for. No new failure semantics: the write was never transactional, so a partial batch leaves exactly what the same imports issued one at a time would have left. The single form is unchanged. **Bulk membership is not available, and both descriptions say why**: an archive write has no inverse (`IArchiveManager` exposes no removal of any kind), so no honest `undo()` exists. For the same reason the tool sits **outside the batching contract** — inside an open batch it writes immediately and returns plain success for a write `end-batch --rollback` cannot reverse, which its description now states.
- **All three image sources now state the SVG condition, and they state the same one.** Reading an SVG is the host platform's job, not this server's: SWT's optional rasterizer fragment arrived with the Eclipse 2026-06 platform, so Archi supports SVG from **5.10** onward and rejects it on every earlier release — a boundary Archi's own help publishes, along with the consequence that matters most, which is that a model carrying SVG images **can lose them when it is opened and re-saved on an older Archi**. That condition previously reached two of `add-image-to-model`'s three sources and stopped: `url` carried no format list and no caveat at all, `imageData` carried only a cross-reference to `filePath` that an agent reading a single property could not resolve, and the URL path's own download-failure remediation still enumerated the formats without it — the exact sentence a caller sees when an SVG url fails on an older host. All **seven** description and remediation sites now state it — three schema descriptions and four error remediations — each drawn from a **single shared constant** rather than written out again, so they cannot drift apart as they already had once. The wording names the *condition* rather than a version to guess with, so it stays true at the next Archi release, and it states a standing rule rather than a diagnosis of the call in hand: one of the four errors fires when the caller sent no image bytes at all, where a sentence about what failed to load would be nonsense.
- **An uppercase extension no longer mislabels an image under a Turkish locale.** Two of the three import paths derived a temp-file extension by lower-casing under the **default** locale. Under a Turkish locale an uppercase `.TIFF` or `.ICO` lower-cases to a dotless-ı string; the content sniff in Archi's image loader still reads the file, so the import *succeeds*, but the format switch — which lower-cases correctly — then matches no arm and falls to its `PNG` default. The response reported **`formatDetected: "PNG"` for a TIFF**, silently, and Archi's archive path inherited the mangled extension too. Four of the eight format tokens are affected (TIFF, TIF, ICO, GIF — the ones containing an `I`), which is why nothing built on `.PNG` or `.SVG` could have caught it. Both derivations moved beside the format switch as pure functions, lower-cased under a fixed locale, and are unit-tested against a forced Turkish default — including the round trip that reproduces the mislabel end to end.
- **The archive path is described as the opaque value it is.** Four surfaces published the shape `'images/<sha1>.png'`. Neither half is true: Archi mints the path as `images/` + a generated identifier + the *source file's* lower-cased extension, so it is not a content hash and it is not always `.png`. Two of the four were shipped tool descriptions that named the path format and, in the same sentence, the `IMAGE_NOT_FOUND` rejection — inviting a caller to construct or validate a path against a shape nothing returns, then naming the error that follows. All now say the value is opaque and server-generated and instruct the caller to pass it back exactly as received.
- **The icon-size advice no longer denies a parameter its sibling tool has.** `add-image-to-model` told every caller that "there is no width parameter", unconditionally, on the import tool that feeds *both* placement paths. It is true of an image drawn as an icon on an element, group or note, and false of `add-image-to-view`, which places a standalone image visual and takes `width` and `height`. The advice is unchanged and still good; it is now scoped to the tools it holds for, and names the sized alternative.
- **A failed URL download names the URL.** The generic download-failure arm substituted the exception's message *for* the url where every sibling arm appends it, so a cause carrying no message — a refused connection and a DNS failure both qualify — delivered `Failed to download image from URL: null`, reading as though the caller had passed a null url. The url is now always named, a cause with no message falls back to its type, and the arm carries a `suggestedCorrection`.
- **`imageCoveragePercent` reports the area the image actually paints, and its warning tells "too big" apart from "too prominent".** The same clipping finding as the assessor fix above, on the surface that assumed an image renders at its natural size: coverage was the image's whole natural area over the element's area with no intersection term, so a 40×40 image on a 120×15 element reported **88.9 %** where the area actually drawn is 33.3 % — and the advisory built on it claimed the image *"may obscure element name"*, which at 33.3 % it plainly does not, while what *was* true (the image is cut off) it could not say at all. Coverage is now the drawn area, **capped at 100 %**, and a **`fill`** image — which Archi scales to the box rather than clipping — correctly reads **100 %**. The oversize fact moved to `imageCoverageWarning`, which now reports **two independent conditions**: the image may obscure the element name, and/or it is larger than its element and will render cut off. Because `fill` coverage is unconditionally 100 % the obscure-name advisory always fires there, so under `fill` it names remedies that are actually available and says plainly that **it persists for as long as `fill` is set** — rather than offering "use a smaller image" (`fill` scales, so a 4×4 and a 4000×4000 image both cover 100 %) to a caller who cannot act on it. `update-view-object`'s description now documents both fields, which had no definition on any client-facing surface.

### Client portability

- **The guidance the server points agents at is reachable on clients that do not implement MCP resource reads.** 26 places in the plugin tell the agent to consult an `archimate://` URI — the routing preconditions checklist, the layer decision aid, the recipe library. On a client that does not expose resource reads to the model, every one was an instruction the agent could not carry out; the observed failure was an agent attempting an HTTP fetch on a non-HTTP scheme, burning turns, then reporting the guidance as unavailable. Two additions fix it without changing a single URI. **Resource templates** (`archimate://prompts/{name}`, `archimate://reference/{name}`, `archimate://recipes/{name}`) advertise the parameterised form of URIs that already ship, expanding to them verbatim. **`get-guidance`** delivers the same bodies through a tool, the one MCP surface every client implements: with no arguments it returns the catalogue of every available URI with its description (a resources-less client cannot list them either), and with a `uri` it returns the full markdown; an unknown URI returns a structured error naming it and listing the valid ones, never an empty success. The static resource registrations are untouched, so clients that already read them are unaffected.
- **A dead guidance pointer now fails the build.** A contract test scans the shipped production source for every `archimate://` URI and asserts each resolves in the resource catalogue. The catalogue, the resource registrations, the templates and the tool answers are all derived from one declaration, so the delivery routes cannot drift apart.

### Prompts

- **New `drawio-to-archimate-model.md` — replicate a draw.io architecture diagram as an ArchiMate model.** Point it at a `.drawio`, `.drawio.xml` or mxGraph `.xml` file and it produces elements, relationships and a view, with **every concept marked by whether it was read from the source or derived by rule** — the same evidence discipline the repo-to-model prompt uses, applied to a drawing. It parses the mxGraph XML directly rather than rendering it: containment comes from geometry (with a documented rule for the shapes authors draw a few pixels outside the box they meant, since draw.io does not snap), cloud-stencil tokens map to `(type, specialization)` pairs through an extensible table, and containers whose name is a separate text cell — the cloud-stencil idiom that otherwise drops the box as unnamed and orphans everything inside it — are re-titled by an adjacency test. What it cannot resolve it **reports rather than invents**: prose-only elements are named and not created, unnamed containers are rendered as genuinely untitled groups instead of being given a guessed or placeholder label, and elements that would otherwise land with zero relationships are surfaced as a gate rather than shipped silently. Two layout modes: `semantic` (laid out from the ArchiMate view recipes) and `mirror` (laid out to resemble the source drawing). The diagram's accompanying design document is an optional second input and is the single highest-value one — it is what turns an unlabelled arrow into a real relationship type — and vendor icon packages can be supplied as further optional inputs, by directory or URL, one per vendor.
- **`drawio-to-archimate-model.md` also ships as the `/drawio-to-archi` slash command, and the copy is kept honest mechanically.** Like `/repo-to-archi` the command is a **self-contained copy** of the prompt plus an argument-parsing preamble, because a slash command has to work without the repository present. Two copies of one document drift, and a drifted copy is worse than no copy — the user runs the command believing it matches the prompt they reviewed. Hand-syncing is exactly the step that gets skipped, so `tools/sync-drawio-command.sh` regenerates the copy from the source prompt, and `--check` fails when the two have diverged.
- **The draw.io prompt takes its inputs from a Confluence page, not only from a file.** The diagram parameter now accepts a path **or** pasted mxGraph XML, because a diagram pulled from a wiki or an issue tracker has no path — that is the route's normal case, not a degraded one. A new section documents locating the diagram on a Confluence page, written from a read-only capability probe rather than from assumption: the Forge/ADF macro names its diagram in `ac:adf-parameter key="diagram-name"` (kebab-case), **not** the legacy `ac:parameter ac:name="diagramName"` (camelCase), so a grep for one returns zero on the other and "no draw.io macro on this page" is a wrong conclusion wearing an observation's clothes. Both macro generations are documented side by side, and because one real page carried four macros and fourteen `.drawio` attachments — around ten of them orphans — an exact filename match is mandatory and a page is treated as a *set* of diagrams rather than one. The attachment-download half ships under an explicit **unverified** banner: the probe's download returned 401, and the failure clinic records both branches (a Data-Center-shaped URL fired at a Cloud site, missing the `/wiki` and `/download` segments, being the likelier cause than the missing permission the probe concluded), so neither outcome invalidates the section. Nothing downstream changes — every gate, trap, count and grade already operated on the mxGraph XML and the prose, never on where either came from — and a run sourced from a file or from pasted XML is untouched.
- **The prompt now detects a compressed diagram payload instead of silently reading nothing.** draw.io can store the `<diagram>` payload deflate+base64, which the prompt had no handling for at all — and an unread compressed payload is indistinguishable from an empty drawing, because every trap finds nothing and none of them raises. A new precondition runs before the first trap on a decisive signal (`<diagram>` present, `<mxCell>` count zero) and gives the decode pipeline, including the negative window size that selects raw DEFLATE, whose omission is the usual reason a correct decode still fails. Marked untested: all seven runs to date used an uncompressed specimen.
- **Seven draw.io prompt defects the sixth conversion run measured are closed, including a gate that could pass by redefining its own population.** The vertex-accounting gate says its buckets sum to the parsed vertex total; the run summed six buckets to 94 against a parsed total of 98 and reported **passed**, having quietly narrowed the denominator to the rectangle-bearing population. The four missing cells were the file's **edge labels** — draw.io stores an edge label as a child vertex of the edge, with a relative geometry and no width or height — and one had already been used elsewhere in the same report as evidence for a relationship. The gate gains a seventh bucket, the denominator is spelled out, and the sum must now be printed beside the parsed total. Two published calibration figures are replaced by what was measured rather than restated: the strict containment count is 75, not 71, and the grid-stretch worst case is 13 elements re-sized across a 230→3330 px stretch, not six across 2230 — with the escape hatch documented for the first time (`row` and `column` do not normalise child widths at all, so the stretch is grid-only and `elementWidth` does not rescue it). Endpoint recovery counted ten where the specimen needs eleven. The container decision table's last row had only a failure branch and now defaults to `Grouping` — the safer default, since a wrong `Grouping` under-commits where a wrong `Node` asserts the container hosts resources — and corroboration is extended to containers through that same row, with the ineligible count reported as a fourth figure so a reader can tell a low corroborated count from a narrow eligible pool. The badge rule and the bare-icon rule stopped competing for the same cells, and mirror mode no longer demands routing be fixed to a standard while forbidding the only remedy.

- **New `archimate-model-to-pdf-report.md` — turn any open Archi model into a print-ready PDF architecture report.** Paste it into an agent session with the Archi MCP tools connected and it produces a professionally typeset PDF, generated entirely from the live model: a **cover page with honest provenance** (model name, any version / date / author the modeller stored in the model's own properties, and the generation timestamp — deliberately *not* presenting the MCP session mutation counter as a version), an **executive summary** (purpose, element / relationship / view counts, layer distribution, element-type breakdown), then **every view in an optimal reading sequence** — the modeller's own folder and numbering order, falling back to ArchiMate abstraction (Motivation → Strategy → Business → Application → Technology → Physical → Implementation) — each with its exported diagram under a numbered caption, a per-view element table, the diagram's notes and any view properties. Two appendices follow: a **full element catalogue** grouped by layer (documentation, properties, evidence grade, and an "appears in" cross-reference) and a **relationship register**; an optional **Appendix C embeds the model's own generating prompt** verbatim. The prompt is **read-only** and tool-agnostic: any capable agent can drive it with the MCP query tools plus a PDF toolchain (**WeasyPrint** preferred, for true page-numbered footers; any Chromium browser works as a fallback).
- **Optional reference implementation — `archimate-model-to-pdf-report.py`.** A standalone Python generator that talks to the MCP server directly over its loopback HTTP endpoint: it harvests the whole model, exports each view, and renders the PDF via WeasyPrint in one command, with no per-run agent steps. It needs only the Python standard library plus the `weasyprint` CLI, is model-agnostic, and takes **`--full`** for 100 % element and relationship coverage, including concepts not placed on any view.

### Features

- **A `bulk-mutate` operation can be given a name, and referenced by it.** An operation may now carry `as: "coreBanking"` — a sibling of `tool` and `params` — and a later operation in the same call may write `"$coreBanking.id"` wherever it would have written `"$4.id"`. The positional form is unchanged, undeprecated, and still works on the same operation; the two may be mixed in one call and are governed by the same rules, so a name is backward-only, create-tool-only, cascade-visible and call-scoped exactly as a position is. What differs is what a typo does. A position lives in a dense namespace — every integer below the current index names some legal earlier operation — so `$5.id` written as `$4.id` resolves, and nests the object inside a different container that nothing rejects, because one `ApplicationComponent` inside another is legal ArchiMate. A name lives in a sparse one: `coreBankng` matches no declaration, so it can only be refused. The mistake this removes has been made twice, in two independent end-to-end runs, and neither run found it from the write response — one found it from a geometry metric that caught one of its two wrong nestings, the other from a downstream symptom, and fixed it by deleting and rebuilding the whole view. Names are validated in the prepare pass, which runs upstream of the immediate/batch/approval branch, so a bad one is refused **in every mode** — including queued into an open batch and parked awaiting approval, where the per-operation `parentViewObjectId` that discloses a mis-aimed positional reference reports nothing at all, because nothing has been written for it to report. A name must start with a letter or underscore and continue with letters, digits or underscores, so it can never be mistaken for a position; it must be unique within the call, and both declarations of a repeated one are refused, naming both positions, so a reference to it cascades loudly rather than being answered by position after all. An unknown name is refused rather than resolved to `null` — on an optional parameter such as `parentViewObjectId` a null is dropped in silence and the object lands at the view root. Relatedly, and for the same reason: **an operation carrying a top-level key that is none of `tool`, `params` and `as` is now refused, naming the key.** Unknown keys were previously discarded without a word, so a name written as `"As"` left the operation looking unnamed and pushed the failure onto whichever later operation referenced it — the same displaced blame the named form exists to remove.

- **`create-relationship` records provenance at create time.** It now accepts `documentation`, `properties` and `source` — the same trio, with the same `mcp.source.` key prefixing merged into `properties`, that `create-element` has always taken. The capability existed on `update-relationship` alone, which meant an agent reading the create tool's parameter list concluded relationship provenance was impossible and left relationships unmarked; the workaround was real but invisible from the tool reached for first. The values land on every non-duplicate path — immediate, approval, batch, and all four `bulk-mutate` back-reference arms — and the response reports the documentation and properties the relationship actually holds, read back off the model rather than echoed from the request. A create that matches an existing relationship still dedupes and is **not** modified: that path returns a no-op command, so writing the caller's metadata there would edit the model outside the command stack where undo could not reach it. The response reports the existing values and the description says so.
- **A container the source material never named can be represented as one.** `add-group-to-view` refused a blank `label` and `add-note-to-view` refused a blank `content`, so an untitled group or an empty note could not be created. The refusal stopped nothing and raised nothing anyone would triage — it relocated the decision from the server to every caller, and each caller answered it differently, one of them by painting raw parser cell ids onto a finished canvas. Archi holds and renders an untitled group correctly: the GUI's `"Group"` is the default for a shape a user drew, not a model constraint, and the canonical stored value for untitled is the empty string, never null. The tool surface was stricter than the model it wraps, which is the inverse of the validation-sync principle this server already holds for relationships. Both tools now accept `""` on all four paths — immediate, `bulk-mutate`, inside an open batch, and awaiting approval — and `update-view-object` accepts `text: ""` to clear a group's label or a note's content on both the handler and bulk paths. **An omitted key and an explicitly empty value stay different requests everywhere.** An empty string remains rejected for element view objects, where `update-element` is the tool that changes a name. Two adjacent surfaces were false once `""` became legal and are corrected with it: the shared missing-parameter diagnostic no longer advises callers to "provide a non-empty string value" where empty is now valid — advice that pushes an agent to invent exactly the placeholder this change removes — and the human-readable effect descriptions now test for *blank* rather than *empty*, so a whitespace-only label no longer renders as `Add group '   ' to view X`. Whitespace itself is still stored verbatim: Archi accepts it, the update path already did, and rejecting it only on create would recreate the born-versus-made asymmetry this change exists to remove.

### Tool documentation

- **Every standalone tool now documents what it returns, not just what it takes.** Twenty tool descriptions described their parameters and said nothing about their response, so an agent had to invoke the tool to learn its output shape — which for a destructive tool means invoking it to find out. Each now documents its response fields ahead of its existing `Related:` clause.
- **The batch and approval response envelopes are documented on the seven tools that reshape into them.** Under `begin-batch` and under pending approval a tool's entity moves under `preview` beside a `batch` or `proposal` sibling, and several adjacent conditionals were undocumented: `approvalRequired` is either true or absent and never false, `pendingApprovalCount` is absent rather than `0` on an empty queue, and queue fields are absent outside batch mode. The id question is documented with its condition attached: under **batch** the queued command closes over the same object, so a previewed created id is final and back-references resolve; under **approval** the proposal stores a deferred rebuild handle and re-runs the prepare at approve time, constructing a second object with a **different id**, so a previewed created id never resolves and the agent must re-query by name.
- **`begin-batch` and `bulk-mutate` name the same still-blind tools.** `begin-batch` listed six tools that report a queued id as not found, where `bulk-mutate` and the mutation-model documentation listed nine. Because that sentence enumerates what does **not** resolve, dropping three from the list implied they did.
- **`bulk-mutate`'s per-operation pointer tells the truth about where the detail lives.** It said per-operation parameters and response fields "are documented on the standalone tool of the same name" — false for roughly twenty of the twenty-seven operations, and an invitation to invoke a destructive operation to discover its response shape. It now says those operations are *governed by* the standalone tool and directs the reader there. The `set-view-label-expression` blank-name skip is corrected from an unconditional claim: blank-named objects are skipped only when *setting* a value; when *clearing*, they are cleared and counted.
- **Four tools now publish the deliberate restrictions their descriptions had left unsaid.** Each has a designed, internally documented exclusion that its published description did not mention, so a caller read the description, got the designed behaviour, and could not tell design from defect. `arrange-groups` treats a Node that happens to hold nested children as a **host, not a zone**, and says so. `layout-within-group`'s ancestor resize stays typed to native groups. `auto-route-connections` excludes both containers and notes from its obstacle set. And `add-image-to-model` never rejected SVG at all — the denial was a remediation hint on a failure path, where the real condition is the host platform's, now stated as a condition on all three import sources rather than as a blanket refusal. None of these designs is wrong; the descriptions were simply silent about them.
- **`arrange-groups` says which containers it left standing, and its "no inter-group connections" reason says what was counted.** `skippedContainers` names every populated top-level container the pass did not arrange, with the type that made it ineligible and what to do about it — a run that skipped fifteen containers used to read as a plain success. It is populated at DTO construction rather than beside the geometry read-back, because what was skipped is known before anything is applied, so a queued call reports it honestly while it still has nothing to say about geometry. Separately, the topology arrangement's fallback reason fired on a view holding 33 connections, none of which happened to run directly between the arranged containers, and a reader reasonably took it to mean the view had no connections at all; it now names what was actually counted.
- **Two rating-bearing metrics stopped describing themselves as informational.** `offFaceParallelTerminalCount` and `nonOrthogonalInteriorSegmentCount` each carried an internal note saying they never fed into the rating. Both are breakdown entries that join the routing tier chain — which is what the glossary and the layout-engine document have said all along — so only the notes were stale. Both are corrected, because correcting one would have left the file arguing with itself.
- **`create-element` states where provenance can and cannot be written.** The description now says `source` is a **create-time** parameter on every path the tool has, `bulk-mutate` included, and that provenance added or corrected afterwards is written as ordinary `mcp.source.`-prefixed keys through `update-element`'s `properties` map — because no update tool takes a `source` map at all. A guard test holds the claim so it cannot go stale as the paths change.
- **`search-and-create`'s optional-parameter list names `createSource`,** which its schema has always declared and its prose had always omitted. The new pin derives the expected set from the schema's own keys, so the description and the schema cannot drift apart again.
- **`update-element` and `update-relationship` state the provenance route their sibling create tools point at.** `create-element`'s description tells an agent that no update tool takes a `source` map and that later provenance goes through `properties` with the `mcp.source.` prefix spelled out — a claim the update tools themselves said nothing about, so an agent that reached for the update tool first (the natural move when the element already exists) read no route at all. Both now carry the reciprocal sentence. A guard test already forbids either tool from declaring a `source` parameter, so the published claim cannot quietly become false.

(1) The **frequency claim** — that the firing is rare, the first observed across many comprehensive test runs — is **withdrawn with no replacement rate**: nothing counts firings, so no rate can be substantiated, and the guidance now states the **condition** instead (expect the guard on a view whose connections carry no stored routing) rather than how often it fires. (2) The **prescribed order** in the disposition matrix gains a routing pass **before** spacing on all three rows that carry a spacing step — the flat-view row has no spacing step and is unchanged — because the spacing convenience tools measure each step against a route-normalized baseline: on connections carrying no stored routing they compare two states that are not comparable in the way the comparison assumes, return `reroute_degraded_input_baseline`, and never enter the loop. Routing first gives that comparison two routed states, and a sentence under the matrix now says so, so the leading pass does not read as a redundant recovery step. Changed across five files: `resources/prompts/routing-preconditions-checklist.md` (decision tree, termination-reason table row, the two withdrawn bullets, the condition, and the three matrix rows plus the new rationale sentence), `resources/reference/archimate-view-patterns.md` (control-loop footnote), `docs/layout-engine.md` (termination-reason table), `ViewPlacementHandler.java` (the `reroute_degraded_input_baseline` clause in all three spacing-tool descriptions, each keeping its `archimate://prompts/routing-preconditions-checklist` cross-reference), and this changelog. Two of the response's seven arrays follow the preset and five do not, and on a view carrying connections the five are usually the larger half, so `exclude` rather than `fields` is usually the parameter that moves the response size. That reach is now stated in the `fields` parameter description, where the preset is chosen, and the tool description no longer coordinates `fields` and `exclude` as interchangeable levers on one axis — it names `exclude` as the size lever and keeps the worked `exclude=['visualMetadata','connections']` example that follows it, which names the two arrays that usually dominate a view's payload. **Both parameters are also documented as applying to `format=json` and `format=graph` only:** `format=summary` and `format=tree` return before the field selector runs, so `fields` and `exclude` are inert there and the reach sentence would have been false on half the format enum if left unscoped. A guard drives the field selector at all three presets and fails if any preset ever reaches one of the five visual arrays, so the sentence goes red when it stops being true rather than only when it is deleted.

The suggestion itself did not: it labelled `6` **the** hub threshold, and did so eighteen characters from a sibling suggestion on the same element correctly reading `(large hub: > 12)`. The sentence now reads `(large hub: > 6)`, matching the sibling's shape and the vocabulary every other surface already published. Behind the label, the value is no longer typed into the sentence at all: it is interpolated from the single constant that also drives the branch and the growth arithmetic, so the published number cannot drift from the one the code tests.

An agent reading a row whose whole `suggestedCorrection` had been lifted into `corrections` found the key **absent** and had every reason to conclude the failure carried no remedy, which is the one misreading the shape was designed to make impossible. Nothing about either tool moved: the shape has been on the wire since the change that introduced it, and this is the surface where an agent learns to read it.

### Fixes

- **`export-view` refuses an oversized raster instead of taking Archi down with it.** The scale parameter was bounded as a *multiplier* — 0.1 to 4.0 — and that says nothing about the pixel area the multiplier produces. Archi renders a raster export as **one bitmap** covering the whole diagram, so a legal scale on a large view could ask the operating system for a buffer larger than the machine could back: a 6777 x 6538 view at scale 2.0 asks for 13574 x 13096 pixels, 711 MB in a single allocation. That failure is a native fault while the buffer is first written, not an exception the server could catch and report — the process died, taking the user's unsaved model with it, and the caller got nothing back at all. PNG and JPG exports now project the bitmap **before** anything is allocated and refuse the ones the machine cannot back, returning a structured `INVALID_PARAMETER` error that names the projected pixel dimensions, the byte estimate, the budget it was compared against, and **the largest scale that would have fitted** — so the retry is one call away. The budget is *free physical memory* — the figure the operating system reports as free, not the larger "available" one that counts reclaimable cache, because the render that exhausted the machine did so with the entire swap file untouched and the free figure was what bound it. It is queried at the moment of the call rather than fixed at build time, since the same export can be comfortable on an idle machine and fatal on a loaded one; where the platform will not report it, a conservative static budget is used instead. One bitmap may claim at most half that pool, because the export path holds the raster twice over while it encodes — the encoder's own buffers add a few percent beyond that, disclosed rather than padded, since widening the reserve would refuse renders that demonstrably succeed. The accepted scale range is unchanged and a small view at 4.0 still exports exactly as before — the new refusal is driven by area, not by the factor. `svg` and `pdf` allocate no bitmap and are not affected; the error names them as the resolution-independent way to get the same diagram at any size.
- **A rename inside `bulk-mutate` no longer reports the name the entity used to have.** Each operation's `entityName` was captured while the operation was *prepared*, before anything had been written — so renaming a relationship to `Renamed` came back saying `Serves`, and clearing a name to `""` came back saying `Serves` too: the one string true of neither the request nor the result. Since the client is an agent that cannot see the model, a name it reads as confirmation would have told it the rename had not taken. `entityName` is now re-read after the whole call has been applied — including when a *later* operation in the same call renames the same entity again — and a cleared name arrives as an empty string. The same read fixes `update-element`, `update-view` and `update-specialization`, and an `add-to-view` that follows a rename now reports the new name. A deletion is the one case the re-read cannot reach, since the id stops resolving the instant the delete applies — so the deleting command records the name at the instant it destroys the entity instead, and both `entityName` and `deletion.name` report the name it was destroyed under even when an earlier operation in the same call renamed it first. A deletion records a name only if it actually destroyed something, so one that declined — or whose subject an earlier operation in the same call had already deleted — leaves `deletion.name` as prepared rather than reporting a name written onto the detached object afterwards.
- **`update-relationship` honours the empty-string clear its schema advertises.** The schema says an empty string clears the name and clears documentation, and the command layer honoured that — but both wire seams read those fields with a blank-stripping reader that turned `""` into `null`, the same signature's sentinel for *leave unchanged*. So a lone `{"documentation": ""}` tripped the "no fields to update" guard naming the field just supplied, and a mixed `{"name": "X", "documentation": ""}` silently kept the old documentation and reported success. Both seams now take the empty-preserving readers already in use for `specialization`, so the standalone tool and `bulk-mutate` cannot diverge. `update-element` deliberately keeps stripping — its schema makes no empty-clear promise. One accepted delta: a whitespace-only value is now stored verbatim where it was previously dropped. The approval card follows, since a proposed blank name was previously discarded exactly as if the key were absent.
- **`update-relationship` now tells you what the relationship holds and what it joins.** Its description's most precise sentence was a confession — *"documentation and properties are NOT echoed even when set"* — because the mapper behind the response hardcoded four fields to null. So a caller could clear documentation through the standalone tool or set it through `bulk-mutate` and be told only that the call succeeded, which made the empty-string clear above only half-reported: an omitted key and a key holding `""` are indistinguishable to an agent that cannot see the model, and the omission reads as *unchanged*. The mutating paths — the standalone tool and the `effectiveRelationship` a bulk operation carries — now report `documentation` and `properties` re-read from the model after the write, preserving a cleared value as an empty string exactly as `name` already did, and resolve `sourceName` / `targetName` so a caller is not handed back two opaque ids. The endpoint names are read after the write too, so an operation that renames an endpoint earlier in the same `bulk-mutate` call is reflected in the relationship's own report. The read tools are deliberately unchanged: they keep normalising empty to null and keep omitting the endpoint names, which would otherwise grow every row of every list they return.
- **`fields:"full"` on the relationship read tools now delivers the fields it names.** `RELATIONSHIP_FULL` has always listed `documentation`, `properties`, `sourceName` and `targetName`, and the mapper behind `get-relationships` and `get-view-contents` guaranteed all four were absent — so `full` was byte-identical to `standard` there apart from `specialization`, and the preset was an unfulfilled promise rather than a verbose option. The shared mapper now populates them on the read side too, still normalising empty documentation to null, and the preset decides who sees them: a default response is unchanged field for field. Two things fell out of it. A depth-3 expansion put its nested relationships into the response as the DTOs themselves rather than through the field selector, so their width was governed only by `@JsonInclude(NON_NULL)` — harmless while the mapper hardcoded nulls, a silent widening at every preset the moment it did not; those rows are now field-selected like every other relationship payload. And `search-relationships` had a second, near-identical relationship mapper of its own, which the parameterised one made redundant: the two were compared field for field on a rich relationship and on a bare orphan before either was deleted, and search now shares the single mapper its callers were always meant to. `get-relationships`'s `fields` description also stated only that it governs depth-1+ element expansion, never that at depth 0 it selects the relationship's own fields.
- **`lineStyle` is now rejected on a connection instead of being dropped in silence.** The parameter was parsed, counted as a requested change, never validated, silently discarded — and the tool answered success. Re-measured against Archi 5.10, an ArchiMate connection has **no settable line style**: the property panel's filter excludes ArchiMate connections, the Format Painter skips the line-type copy for them, the ArchiMate figures hardcode their dash per relationship type and never consult the model, and the metamodel carries no connection line-style attribute at all. The parameter is now refused before any other connection styling check, so the refusal is value-independent, and the correction names the idiom that does work (`lineColor` + `lineWidth`). Applies on all six paths that reach a connection. A connection's dash is derived from its **relationship type** at render time and always was; view-object `lineStyle` is unaffected.
- **A connection endpoint that is itself a relationship gets a reason instead of `INTERNAL_ERROR`.** ArchiMate permits a relationship whose endpoint is another relationship, and no view object can reference such an end. Naming one in `add-connection-to-view` failed from both connection prepares by two different routes — one dereferenced the null its endpoint resolver answered for a non-element end, the other cast that end to an element outright — and both surfaced as an internal error carrying nothing the caller could act on. They were also easy to mistake for one bug: the two throw different exceptions and are caught in different places, so one arm reported "Error adding connection…" and the other "Error executing bulk mutation", and fixing either alone left the other looking fixed. The near-duplicate match check both prepares carried is now a single validator; a non-element end cannot match and falls to the `RELATIONSHIP_MISMATCH` that was always the right answer, whose detail line names the relationship's real ends so the offending shape can be looked up.
- **A bulk `move-to-folder` reports `action: "moved"`, and the two placement tools report `"placed"`.** `move-to-folder`, `add-image-to-view` and `add-view-reference-to-view` had no entry in the action-verb table and fell through to the create-shaped default, so a move and two placements each described themselves as a creation. The default now covers only tools that genuinely create.
- **First-time HTTPS enablement no longer fails on roughly one generation in 4096.** The generated keystore password is 16 characters of Base64 URL encoding, an alphabet that includes `-`. That value was handed to the `keytool` **launcher** as a command-line argument, and the JDK launcher pre-scans its arguments and consumes any one beginning with `-J` as a JVM option before keytool's own parser runs. A password that happened to start with `-J` was therefore stripped of those two characters, and its remaining 14 handed to the JVM as a main class name — failing with a message that named a random token and mentioned neither certificates nor passwords, unattributable by construction. The same failure folded 14 of the 16 password characters into the exception, which the preference page logs to the workspace log. The password is now passed **in the child process's environment** instead, so no password value reaches the launcher's argument pre-scan at all: the whole class of launcher-option collisions is closed structurally rather than one case filtered. Entropy is untouched — same random bytes, same alphabet, no rejection sampling — so existing keystores keep opening.
- **`create-relationship` names what a duplicate joins.** The tool resolves its source and target **names** on the create arm, and the approval gate consumes them to name the endpoints on the card. The duplicate-detection arm rebuilt its result field by field and hardcoded the four optional fields to null, so one tool answered the same question two different ways depending on whether the relationship happened to exist already: a new relationship came back naming what it joined, and a duplicate came back with two opaque ids — with an approval card degrading to raw ids and no signal that it had.
- **A missing required parameter now names the spelling you supplied.** The same identifier is spelled several ways across the surface — an element's model id is `id` on `update-element`, `elementId` on `add-to-view` and `delete-element`, `objectId` on `move-to-folder`; a relationship's is `id` or `relationshipId`; a folder's is `id` or `folderId`. No tool schema declares `additionalProperties`, so a key spelled a sibling tool's way is dropped in silence and the caller is told a required parameter is missing while holding it under a name one synonym away — and inside `bulk-mutate` that costs the whole call, since the failure is re-wrapped over the entire operation list. The error now names the near miss, which teaches the accepted spelling and covers every colliding spelling at once rather than adding permanent alias surface. A missing-parameter failure inside `bulk-mutate` also carries its **own** correction now, instead of falling through to the generic "fix the failed operation and retry the entire `bulk-mutate` call".
- **`update-view-object` reports the label a group now holds, not the one it held before.** `elementName` was built from a prepare-time read, so every group rename came back naming the old label — not only the clears that made the defect visible. Both sites now resolve the post-write value, and the fix is scoped to groups deliberately: a note's `text` writes its content and never touches its name, so applying the same substitution there would report a note's content in a field that means "name".
- **A note re-fits its height to new text instead of clipping it.** Auto-fit was create-time only: `add-note-to-view` sized a note's height to its wrapped content whenever `height` was omitted, and `update-view-object` then kept the stored height however the text changed — so replacing a short body with a long one silently clipped it, and `assess-layout` prescribed the very thing the caller had already done ("omit the note height so the server auto-fits"). A conversion run measured a note auto-fitted to 102 px, re-texted to content needing 294 px, and returned 102. Both update prepares now re-fit, reusing the same `ElementSizer` measurement the create path uses, so the same content at the same width resolves to the same number on either path. The fit fires for a **note** when `height` is absent and the request supplies `text` or `width` — the two inputs that change the wrap — so a pure move never resizes, and supplying `height` still pins a fixed size. It is symmetric rather than grow-only, because nothing distinguishes a height an author pinned from one an earlier fit produced; the single piece of negative provenance is honoured at **both** ends of the clamp — a height outside [80, 600] cannot have come from the fit, which clamps into that range, so the floor is the lesser of the default and the note's current height and the ceiling the greater of the cap and that same height, and a clamp never moves the height in a direction the content does not justify. Groups and legends stay out: a group's height must also contain its children, so fitting one to its label could shrink it away from its contents, and Archi sizes a legend from its layout options rather than its text. The fit's fire signal is OR-ed into `boundsModified`, so the parent-fit cascade still runs when no bounds field was passed — otherwise a note growing inside a group hangs outside it with the group reporting nothing. The published `noteClipCount` remedy changes with it: re-send the note's `text` (or its `width`) with `height` omitted, since omitting `height` on its own is not a request the tool accepts — at least one field must change. Where the runtime has no SWT display to measure with, the update path degrades to the height the object already holds rather than failing an otherwise-valid text edit; the create path keeps its loud failure, having no height to fall back on.
- **`bulk-mutate`'s `create-element` no longer discards the `source` map.** The arm read `properties` and never read `source`, so every element created in bulk was silently stripped of its provenance while the sibling `create-relationship` arm, seventeen lines below, merged it correctly. The tool advertised the capability, reported the write as succeeded, and did not perform it; one conversion run measured the loss at 75 elements and repaired it with 75 hand-written update calls. Both map reads now fold through the same shared helper the relationship arm already used, which preserves its precedence rule: a literally prefixed `properties` key loses to the `source` entry of the same name. The real gap was coverage — `create-element`'s provenance was pinned on no path at all, and the relationship capability it mirrors is pinned by five tests that skip in every lane because a runtime-availability guard disarms them. Six pins are added, written bare so they actually execute: direct, batch-queued, approval rebuild, bulk, bulk with back-references, and the majority path where no `source` map is supplied at all.

- **Eight tools now say when an element's `documentation` and `properties` are absent — and four stop promising they are not.** An element that carries neither reports neither, deliberately: a concept's documentation defaults to the empty string, so without the collapse every element row would ship `"documentation": ""`. Nothing said so. Worse, four surfaces claimed the opposite in an unconditional "returns …" list — `get-element`, `search-elements` and `get-relationships` in their `fields` preset description, and `update-element`, which scoped the third field ("specialization only when set") and left the two beside it reading as guaranteed. `get-relationships` was the sharpest instance in the tree: one description string documented the omission rule for a relationship and left it unexplained for an element. The other four — `get-view-contents`, `get-or-create-element`, `search-and-create` and `create-element` — published the fields and said nothing. All eight now carry one wording, asserted off the live registry across both served surfaces a client reads: the tool description and the input-schema property descriptions. `bulk-mutate` is deliberately excluded, since it already points at the standalone tool of the same name. `update-relationship`'s contrast — that clearing documentation returns an empty string rather than omitting the field — deliberately does **not** travel: it is false of every element tool, because `update-element` strips a blank documentation before the command sees it and so cannot clear one at all. The guard asserts that clause absent on every element surface and present on the one that earns it, so the absence check cannot go vacuous.

- **`create-relationship` describes a fresh create the same way whether or not the call happened to be the first.** The fresh arm built its DTO by hand and mapped an empty `documentation` to null, so the key was dropped; a create matching an existing relationship routed through the mapper's mutation flavour, which deliberately preserves `""`. Same tool, identical inputs, two differently-shaped answers decided by nothing but ordering — and an agent that cannot see the model reads an omitted key as "unchanged". The fresh arm now passes the value it read through unchanged, so both arms report what the relationship actually holds. One edit covers the immediate, batched, approval and all four `bulk-mutate` paths, because they all return the same prepared DTO. The `properties` collapse is unchanged on both arms: an emptied collection stays absent, which is settled the other way on purpose. The tool description said `documentation only when it is non-empty` and now says what the code does.

- **An approved `bulk-mutate` is refused once the batch its operations were resolved against has been rolled back.** `bulk-mutate` is one of fourteen tools whose approval path applies the compound the human already reviewed rather than re-running the pass — deliberately, since re-running a whole bulk could produce something other than what was on the card. For those fourteen the tracked set the staleness guard vets is the *only* check there is: with no rebuild, there is no rebuild-throw to fall back on. Thirteen of them built that set by walking the compound's typed child commands. `bulk-mutate` did not — it fingerprinted each operation's own new entity id, which resolves nowhere at propose time, so a bulk of creates produced an **empty** tracked set and the guard passed without checking anything. Measured: with a container queued by an enclosing batch and that batch then rolled back, approving reported `action: "placed"` with a real-looking `entityId` for a view that gained nothing. It now joins its thirteen siblings on the shared walk, which gained arms for the three placement commands — tracking the **container being placed into**, since the object being placed does not exist yet — plus recursion into nested compounds, without which a wrapped placement was skipped. Both routes to the hazard refuse with a message naming the object that went away, and reviewed-or-reject is preserved. A nested bulk whose enclosing batch **commits** still approves. The three placement arms reach `bulk-mutate` alone — they are constructed in three prepare methods whose only callers are the standalone add tools and `bulk-mutate`. The nested-compound recursion reaches one tool further, and closes the same class of hole there: `auto-connect-view` wraps each connection it creates in a placement guard that is itself a compound, so its `AddConnectionToViewCommand` children were never walked and its tracked set was the view id alone. It now tracks both endpoints of every connection it draws, matching what the single-tool `add-connection-to-view` has always tracked — so deleting an element mid-review reject-stales the frozen compound instead of attaching a connection to a detached object.

- **`auto-route-connections` routes a repeated `connectionIds` entry once, and says it routed once.** The filter appended the resolved connection per input entry with no uniqueness check, so `["c1", "c1", "c2"]` produced three entries for two connections. The routing pipeline downstream is index-parallel rather than id-keyed, so the duplicate was routed a second time and recorded its corridor occupancy twice — and corridor occupancy feeds the A* cost of every connection routed after it, so a repeated id perturbed the router's output rather than merely being redundant. It also inflated `connectionEdgeCoincidenceCount`, which is rating-bearing, and `coincidentSegmentCount`, whose self-pair guard compares list position rather than connection id and therefore could not see the duplicate at all. Measured, the response said `connectionsRouted: 3` for two connections — a count a caller who cannot see the canvas has nothing else to check against. The ids are now deduplicated first-seen on the filter's input, which also stops a repeated *unknown* id being named twice in the `CONNECTION_NOT_FOUND` warning. Silent, as `arrange-groups`' `groupIds` and `get-element`'s `ids` already are; no new warning code. `auto-layout-and-route` is unaffected — it takes no `connectionIds` parameter and routes off a model-derived list.

- **A `source` key that collides with a `properties` key is refused instead of quietly winning.** The merge that folds a `source` map into `properties` seeded the caller's own properties first and then wrote each prefixed source entry over the top unconditionally, so `properties: {"mcp.source.file": "A"}` with `source: {"file": "B"}` stored `B` and discarded `A` — no error, no documented precedence, and no way for a caller who cannot see the model to discover which of the two values survived. A key that already carried the prefix fared worse: `source: {"mcp.source.tool": "x"}` was prefixed a second time and stored as the property `mcp.source.mcp.source.tool`. Both are now refused with `INVALID_PARAMETER` naming the offending key and the correction to make, on the same grounds an unusable image filename is refused rather than coped with: a silently-mangled provenance key resurfaces later as an attribution nobody can trace. The rule is stated on all five surfaces that describe the merge — both create tools' descriptions, both `source` input-schema descriptions, and the README — and reaches `create-element` and `create-relationship` on their standalone and `bulk-mutate` paths alike, because all four call one helper.

- **A `bulk-mutate` back-reference to a note it just created no longer destroys the note with it.** `add-note-to-view` is published among the back-referenceable create tools and validated as one, so a `$0.id` naming a note passed validation and resolved to the note's real id — and then failed anyway. `executeBulk` keeps one registry per back-referenceable create tool and six of the seven were registered; the note registered nothing, so the container lookup answered null and could not have answered otherwise, since it returns an `IDiagramModelContainer` and a note is not one. The arm fell through to the id path, where a note whose add command has not executed yet is still detached. Under the default all-or-nothing semantics the refusal destroyed the note creation too, and the diagnostic named a resolved GUID the caller never typed while prescribing `get-view-contents`, which cannot answer for an object that does not exist yet. Seven of seven are registered now, through the same raw-object seam the note's prepare already returned, and a note-typed lookup answers only where the container lookup misses. A second lookup is admissible here for one permanent reason rather than a judgement call: the parent answer for a note is **always no**, so the "works as a parent, fails as a target" drift a split once opened for groups has no shape to take — a batch-created note is still refused as a `parentViewObjectId`, and the five parent call sites keep their compile-time container guarantee rather than trading it for five runtime checks. Opening the path also made a dormant gap live and made it ours: `add-note-to-view` never recorded its pending parent, so the parent-fit cascade resolved null for a detached note and silently declined to grow the group around it, while the identical operation on a group target cascaded correctly. It records it now. The not-found advice on **both** sibling prepares — `update-view-object` and `update-view-connection` — now names the back-reference case instead of prescribing `get-view-contents` as the only route, and the two strings are asserted against each other rather than each against a substring, because drift between duplicated literals is what put them out of step. Recovering the caller's literal `$N.id` in that message is declined with its reason: the token is replaced before the arm runs, so recovery means a new mechanism for a message. Opening it also makes an earlier fix real. The note-height re-fit on the direct update prepare shipped as a declared **forward guard no caller could reach**, and mutation measured exactly that: neutralising it turned nothing red across 582 tests. It is now a live, pinned path, and neutralising it turns one test red — the same test that is simultaneously the measurement that it was dead before.

- **A refusal listing many failures carries what they all say once, instead of once per row.** Reporting every bad entry at once exists to spend one round-trip instead of several, and it was giving back most of that saving in bytes: the response grew with how many entries were wrong *in the same way*, not with how many distinct things were wrong. Replaying a stale layout through `apply-positions` makes every id fail identically, and at the fifty-row cap the refusal was **35,710 bytes**, of which about two-thirds was one 477-character sentence of back-reference advice repeated fifty times. `bulk-mutate` was worse and had no cap at all: a hundred and fifty operations naming an unsupported tool each republished the whole twenty-eight-tool list in their `message`, for **112,866 bytes** — the largest repeated string in the tree. A long ending shared by every row of one error code is now published **once**, beside the `failed` array, and the rows reference it by error code: `corrections` and `messages` hold the shared strings, `correctionRef` and `messageRef` name them. Measured on the wire, before and after: `apply-positions` at the cap **35,710 → 12,738** bytes and at nine thousand entries **35,888 → 12,916**; `bulk-mutate` at its 150-operation ceiling **112,866 → 39,180** for malformed operations and **96,495 → 26,523** for operations that fail validation; ten operations **9,376 → 4,990**. Nothing is truncated — a split row keeps its own head under the field's own name, and the head followed by the shared string is byte-for-byte what the row carried before. A `message` is never taken away whole, because it is the row's own account of what went wrong and two entries can genuinely fail in identical words; only a trailing clause shared with its siblings is ever split off, and only at a sentence boundary, so a client that never resolves the reference still reads a complete sentence rather than a fragment. Every row stays self-describing — whether a key is present depends only on that row's own content, never on the row before it — so rows remain independently parseable. The rule declines where it would not pay: a string shorter than the keys replacing it, or one only a single row carries, stays on the row, and a refusal naming one failure is byte-identical to what it was. One projection builds the rows for both tools and all four places they appear, including the `continueOnError=true` response where failures arrive beside successes, so the two cannot drift apart. This also corrects a pin that had ruled the per-row copy "the irreducible amount — that is the data": it was judged on a three-row fixture, where the list looked like data; scaled to the ceiling the same reading licensed tens of kilobytes of one sentence.

### Features

- **Connection labels no longer crowd on dense auto-laid-out views.** When `auto-layout-and-route` runs the ELK layout, it now reserves space for each connection label's estimated text width while it spaces the elements, so labelled edges keep enough room for their labels instead of letting them overlap. The estimate uses the same width yardstick the layout-quality check already measures labels with, so the spacer and the detector agree. Labels you have deliberately hidden (`showLabel` off) — and edges with no label — reserve nothing, so manual label suppression stays an effective way to de-clutter a busy view. Default behaviour for label-free views is unchanged. Verified on a crowded view: connection-label overlaps cleared (2 → 0) after a re-layout, with label-free elements left compact rather than over-spread.

- **Connection Label Offset lifts a Middle label off its own box (Archi 5.10).** Archi 5.10 adds a per-connection "Label Offset" — a Centre-plus-eight-compass anchor that nudges a Middle-positioned label off the connection's midpoint. `auto-route-connections` and `auto-layout-and-route` now use it: when the best along-path label position still leaves a Middle label rendered *on* one of its endpoint boxes, the router scores the eight perpendicular directions and applies the first one that lifts the label clear, choosing the direction from the label's hosting segment so a Z-routed connection gets the right side tried first. The along-path label-position optimizer is itself now **own-endpoint-aware** — it penalises a candidate position that would drape a label over its own source or target box, so it picks a cleaner spot along the route first and the offset stays a fallback for when no along-path position is clean. On `auto-route-connections` the offset is the *only* channel that can clear this bleed, because a hand-tuned view keeps its positions; on `auto-layout-and-route` it is a last-resort fallback after element re-spreading. The offset is metric-neutral (it moves the rendered label without changing the route geometry the assessor scores). **Runtime-guarded:** on Archi 5.7, with no Label Offset feature, the step is a silent no-op. One caveat to verify in the editor, not an export: Archi's PNG/SVG export renderer does not draw the offset — only the live editor and the Properties panel show the lift (use `get-view-contents`, below, for a programmatic read-back).

- **`get-view-contents` reads back a connection's Label Offset.** `ViewConnectionDto` gains a nullable `relativePosition` field (the Archi 5.10 "textRelativePosition" anchor), so an agent can confirm an offset actually landed — the programmatic channel that neither `assess-layout` nor `export-view` exposes. The field is omitted (`NON_NULL`) when the platform lacks the feature or the anchor is the un-offset default (Centre), so the wire format is byte-identical on Archi 5.7 and for any connection without an explicit offset.

- **Pending Approvals cards gain a `Copy JSON` button.** Each proposal card in the **Pending Approvals** dock now carries a secondary, left-aligned **`Copy JSON`** button that copies the proposal's full structured payload to the clipboard — `proposalId`, `tool`, `status`, the server-generated `description`/`effectDescription`, `currentState`, `proposedChanges`, `validationSummary`, `createdAt`, and the optional agent `intent` — for pasting into an issue or log, or inspecting the complete change before deciding. It is read-only and side-effect-free: the proposal stays pending, the model is untouched, and the internal session-routing key is never included.

- **Nesting a child auto-recedes an unauthored container fill to a backdrop.** When `add-to-view` or `add-group-to-view` places a child *inside* a container element or group whose fill colour you have not explicitly set, the parent's fill now automatically recedes to a subtle light backdrop (`#F4F4F4`) so the nested content reads as foreground-on-depth instead of a flat single-colour block — the standard "the container is the canvas, the children are the figures" convention, applied without the agent having to colour it by hand. The recession is **provenance-gated and idempotent**: only a container with no author-set fill is touched, an already-receded parent is left alone, and an explicitly coloured container is sacrosanct. The root view is excluded structurally, and the recede rides the placement as one atomic undo unit. Opt out per call with `recede: false`. A new informational `assess-layout` signal (`containerFillEqualsChildCount`, below) backstops the case where a container's *authored* fill still equals a child's. Default behaviour for elements placed at the top level (no container parent) is unchanged.

- **A view object can anchor to a container and follow it as it grows or moves.** `update-view-object` gains optional **anchoring**: a note or child records an anchor `{anchorTarget, anchorEdge, dx, dy}` so its position is resolved from the target container's *current* bounds at commit time instead of a frozen absolute snapshot. Edge `below` (default) tracks the target's growing bottom; `above` / `right` / `left` track the corresponding edge. When a later mutation moves or grows the target, every object anchored to it is repositioned **within the same undo unit** — so the flagship note-below-a-group stays aligned as the group grows, instead of silently drifting the way a captured absolute position would. Target and object must share a coordinate space (same parent); self-anchors and cross-space anchors are rejected on set and skipped in the cascade. `add-note-to-view`'s content-relative placement now delegates to the same edge resolver (byte-identical rounding), and the resolved anchor reads back on the `update-view-object` result. Existing calls that pass no anchor are unchanged.

- **`export-view` stamps each render with the model's mutation version, so a stale image is detectable.** Every `export-view` response now carries the model's monotonic mutation counter as `modelVersion` (inline mode: a top-level field; file mode: in `_meta`), the same counter `assess-layout` and the other tools already report. It is a decimal-encoded integer — **compare it numerically, not as a string**. Against a later `assess-layout` `_meta.modelVersion`: if the export's `modelVersion` is numerically lower, the model changed after the render and the exported image is stale — re-export before relying on it for a visual close-out. Previously the inline formats stamped no version and the file mode stamped `null`; the route geometry and image bytes are unchanged. This closes the verification gap where an agent could assess a freshly-mutated model against a render taken before the mutation.

- **`bulk-mutate` gains a view-scoped `set-view-label-expression` op for stamping one label template across a whole view.** A new `set-view-label-expression` operation applies a single `labelExpression` template — e.g. `${name} ${property:evidenceMark}` — to every eligible diagram object on one view in a single atomic command, collapsing what used to be one `update-view-object` call per object into one operation per view (the common case when an agent retro-fits an evidence-mark or status glyph onto an existing diagram). It is **retroactive, type-filterable, and idempotent**: the default scope is ArchiMate **element** objects, and an optional `objectTypes` array widens it to notes and groups; a non-blank-name guard skips any object whose name is blank when *setting* a template (so a placed object never renders a half-empty glyph), but is bypassed when *clearing* (an empty/blank expression removes the override everywhere). The whole sweep is one GEF command, so it is a single undo unit, and the per-op result reports `appliedCount` / `skippedCount`. It is a `bulk-mutate` operation, not a new top-level tool — the served `bulk-mutate` description advertises it automatically. Verified live on a real view (11 applied / 1 skipped, the glyph renders, a note shows no ghost token, and undo restores the model byte-for-byte).

- **The router now clears an off-face terminal hug — a connection that leaves a face then runs parallel hugging it.** When a terminal route departs an element face and then runs a pixel or two *parallel* to that same face before turning, the result reads as a connection grazing the box it attaches to. `auto-route-connections` (and `auto-layout-and-route`) now push that first trunk clear of the face, in **both** routing modes. In the full-route pipeline, the terminal egress-clearance pass replaces an over-strict, wrong-axis "never reduce the vertical parallel-gap" guard with a **dual-axis healthy-floor** model: it enforces a healthy minimum parallel gap (`HEALTHY_PARALLEL_GAP_PX`, 15 px) on *both* the vertical and horizontal axes, so a healthy-to-healthy tightening is allowed while a push into the danger zone stays blocked — and a short-run sub-10 px micro-hug of an element's *own* face (which the foreign-edge overlap test was too coarse to see) is now caught by an own-face short-circuit plus an off-face-stub keep-signal that mirrors the assessor's 8 px oracle. In `mode: "terminals-only"` — which renders centre → L-bend → trunk, so the hug is the trunk *after* the L-bend and the full pipeline's pass cannot be reused — the same healthy-floor is mirrored as pure geometry in the routing pipeline, with a per-side orthogonality backstop that declines any lift which would introduce a diagonal. Detection fires at the 8 px oracle threshold (so an already-clearing terminal is byte-identical) and pushes to 15 px. The work is metric-neutral where nothing hugs, and it drives the new `offFaceParallelTerminalCount` signal (below) to zero. Verified live on a dense view: off-face parallel-terminal hugs cleared (3 → 0), the live geometry matching the headless route byte-for-byte.

- **The router dissolves a coincident same-face hub port.** A downstream terminal stage can pull one connection's source-exit and another's target-entry on the *same low-degree element face* onto that face's centre, collapsing two terminals onto one perimeter port — two edges that appear to leave a single point (the `coincidentFacePortCount` defect the assessor now sees). `auto-route-connections` (and `auto-layout-and-route`) add a gated **final spread pass** in the full-route pipeline that groups terminals per face, clusters them by along-face slot, and for each collision moves whichever terminal *can* move to a free on-line slot (swapping the anchor when the one tried is an immovable face-hug), avoiding every other terminal already on that face. Every move is gated — element degree below the hub threshold (a dense hub keeps its own distribution), the terminal on the perimeter, a provable collision, a free slot at least the 12 px distinguishability floor from every occupied one (else the collision is accepted rather than forced), the relocated stub staying perpendicular, and zero new edge or obstacle crossing — so the pass is a **byte-identical no-op except on an actual collision** and needs no routing-corpus re-baseline. Verified on the organic hub view: coincident ports fan apart with no crossing rise.

- **`auto-route-connections` surfaces a layout-bound egress-lift decline honestly instead of silently.** When the router generates an off-face terminal egress lift but then rolls it back — because applying it would narrow a parallel-connection gap below the 15 px healthy floor — the residual hug is *layout-bound*, not a routing bug the tool can fix on its own. The response now reports the rolled-back count as an `EGRESS_LIFT_LAYOUT_BOUND` structured warning (alongside the free-text warning) plus a matching layout-bound `nextSteps` entry that names spreading the elements sharing the departed face, rather than declining without explanation. It is **signal only** — the routing decision, the routed geometry, and the assessed rating are all unchanged. `assess-layout`'s off-face remedy (above) cross-references the same warning so detection and remediation advice stay consistent.

### Layout Quality Assessment

`assess-layout` learns to see several label/visual defects it was previously blind to, so the agent can catch them programmatically instead of only on a human's screen — plus a new hub-to-neighbour crowding signal, two routing-rating-affecting route-quality detections, and a coverage map that makes "we checked it and it's clean" distinguishable from "we never looked". Except where noted, these do not change the overall rating.

- **A connection label rendered on its own endpoint box is now flagged.** The label-overlap detector previously excluded a connection's own source and target from the overlap test (so a label always "grazing" the box it attaches to would not false-positive), which left a real defect invisible: a Middle label that bleeds substantially onto its endpoint. It is now flagged when more than 30% of the label's render-calibrated area falls on its own endpoint — asymmetric by design, so light grazing is tolerated while a clear bleed is reported, naming the more-overlapped endpoint. This is the detection half of the Label Offset fix above. Three companion rules close the cases the area-fraction alone missed: a **box-coverage** test flags a label that blankets a *tiny* endpoint box (e.g. a 14×14 junction sitting almost entirely under a label registers low label-area overlap but ≥ 60% box coverage); a **short-segment** promotion lowers the bar to 15% when the label is wider than the first/last segment it anchors to — the long-source/target-label-on-a-short-segment bleed the assessor used to under-count; and a **junction** rule drops the own-endpoint bar to a near-zero 5% when the endpoint is a Junction, because a junction renders as a solid dark shape with no readable interior — so the box-grazing tolerance a normal box earns is wrong for it, catching an *oversized* junction (e.g. the 120×55 default) grazed by a label that the box-coverage rule, which only fires on a tiny junction, would miss. The detector is also now **offset-aware**: a Middle label that has already been lifted clear by an Archi 5.10 Label Offset is not re-reported as bleeding.
- **Label width is render-calibrated.** Connection-label overlap detection now widens the estimated glyph box by the same 1.35× render-versus-measure factor already used for element-label truncation, because Archi renders glyphs wider than the raw estimate and short, tight segments were under-flagged. This is detection-only — the routing-side label-width *reserver* deliberately keeps the raw estimate, so the detector is intentionally the more render-accurate of the two. Suppressed labels (`showLabel` off) correctly reserve and flag nothing, so manual label suppression is no longer penalised with phantom overlaps.
- **Clipped notes are detected (informational).** A new `noteClipCount` / `noteClipDescriptions` signal flags a note whose text needs more height than its box provides — typically an explicit `height` that defeats the server's auto-fit. It uses the same SWT text measurement as the note auto-fit path, so it fires exactly on the auto-fit-defeating case. Remedy: omit the note `height` to let the server fit it, raise the height, or reduce the font size. No rating impact. *(Remedy superseded in v1.9.0, where the fit also runs on the update path: re-send the note's `text` or `width` with `height` omitted.)*
- **Image-overlap detection is made accurate (informational).** The image-sibling-overlap detector now also examines **specialization / profile icons** (resolved from the element's profile when the view object carries no custom image), not just custom images, and sizes the image rectangle from the archive's **true pixel dimensions** instead of a fixed 24 px assumption — so it stops both missing real icon overlaps and mis-measuring large images. No rating impact.
- **Hub-to-neighbour crowding is now measured, and a crowded resize can no longer rate `good` (rating-affecting).** A new `hubNeighbourClearanceMin` field reports, in pixels, the smallest clearance between a hub element's edge and the row of spoke neighbours packed against it — measured only on a face carrying at least three overlapping spoke neighbours, so an ordinary element never registers. It exists because the previous metrics had no way to see the failure mode where enlarging a hub to fix port distribution crowds its neighbours: a layout could read `good` on every existing metric while rendering tighter than an alternative that scores only `fair`. A clearance below the 60 px crowding floor now caps the layout tier so a crowded hub cannot rate `good`; a clearance at or above the floor — and the `-1.0` "no measurable hub" sentinel — leave the rating untouched, so no previously-clean view changes tier. The field is appended to the result (older clients ignore it).
- **`assess-layout` next-steps diagnose a saturated container-nested hub.** When corridors are near-saturated (`corridorUtilisationScore ≥ 0.9`) with edge-coincidence pressure and hub-port quality is *not* the limiter, `nextSteps` now emits a single diagnostic step that supersedes the generic spacing-inflation advice — because spacing inflation is the wrong lever there. The step points at `detect-hub-elements` and branches on the new clearance reading: a sparse hub (clearance ≥ 60 px) gets the *enlarge-then-re-route* lever; a dense hub (clearance below the floor) gets the *revert-to-normal-size, re-place with ELK, then full re-route* lever; and the un-measurable case presents both, deferring the choice to `detect-hub-elements` and a render check. Every branch carries the render-authoritative caveat — the rating alone can score a crowded layout `good`, so confirm with `export-view`.
- **The off-face terminal-hug next-step is now router-consistent and honest.** When `assess-layout` reports an `offFaceParallelTerminalCount` hug, its remedy branch no longer over-promises a perpendicular re-route it cannot guarantee. It gives a confident *layout* fix only when the local corridor is below the healthy floor; otherwise it defers to `auto-route-connections` (cross-referencing the router's new `EGRESS_LIFT_LAYOUT_BOUND` warning, below), because the router may legitimately decline the lift to protect a parallel-connection gap; and on a *contested* hub face (two or more connections sharing it) it names **spreading the connections** rather than a plain widen. Signal/description only — no rating changes.
- **Connections routed through a note or image are flagged, and any crossing nudges the routing rating to `good` (rating-affecting).** A new `connectionThroughNoteCount` / `connectionThroughNoteDescriptions` signal flags a connection whose route runs straight through a Note's box or through an element's rendered image rectangle (the "the line crosses the caption/legend" defect). Notes are deliberately excluded from the element pass-through scoring set, and for an image-bearing element this tests the rendered image *rectangle* — which can overhang the element box — so it catches clutter the box-based `connectionPassThroughs` (Tier-1R) misses. It is a Tier-3R routing detection with **binary presence** semantics: a single crossing caps the routing tier at `good`, and several crossings rate the same (one line through a note is already jarring; more is not "worse" for tiering). Where a route trips both this and the box-based pass-through, the routing tier takes the worse of the two, so the Tier-1R pass-through dominates and there is no double penalty. A visual on a connection's own endpoint or container is not flagged. Counted per connection × visual. Reroute the connection or move the note/image clear.
- **Non-orthogonal interior (mid-route) segments are flagged and rated (rating-affecting).** A new `nonOrthogonalInteriorSegmentCount` / `nonOrthogonalInteriorSegmentDescriptions` signal generalises `nonOrthogonalTerminalCount` from the source/target segments to the *interior* of a route: any segment more than ~5° off horizontal/vertical that sits between the two terminal segments. It is a Tier-2R routing detection, ratio-bucketed identically to its terminal sibling (a low interior-diagonal-per-connection ratio rates `good`, a high one `fair`); the two are separate breakdown entries, but the routing tier combines them by the worse, so a connection diagonal at both a terminal and an interior segment is capped once. Counted per connection. Re-run `auto-route-connections` for clean orthogonal paths.
- **Redundant (collinear, removable) bendpoints are detected (informational).** A new `connectionRedundantBendpointCount` / `connectionRedundantBendpointDescriptions` signal flags a bendpoint that lies on — and between — its two neighbours along a *horizontal or vertical* run, so removing it would not change the rendered orthogonal route (the "many unnecessary bendpoints / wobbles" defect). The test is deliberately **axis-aligned** (a triple's `min(spanX, spanY)` within a 0.5 px reconstruction-noise epsilon), not any-angle, so it matches the router's exact `removeCollinearPoints` contract — the agent's only remediation lever: a near-collinear *diagonal* micro-jog is not flagged, because removing it would diagonalise an orthogonal segment. Router-pinned **terminal egress-stub ports** (a first/last bendpoint on its element's perimeter face, held for terminal anchoring / port distribution) are also excluded, because a full re-route never removes them — so a nonzero count is a genuinely collapsible *interior* point. It is counted per redundant point and is distinct from the reversal-based `zigzagCount`. No rating impact. Straighten the route or re-run `auto-route-connections` — `mode: "terminals-only"` now also sweeps these interior collinear survivors (an inserted terminal L-bend that lands collinear with the trunk) while leaving the pinned terminal anchors untouched, so a terminals-only re-route drives the count toward zero.
- **Same-colour container/child "flat-blob" fills are detected (informational).** A new `containerFillEqualsChildCount` / `containerFillEqualsChildDescriptions` signal flags a container whose *authored* fill colour equals a nested child's fill, so the parent and its children merge into one flat single-colour block. It is the backstop for the new auto-recede behaviour (above): because nesting a child now auto-recedes an *unauthored* container fill, this only fires on a blob produced by an *explicit* same-colour fill. Counted per container. No rating impact. Give the container a distinct (lighter) fill.
- **A per-dimension coverage map distinguishes "checked and clean" from "partially checked" from "never evaluated" (informational).** `assess-layout` now returns a `coverage` map keyed by defect dimension, each value one of `checked` (the detector ran and fully covers this dimension's failure modes — so a zero/absent metric means genuinely clean), `partial` (a detector ran but covers only *some* of the dimension's failure modes — a zero/absent metric means only the covered modes are clean, so the uncovered modes must be render-verified before certifying clean), `not-checked` (no detector evaluated this class — absence of a finding is *not* evidence of absence), or `not-applicable` (the view structurally cannot exhibit it). The map is always present on a normal assessment (empty only on degenerate empty/single-element views), is informational and never affects a rating, and lets a done-gate read both `coverage` and `ratingBreakdown` so a dimension counts as "clean" only when `coverage == checked` *and* the breakdown passes. The `partial` level was introduced for two dimensions — `connectionThroughNote` and `labelOverlaps` — whose detectors were known to miss adjacent failure modes. The new graze, label-on-note, and label-on-group detections below close the `connectionThroughNote` gap, so it reports `checked` again. `labelOverlaps`, however, now carries a **contextual** `partial`: the registry still *declares* it `checked`, but on any run where a label is wider than its hosting segment (`shortSegmentCount > 0`) the map downgrades it to `partial`, because a label can crowd a neighbour box while still clearing it geometrically — so the overlap count is honestly zero yet the crowding mode is unverified. A clean run (no over-wide labels) keeps the whole map `checked`. Separately, a new `corridorCentering` dimension ships as a standing **`not-checked`**: it makes explicit that `corridorUtilisationScore` measures multi-occupant corridor *spread*, not whether a single route centres in its corridor versus hugs an edge — a mode no detector evaluates (`corridorUtilisation` itself stays `checked`, fully covering its own scoped question). The `partial` and `not-checked` levels remain defined for dimensions added later.
- **A de-noised headline rating separates accepted ELK cosmetics from real defects.** `ratingBreakdown` now carries `overallExcludingAcceptedCosmetics` — the same overall rating recomputed with the `nonOrthogonalTerminals` contribution removed. Diagonal terminal segments are the straight-line signature of ELK auto-layout and routinely push an otherwise-clean view to `fair`; comparing the two readings tells a real defect from an accepted cosmetic. When `overallRating` is `fair` but `overallExcludingAcceptedCosmetics` is `good`/`excellent`, the `fair` is terminal cosmetics only (run `auto-route-connections` mode `terminals-only` to clear it, or accept it); when the two are **equal**, the rating reflects a real routing/layout defect to fix. It is a **floor, never a lift** — it can only equal or improve `overallRating`, never worsen it — so no existing rating moves down. The headline `overall` value is byte-identical to before (the de-noised value is computed on a copy).
- **`assess-layout` gains a whole-model `scope` for a one-call close-out sweep.** A new `scope` parameter takes `single` (default — unchanged behaviour, full assessment of the one `viewId`) or `all-views`, which assesses every diagram in the model and returns a compact map keyed by view id: each value carries `{name, overallRating, overallExcludingAcceptedCosmetics, elementCount, connectionCount, overlapCount, nonOrthogonalTerminalCount, connectionPassThroughCount}`. It omits violator ids, descriptions, and the per-metric breakdown — one cheap overview instead of one full payload per view — so a final close-out can triage the whole model at a glance, then drill into any `fair`/`poor` view with a single-scope call. `viewId` is ignored under `all-views`; an empty model returns an empty map.
- **A connection grazing (clipping) a note's or image's border is flagged (informational).** A new `connectionGrazesVisualCount` / `connectionGrazesVisualDescriptions` signal flags a connection whose route touches or clips the *border band* of a Note or image — the outer strip that the through-visual interior test (`connectionThroughNoteCount`, above) discards — including a visual too small to inset that a route crosses at all. It is **disjoint by construction** from the interior through-visual count: a single crossing is classified as exactly one of *through* or *graze*, never both, so the two never double-count the same line. Counted per connection × visual. No rating impact. This is the detector that flips the `connectionThroughNote` coverage dimension from `partial` back to `checked`. Reroute the connection or move the note/image clear.
- **A connection label rendered on a note is flagged (informational).** A new `labelOnNoteCount` / `labelOnNoteDescriptions` signal flags a connection *label* (not the route) rendered on a Note's rectangle — the caption/legend collision the route detectors cannot see, because a label is positioned independently of the line it annotates. Counted per label × note, independent of the through-note and graze route signals. No rating impact, and a new `labelOnNote` coverage dimension reports `checked`. Reposition the label (apply a Label Offset or re-run `auto-route-connections`) or move the note clear.
- **A connection label rendered on a group's title band is flagged (informational).** A new `labelOnGroupCount` / `labelOnGroupDescriptions` signal flags a connection label rendered on a visual Group's **title band** — the top title strip — which the connection-label-overlap detector cannot see because it skips groups wholesale as transparent containers. Only the title strip is tested, so a label sitting inside the group *body* is normal and not flagged. Counted per label × group. No rating impact, and a new `labelOnGroup` coverage dimension reports `checked`. Reposition the label or reroute the connection clear of the group title.
- **An off-face parallel-terminal hug is flagged (informational), as the detector half of the router's egress-clearance fix.** A new `offFaceParallelTerminalCount` / `offFaceParallelTerminalDescriptions` signal flags a connection whose terminal route *departs* an element face and then runs **parallel to and hugging** that same face — the first exterior segment travels along the departed face within `OFF_FACE_MIN_STUB_PX` (8 px) of it. This closes a blind spot in the angular terminal check (`nonOrthogonalTerminalCount`): when a route exits a fraction of a pixel off the perimeter and turns to run just beside the face, the exit stub is a sub-perceptible diagonal that the visible-length guard suppresses — so the terminal detector sees nothing, yet the parallel hugging trunk is plainly visible. The departed face is resolved through the same terminal-slot helper the assessor already uses (which attributes a face even for a bendpoint a pixel off the perimeter), not the raw segment angle. Counted per connection, with its own `checked` coverage dimension. **Measurement-only** — the rating-bearing `nonOrthogonalTerminalCount` and its visible-length calibration are untouched, so no rating moves. It is the oracle the new router egress-clearance work (above) drives to zero.
- **A coincident same-face port is flagged (informational).** A new `coincidentFacePortCount` / `coincidentFacePortDescriptions` signal flags an element face on which two or more connection terminals collide onto the *same* perimeter port (within ~1 px along the face axis), so two edges appear to leave one point. This closes a blind spot in the M5 hub-port-quality metric (`hubPortQualityScore`): its per-face guard only scores a face carrying four or more connections, so a face with two or three coincident terminals reads a vacuous `1.0` despite the collision. The detector clusters ports with the same greedy slot sweep the distinct-slot count uses and flags only a cluster holding two or more *distinct* connections, so it neither over-attributes a chain of near-tolerance ports nor mistakes a self-referencing connection for a collision. **Measurement-only** — the count never enters the rating, so M5 and every existing rating are untouched. It is the oracle the new router coincident-port dissolution (below) drives to zero, with its own `coincidentFacePorts` violator key and `checked` coverage dimension.
- **The edge-coincidence detector now enumerates every grazed element (informational).** The M4 edge-coincidence detector previously stopped at the *first* grazed element per connection, so a connection whose trunk hugs the edges of three elements reported only one — and surfaced a single, arbitrary violator. It now enumerates every distinct `(connection, element)` graze: a new informational `edgeCoincidenceGrazedElementCount` (the sum of distinct grazed elements across all connections) and a new `edgeCoincidenceGrazedElements` violator key carrying the grazed *element* ids. The rating-bearing `connectionEdgeCoincidenceCount` and its existing `edgeCoincidence` (connection-id) violator key are **byte-identical** — the per-connection count and violator are now guarded behind a once-per-connection flag — so the rating and the legacy report are unchanged; only the new informational count and element-id key are added.

### Security & Hardening

- **Undeclared and declared non-UTF-8 request bodies are now rejected (HTTP 415).** Two new Jetty handlers, both default-on, close the request-encoding gap. A header-only check rejects any request whose `Content-Type` declares a non-UTF-8 `charset` (e.g. `charset=iso-8859-1`) without reading the body; a second, body-scanning check reads a POST body once (still bounded by the 32 MiB size cap) and rejects it if the bytes are not well-formed UTF-8 — catching a client that sends Windows-1252 / ISO-8859-1 bytes with *no* declared charset, which the header check cannot see. Both render the canonical JSON-RPC error envelope (`-32600`, `httpStatus: 415`). A body that legitimately contains a genuine `U+FFFD` is accepted (the scan tests well-formedness, not a replacement-character literal), and a conformant client — no charset, or `charset=utf-8` — passes through byte-for-byte unchanged. The checks sit innermost in the guard chain (after the size, Origin/Host, and bearer-token gates), each with its own kill switch (`-Darchi.mcp.rejectNonUtf8=false`, `-Darchi.mcp.scanBodyUtf8=false`).
- **Literal HTML/XML entities in a name or label are rejected, not silently stored.** A mutation whose supplied name, label, view-object text, or `labelExpression` contains a well-formed HTML/XML entity token (`&amp;`, `&lt;`, `&#160;`, `&amp;amp;`, …) is now **rejected with a corrective hint** instead of storing the escaped literal — closing the recurring `&amp;` footgun where a value pasted from JSON-escaping muscle memory would render the five-character literal where a human expects a single `&`. The grammar (`&(amp|lt|gt|quot|apos|#[0-9]+|#[xX][0-9a-fA-F]+);`) requires the trailing `;`, so a bare ampersand and non-entity text (`R&D`, `A & B`, `<tag>`, `${name} & ${property:x}`) pass through and are stored byte-for-byte. The rule covers element / relationship / folder / view / specialization / clone names, group and note labels, view-object text, and the `update-view-object` / `set-view-label-expression` `labelExpression`, across `create-*` / `update-*` / `add-*` and their `bulk-mutate` equivalents. Auto-unescaping was rejected as lossy and ambiguous (a genuinely-intended `&amp;amp;amp;` would be corrupted), keeping the plugin a faithful verbatim store.
- **Folder-type placement now fails fast at mutation time.** Placing a concept into a folder whose ArchiMate layer is illegal for it (e.g. a Junction under the Application folder) was previously accepted at the API and only refused later by host Archi when it tried to save the model ("Object is in wrong folder type"). `create-element` and `move-to-folder` now reject it immediately with `FOLDER_LAYER_MISMATCH`. The check delegates to Archi's own `getDefaultFolderForObject` rather than a hand-maintained type→folder map, which closes a real gap — the old map returned no answer for Junction, Grouping, and Location, so those silently skipped validation — and covers relationships for free. `move-to-folder` was previously unguarded entirely; it now enforces the same rule as `create-element`.
- **Duplicate tool-name registration fails fast (developer-facing).** The internal tool registry now rejects a second registration of an already-registered tool name with an `IllegalStateException` at the source, instead of silently accumulating a duplicate that a discovery test caught only after the fact. This affects extension authors registering custom handlers; the normal boot path (each tool registered once) and the clear-then-re-register restart lifecycle are unchanged.

### Fixes

- **Multi-line note and group-label auto-fit no longer grows quadratically.** When a note or group label's `height` is omitted, the server auto-fits the box to the wrapped text. For multi-line content the height grew roughly with the *square* of the line count and clamped at the 600 px maximum, because a single line's height was derived from the measured extent of the whole multi-line block and then multiplied by the line count again. It now measures a true single-line height, so multi-line boxes grow linearly (a 5-line note that auto-fit to 406 px now fits to 86 px; a 10-line note that hit the 600 px clamp now fits to 182 px). Single-line elements, labels, and paragraphs are byte-identical — only multi-line auto-fit changes. Latent since note/group auto-fit was introduced; it only surfaced when a caller omitted the height *and* the text contained explicit newlines.
- **Compound undo preserves child paint order and folder order.** Undoing a compound that deleted several sibling diagram objects or model elements (via `bulk-mutate` or a forced folder delete) restored full membership but scrambled the children's z-order and the model-tree folder order, because each delete captured an absolute insertion index and a compound undoes its members in reverse — so a later delete restored into a list whose earlier members were not yet back. Each removed item now records its surviving-successor sibling at delete time and, on undo, re-inserts directly before that anchor, falling back to the clamped absolute index only for a tail item. Single deletes and the common ascending-order multi-delete are exact; membership and connection integrity are always preserved.

## v1.7.0 (2026-06-18)

Security & hardening release. v1.7 hardens the server's trust boundary for the agent era: Origin/Host header validation **on by default**, **opt-in bearer-token authentication**, the TLS keystore password and the auth token moved out of the plaintext preference store into the **OS keychain** (Equinox secure storage), **request-size / idle-timeout / bounded-thread-pool** guardrails on the embedded Jetty server, **bounded remote-image downloads**, and **idle-TTL eviction** of per-session state — with the full responsibility boundary written down in a new top-level **`SECURITY.md`**. It also adds a human-owned mutation **approval queue** with a dockable desktop review surface (the agent can no longer un-gate itself), **scopes agent undo/redo** to the agent's own edits, and adds a build-from-source + CI safety net for the full test suite. Three tools were removed from the MCP surface — the legacy Zest `compute-layout` tool, and the two agent-side approval-control tools (the gate toggle and approve/reject, now human-only) — so the tool count is **69** (down from 72; resources unchanged at **14**).

### Features

- **Human-in-the-loop approval queue with a desktop review surface.** When approval mode is on, the agent's queued changes appear in a dockable **Pending Approvals** view inside Archi (open via **Window → Show View → MCP Server → Pending Approvals**, or the **MCP Server → `Pending approvals (N)`** menu item, which carries the live count). Each gated tool-call — a whole `bulk-mutate` included — is **one card** whose effect text is **server-generated from the model's own truth**, so you can decide Approve/Reject from the card alone without opening the raw JSON. Cards name what they touch: relationships name both endpoints (`Create ServingRelationship: 'Payment Gateway' → 'Fraud Engine'`), a delete names its endpoints plus the cascade (`Delete …: 'A' → 'B' (cascade: 2 view connections)`), visual changes name the **destination view** (`Add ApplicationComponent 'Mobile Banking App' to view 'Application Collaboration'`), and a `bulk-mutate` card's expanded rows are named per operation. An **icon encodes each concept kind** — `▢` model element, `↔` model relationship, `▣` placed node (visual object), `⇿` drawn connection — and destructive counts are called out in **amber** (colour means destructive only). **`Show changes`** expands a card to verb-prefixed rows (deletes hoisted to the top) with a `Technical details` disclosure of the raw parameters; **`Approve`** applies the change (a card containing a delete stays disabled until expanded once), **`Reject`** discards it with no change to the model. Toolbar **`Approve all safe`** clears purely-additive cards in one click and **`Approve all ⚠`** drains everything after one confirmation that names the deletion count; both go oldest-first. A queued change that the model has moved past since it was proposed is rejected as **stale** rather than applied blindly. New gated changes appear live, no refresh needed.

- **Optional `intent` parameter on `begin-batch` and `bulk-mutate`.** The agent can supply a plain-language "why" for a batch; when present it appears as a quiet, italic `agent's note:` line **below** the server-generated effect on the approval card — never replacing or outranking it, and **suppressed when hollow** (generic notes like "Updating the model" are dropped so vagueness never occupies the trust slot). Effect text is non-spoofable server ground truth; intent is a separate, lower-trust, suppressible claim — the two are never merged, and the server never depends on intent.

- **`resize-elements-to-fit` gains a `wrapFit` mode.** With `wrapFit: true` the tool keeps each element's width and grows only its height, so a long label wraps onto extra lines instead of being clipped or forced into an over-wide box — useful for nested labels in fixed-width containers. (After a parent grows to contain a wrapped child, follow with `auto-route-connections`.) Default behaviour is unchanged.

- **`get-view-contents` graph nodes and edges now carry their visual identifiers.** Nodes include a `viewObjectId` and edges a `viewConnectionId`, so a visual returned by a query can be fed straight into `remove-from-view`, `update-view-object`, or `update-view-connection` without a second lookup to resolve the visual id.

### Security

- **Origin/Host header validation, on by default.** The embedded server now rejects (HTTP 403) any request whose `Host` header — or `Origin`, when a browser sends one — is not a loopback name, closing the DNS-rebinding / malicious-web-page vector that could otherwise drive the MCP tools from a page in your browser. Enforced in front of both the `/mcp` and `/sse` transports. Zero configuration change for existing users: every localhost client (Claude CLI, Cline, `mcp-proxy`) already connects via `127.0.0.1` / `localhost` and is unaffected. Validation is relaxed automatically when you deliberately bind to a non-loopback address (that advanced case is governed by network/firewall and token controls instead).
- **Opt-in bearer-token authentication.** You can now require an `Authorization: Bearer <token>` header on every request. Enable it in **Window → Preferences → MCP Server → Authentication**: a 256-bit token is generated on first opt-in, stored in Equinox secure storage (the same OS-keychain-backed store Archi itself uses — no separate password), and shown with a **Copy** button and a **Generate / Regenerate** action. When enabled, both the `/mcp` and `/sse` transports reject any request with a missing, malformed, or wrong token with HTTP `401` (constant-time comparison; JSON-RPC error envelope; `WWW-Authenticate: Bearer` challenge). **Off by default — zero change for existing users** until you turn it on; if enabled but the token can't be read, the server fails closed (rejects everything) rather than serving unauthenticated. Composes with the Origin/Host validation above. See the README "Enabling authentication" section for client configuration (`claude mcp add … --header`, `mcp-proxy --headers`).
- An in-context exposure warning now appears on the preferences page when the server is bound away from `127.0.0.1`; once a bearer token is enabled, that warning softens to an advisory noting the exposure is mitigated (and recommending TLS so the token is not sent in cleartext).
- **TLS keystore password moved out of the plaintext preference store into Equinox secure storage.** When TLS is enabled, the keystore password is now stored encrypted in your OS keychain (the same store the bearer token and Archi itself use — no separate password to manage), instead of in cleartext in the workspace `.metadata` preference file where an automated secret scanner would flag it. The preferences field is now masked. Any keystore password set in an earlier version is migrated automatically and fail-safely on first start — read once, written to secure storage, and only then cleared from the plaintext store; if secure storage is unavailable (e.g. a locked or lost keychain), the old value is left untouched so TLS keeps working and the migration simply retries next start. No configuration change and no behaviour change for existing TLS setups.
- **Approval mode is now human-owned — the agent can no longer ungate itself.** A self-ungating safety control is a lie to the user, so the control plane has moved to the human and the agent's path to it no longer exists. The `set-approval-mode` (toggle) and `decide-mutation` (approve/reject) MCP tools are **removed entirely** from the surface — not guarded, removed, because the only robust guard is non-existence. The on/off toggle now lives in Archi (the checkable **MCP Server → Approval Mode** menu item), written only from the desktop UI; turning the gate *off* requires a confirmation, turning it *on* is a single click. Your setting is **remembered across restarts** (stored in MCP preferences); a fresh install defaults to **GATED** (fail safe). The agent keeps a **read-only** view of the mode (a new `approvalMode` field on `get-model-info`) and the read-only `list-pending-approvals` observation tool, so it can honestly tell you "you're gated — confirm in Archi" instead of silently failing. Approve/reject moves to a UI-callable service the desktop binds to. _(Together with the Pending Approvals view, this forms the full human-in-the-loop gate.)_
- **Agent undo/redo is scoped to the agent's own changes.** Agent-authored CommandStack entries are origin-tagged, and the `undo`/`redo` tools stop at — and refuse to cross — any human edit on the stack, so an agent can never silently revert your hand-drawn work (to reverse a human change it must submit a new proposal). Your own native `Ctrl+Z` in Archi remains unscoped and still undoes anything.
- **Request-size cap, idle timeout, and a bounded thread pool on the embedded server.** The embedded Jetty server now rejects oversized request bodies (~32 MiB cap, enforced on both declared `Content-Length` and actual streamed/chunked bytes) with HTTP `413` rendered as a JSON-RPC error envelope, drops connections idle past 120 s, and runs on an explicit bounded worker pool (8–50 threads) instead of the implicit default-200 pool. Closes the gap where a single giant request body could exhaust memory and take down Archi along with your unsaved model. The limits are fixed safety-bound constants, not preferences; no configuration or behaviour change for normal use.
- **Per-session state is now bounded by an idle TTL.** MCP sessions, their caches, and batch contexts were previously kept forever, so a client fabricating session IDs (or a long-running install) could leak memory without limit. Sessions and caches idle past a 24-hour TTL are now evicted on an opportunistic write-path sweep (no background thread); a batch's context is dropped when it ends, but only when no approval proposals are still pending, so the pending-approval queue is never silently discarded. Active sessions are never evicted mid-conversation, and the default session is never evicted.
- **Remote image downloads are now bounded before buffering.** When a tool fetches an image from a URL, the response is streamed into a single fixed buffer that aborts the instant it would exceed the 1 MiB cap, and an overall download deadline is enforced between reads. Previously the whole body was buffered *before* the size was checked, so a chunked or `Content-Length`-less oversized response — or a slow-drip "slowloris" body — could exhaust memory or pin a worker. Allocation is now bounded regardless of what the remote server sends.

### Changed

- **Approval mode is now a single global switch, not per-MCP-session.** Previously each MCP session carried its own approval flag; with one human owning one desktop gate, that is now one plugin-wide state — two concurrent sessions see the same mode. Pending proposals remain per-session. This is the only model consistent with a human-owned control plane.

### Removed

- **`compute-layout` removed.** The legacy graph-layout tool (Zest tree / spring / directed / radial / grid presets) is gone; its role is superseded by `auto-layout-and-route` (ELK Layered), which both positions elements and routes connections in one call. Removing it also resolves a startup failure on **Archi 5.10**, whose bundled graph-layout library otherwise made the entire MCP tool surface fail to load. This is the `72 → 71` part of the tool-count change.

### Fixes

- **Server startup failures are now self-diagnosable from the status message.** Two common desktop failures were previously reported as a generic `SERVER_START_FAILED`: a port-in-use error nested more than one level deep in the cause chain, and — under TLS — a keystore load failure that the pre-flight validation cannot catch (wrong password, or a corrupt/empty/wrong-type keystore file, since Jetty loads the keystore during start). They are now classified as `PORT_IN_USE` and `INVALID_TLS_CONFIG` respectively, reusing the existing error codes and status-message mapping, so you can tell *why* the server did not start without reading the log. A guard keeps unrelated runtime failures generic rather than mislabelling them. No manager, UI, or wire change.

- **`assess-layout` hub-port quality now reports the worst face, not the average.** The M5 hub-port-quality metric (HPQ) averaged across an element's connection faces, which let one badly-distributed face hide behind well-distributed ones; it now reports the minimum (worst) face, so a degraded hub is no longer mean-diluted in the score. This changes the HPQ value an agent reads back from `assess-layout` on hub-heavy views.

### Documentation

- **`SECURITY.md` — the responsibility boundary, made citable.** A new top-level `SECURITY.md` states what the server protects against by default (loopback bind, Origin/Host validation, request/session/image resource limits, the human-owned fail-safe-GATED approval gate, agent-scoped undo, secrets in the OS keychain) versus what is the operator's responsibility (transport encryption, client authentication, securing a non-loopback bind, the prompt-injection backstop, and the not-yet-allowlisted filesystem paths), with a trust-boundary diagram, a supported-versions note, and a private vulnerability-reporting process via GitHub Security Advisories.

## v1.6.0 (2026-05-29)

Refinement release. v1.6 broadens `layout-within-group` to ArchiMate-element containers, completes `get-view-contents` read-back parity (styling fields plus element-container tree nesting), and fixes three verify-after-mutate gaps in `remove-from-view`, `auto-route-connections`, and `bulk-mutate` diagnostics. No new tools or resources — tool count is unchanged at **72**, resource count at **14**. Every change is additive and wire-compatible: responses are byte-identical to v1.5 for any input that did not exercise the changed behaviour.

### Features

- **`layout-within-group` now arranges children inside any container view-object, not just visual groups.** ArchiMate-element containers — `ApplicationComponent`, `Node`, `ApplicationFunction`, and any other element that holds nested children — are now accepted alongside native visual groups. The same `arrangement` (row / column / grid), `spacing`, `padding`, `columns`, `autoResize`, and `autoWidth` semantics apply unchanged. This removes the need to hand-compute positions for nested children such as ApplicationFunctions inside ApplicationComponents, or SystemSoftware and Artifacts inside Nodes. The tool name, parameters, response shape, and error codes are unchanged; only the set of accepted containers broadens. Notes, view-references, and connections are still rejected as containers, per the coordinate model.
- **`get-view-contents format=tree` now descends ArchiMate-element-container nesting** the same way it already descends visual-group nesting. When an `ApplicationComponent`, `Node`, or any other element node has children nested inside it (placed via `add-to-view` or `bulk-mutate` with the element's view-object ID as the parent), those children appear in the parent element node's `children` array with a `childCount` field — exactly as group nodes already render. Agents discovering layoutable containers through the tree view now see element containers structurally before reaching for `layout-within-group`. The tree wire shape is unchanged for views without element-container nesting; element nodes emit `children` and `childCount` only when they actually contain children.

### Read-Back Parity

- **`get-view-contents` now surfaces every v1.5 styling field that the add-/update-tools accept** — `labelExpression`, `figureType` / `textAlignment` / `verticalTextAlignment`, `fontName` / `fontSize` / `fontStyle`, `gradient`, `borderType` (notes only), `deriveLineColor`, `outlineOpacity`, and `lineStyle` — on `ViewNodeDto`, `ViewGroupDto`, and `ViewNoteDto`, plus typography and `labelExpression` on `ViewConnectionDto`. Agents that write the v1.5 styling surface via `update-view-object` or `update-view-connection` can now read the post-mutation state back through `get-view-contents` and confirm the styling actually landed, instead of trusting the write tool's request echo. Wire format is byte-identical to v1.5 for default-styled view-objects — every new field is omitted when unset (`@JsonInclude(NON_NULL)`).

### Fixes

- **`remove-from-view` now actually removes nested ArchiMate-element view-objects** — those placed inside another component, node, or group via `parentViewObjectId` — instead of silently doing nothing while still returning `{action: "removed"}`. The element-removal path now resolves the real immediate parent container, matching the group and note paths, so nested ghost view-objects no longer persist on the canvas, in `assess-layout`, or in the saved `.archimate` file. A postcondition guard now fires if the underlying removal does not take effect, converting any future regression into a structured `INTERNAL_ERROR` that names the parent and the object — rather than the previous silent no-op reported as success.
- **`auto-route-connections` now self-heals the "exit-then-return" terminal zigzag** — a connection that overshoots past its target's far edge and then doubles back to attach (for example, routing up past the top of a box, then down to its bottom face). Previously the reversal-elimination pass detected the overshoot but could remove a terminal anchor while collapsing it, which caused the terminal-anchor guard to roll the whole straightening pass back — so the cosmetic defect survived and only a full `auto-layout-and-route` re-layout could clear it. The pass now confines its collapse to the route interior, leaving both terminal attachment points byte-identical, so re-running `auto-route-connections` removes the overshoot in place. When a foreign element genuinely blocks the straightened corridor, the pass correctly declines and leaves the route untouched. Behaviour is unchanged for every route that did not carry this defect.
- **`bulk-mutate` back-reference errors now distinguish self-reference from forward-reference.** A `$N.id` that points at operation N itself — a create tool cannot reference its own not-yet-created result — now produces a different, actionable message from a `$N.id` that points at a later operation, with a "Did you mean `$(N-1).id`?" suggestion when a previous operation exists. The tool description also clarifies the 0-indexed back-reference semantics. Both cases still reject with `INVALID_PARAMETER`; only the diagnostic text changes, so an agent can tell an operator off-by-one apart from a forward-reference mistake on the first response.

## v1.5.0 (2026-05-28)

Authoring completeness. v1.5 adds four new tools — `add-image-to-view` (place a standalone image as a diagram node), `add-view-reference-to-view` (embed one view inside another), `update-model` (write model name, purpose, and properties), and `find-concept-usage` (reverse where-used lookup before deletes and renames) — plus broader Archi-GUI styling coverage on view objects and connections (typography, gradient, alignment, line style, opacity), two new `export-view` formats (PDF and JPG, plus a real SVG instead of the previous stub), and a batch of routing and validation fixes. Validated end-to-end on a fresh 221-element reference model — 11 of 11 views rated good or better, 8 excellent. Tool count grows from 69 to **72**; resource count is unchanged at 14.

### New Tools

- **`add-image-to-view`** — Place a standalone image as a first-class diagram node on a view, sibling to notes, groups, and view-references. Distinct from the existing `update-view-object` `imagePath` parameter, which sets an icon overlay on an element. Requires `viewId` and `imagePath` (returned by `add-image-to-model` or `list-model-images`). Optional `x`/`y` (both-or-neither, parent-relative when `parentViewObjectId` is set), `width`/`height` (default: the image's natural dimensions read from the model archive; falls back to 200×200), and the full visual styling surface (fill / line / font colour, opacity, line width, line style, gradient, alignment, border type) plus image-specific `borderColor` and `documentation`. Typo'd `imagePath` values are rejected with the new `IMAGE_NOT_FOUND` error rather than silently rendering as a broken-image placeholder. Image visuals are bulk-mutate-callable and now round-trip via `get-view-contents` in a new `images` array.
- **`add-view-reference-to-view`** — Embed one ArchiMate view inside another as a clickable thumbnail — the agent-driven equivalent of Archi GUI's drag-view-onto-view. Useful for landscape views that embed each layer view, index views that link every viewpoint, and cross-cutting documentation views that reference detail views. Requires `viewId` (target) and `referencedViewId` (source — must be an existing ArchiMate view in the same model). Optional bounds, parent nesting, and the full visual styling surface. The referenced view's name is not stored on the visual; Archi reads it dynamically at render time, so renaming the referenced view via `update-view` updates every embedding automatically.
- **`update-model`** — Write the loaded model's own `name`, `purpose`, and custom `properties` as a single undo unit (mirrors the shape of `update-view`). At least one of the three must be provided; omitted fields stay untouched. Empty-string `purpose` clears the field; null property values remove a key. Archi 5.7/5.8 exposes a single free-text field on the model — `purpose` — so there is no separate `documentation` parameter. `bulk-mutate` accepts `update-model`.
- **`find-concept-usage`** — Reverse where-used lookup: given an element or relationship ID, returns every view and every visual object or connection that references it across the model. The inverse of `get-view-contents`. Intended for impact analysis before `delete-element`, `delete-relationship`, rename, or re-type workflows — one round-trip reveals the full cross-view footprint. Placements are grouped by view; each view carries a `viewKind` (`archimate` / `sketch` / `other`) plus `viewReferenceCount` and `visualReferenceCount`. Views are ordered by name, visual objects by ID — deterministic regardless of underlying iteration order.

### Read / Write Parity

- **`get-model-info` now returns `purpose` and `properties`** — read-side companion to `update-model`. Existing callers see byte-identical responses on default-state models; the new fields appear only when set.
- **`list-specializations` now returns `imagePath`** — surfaces the archive path of the specialization's icon when one is set; omitted otherwise.
- **`get-view-contents` now returns an `images` array** — image visuals (placed via `add-image-to-view`) round-trip on view reads. The DTO carries the visual's ID, image path, bounds, parent, border colour, and documentation.

### Existing Tools Extended

- **Relationship semantic attributes on `create-relationship` and `update-relationship`** — three new type-conditional optional parameters fill out ArchiMate semantics that the create/update path previously could not set:
  - `accessType` (AccessRelationship only) — enum: `"access"` (unspecified), `"read"`, `"write"`, `"readwrite"`.
  - `associationDirected` (AssociationRelationship only) — boolean.
  - `influenceStrength` (InfluenceRelationship only) — free text, max 255 characters; empty string clears.

  Supplying a parameter on the wrong relationship subtype is rejected at the boundary with a `suggestedCorrection` naming the valid type. The three fields populate on the response DTO only when the relationship is of the matching subtype, so JSON shapes for relationships of any other type are unchanged. The new fields automatically appear on every read surface (`get-relationships`, `search-relationships`, `get-view-contents`, `find-concept-usage`).
- **Specialization icons on `create-specialization` and `update-specialization`** — both tools accept an optional `imagePath` (an archive path from `add-image-to-model` or `list-model-images`). When set, Archi renders this image as the specialization's icon on every element or relationship of that specialization. `update-specialization` also accepts `clearImagePath: true` to explicitly clear the icon (mutually exclusive with `imagePath`). `update-specialization` has relaxed `newName` from required to optional — at least one of `newName`, `imagePath`, or `clearImagePath` must now be supplied.

- **`export-view` PDF, JPG, and a real SVG** — `export-view` now accepts `format: "pdf"` (vector, print-ready) and `format: "jpg"` (lossy raster) in addition to `png` and `svg`. ### Fixes

- **`add-to-view` and `update-view-object` now reject typo'd `imagePath` values with `IMAGE_NOT_FOUND`** — closing the gap between these surfaces and `add-image-to-view`. Previously, a typo'd archive path on `add-to-view` or `update-view-object` (also via `bulk-mutate`) was accepted at the prepare boundary and rendered as a broken-image placeholder downstream, with no error envelope for the agent to act on. The validator added in v1.5 for `add-image-to-view` / `create-specialization` / `update-specialization` is now wired into the four `add-to-view` / `update-view-object` prepare paths, producing the byte-identical `IMAGE_NOT_FOUND` reject payload across all three tool surfaces. Empty-string `imagePath` on `update-view-object` remains the documented "clear the icon" sentinel and is not validated.
- **`auto-connect-view` now skips connections between an ancestor and its descendant on the view** (which would render as a self-pass-through), reporting them under a new `skippedDueToNesting` field on the response DTO. The model relationship is preserved; the agent can choose to draw it explicitly via `add-connection-to-view` if desired. This closes a gap where the tool was creating exactly the `M4 connectionEdgeCoincidence` defect class that `assess-layout` is built to catch. Sibling-pair, cross-branch, and flat-view behaviour are unchanged.
- **`auto-route-connections` now surfaces autoNudge-blocked recommendations under a new `blockedRecommendations` field with a top-level `nudgeBlockedReason` (`"sibling_overlap"`), reserving `recommendations` for the advisory (`autoNudge=false`) path.** Previously, an `autoNudge=true` call against a view with overlapping sibling elements returned `recommendations` populated AND `nudgedElements` empty — a mixed signal the agent had to disambiguate via `structuredWarnings`. The underlying refuse-to-nudge behaviour is unchanged; the `AUTO_NUDGE_SKIPPED_SIBLING_OVERLAP` structured warning continues to emit in parallel.
- **`delete-view` now cascades view-reference visual placeholders correctly** — when a view that was embedded in other views (via `add-view-reference-to-view`) is deleted, the visual placeholders pointing at it across the rest of the model are now removed atomically with the view, mirroring Archi GUI's tree-delete cascade. Without the cascade, the EMF cross-reference stayed resolvable in-memory (so the live MCP session saw no problem) but `.archimate` save+reload wrote a dangling reference and Archi could not reopen the file with an "Unresolved reference" error. Reproduced against a real model on 2026-05-27. Latent in `delete-view` since v1.0 but only newly exploitable in v1.5, because v1.5 added the first MCP path to *create* view-reference visuals. Placeholders contained inside the view being deleted are correctly skipped (they die with the view).
- **`auto-route-connections` source-side reversal on lane-crossing hand-off** — when a connection crossed a swimlane boundary at a hub or anchor, the late-stage terminal-egress clearance passes treated the endpoint's ancestor container as an obstacle, occasionally reversing the source-side terminal segment. The clearance passes now mirror A*'s ancestor-exclusion rule, so the endpoint container is no longer in the obstacle set during clearance — the connection routes from the inside of its container out, matching the GUI's manual-routing result.
- **`auto-route-connections terminals-only` mode interior-termination and zigzag vetoes** — the terminals-only rectification no longer leaves a route in a worse state than it found it. A rectification that would introduce an interior termination or convert a clean L-bend into a zigzag is now vetoed and the original terminal is preserved.
- **`get-view-contents format: "graph"` no longer crashes on views with groups or notes** — the graph-format converter was assuming every view object was an element-bearing node, and threw on groups and notes. It now emits them as the documented graph nodes.
- **`bulk-mutate` operation-cap contract reconciled** — the `operations` array's own parameter description advertised "Max 50 operations" while the schema, the tool-level description, and the enforced limit all said 150 (the limit was raised in v1.2). Agents read the param description closest to the array and self-throttled to ~48-op batches. Both surfaces now derive the cap from the same constant. No behavioural change — the enforced limit was, and remains, 150.
- **`bulk-mutate` supported-tools list completed** — the tool advertised two incomplete supported-tools enumerations: the parameter description named 10 of 24, and the tool-level description named 12 — both omitting high-value mutations like `delete-element`, `update-relationship`, `update-view`, and the folder and specialization tools. An agent reading either list could wrongly conclude those tools were not bulk-callable. Both descriptions now derive from the same source of truth and list every supported tool. No behavioural change.
- **`update-view-connection` no longer falsely reports "Connection bendpoints cleared" on styling-only updates** — the next-steps message now distinguishes bendpoints-cleared, bendpoints-set, and styling-only changes accurately.

## v1.4.0 (2026-05-21)

Routing-perception cycle. v1.4 reworks how layout quality is *measured* so the rating reflects what an architect actually perceives, and lifts the LLM-facing precondition surface so an agent can set a view's geometry up correctly *before* routing. Tool count grows from 65 to 69; resource count grows from 7 to 14. The metric acronyms used below — M1–M6, R8, `parallelConnectionGap_V_p10`, HPQ — are defined in the [glossary](docs/glossary.md).

v1.4 delivers improved layout and routing compared to v1.3, validated end-to-end by an LLM agent driving the tools to build a comprehensive multi-view reference model.

### New Tools

- **adjust-view-spacing** — Inflate inter-element and inter-group spacing on an existing view, then re-route, in a single atomic operation. Use it when a view is laid out correctly but looks cramped, without re-running layout from scratch and losing manual placement.
- **apply-element-spacing-recommendations** — Widen within-group element spacing until the view reaches good quality, is honestly flagged as needing a structural reflow, or the iteration budget runs out. Runs an internal control loop — take a small step, re-assess, then continue, escalate, or stop — and reverts any step that makes things worse. Returns before/after `assess-layout` snapshots plus `terminationReason`, `iterationCount`, and `appliedDeltas`. Set `dryRun: true` to preview. One call is one undo step.
- **apply-group-spacing-recommendations** — The same control loop applied to inter-group corridors only, preserving group order and topology.
- **apply-spacing-recommendations** — Runs both arms (element, then inter-group) in one transactional call. The `scope` parameter (`both` / `element` / `group`) selects which arm(s) run. Per-iteration step caps prevent over-inflation; per-arm termination reasons, iteration counts, and applied deltas are reported.

### Routing Preconditions (LLM-Facing Surface)

A precondition is a property of the view's geometry that must hold *before* routing — the pipeline can refine routes but cannot create hub sizing, spacing, or group arrangement. v1.4 makes the three load-bearing preconditions first-class.

- **Control loop with density-aware termination** — The three spacing tools no longer apply one delta and return; each iterates internally and stops honestly. A step that degrades the view is always reverted, so the tool never returns a silently-worse view *(Superseded in v1.9 — that guarantee was true only of the loop's own step scalar, which is narrower than `overallRating`; see the v1.9 entry on the spacing tools reporting a rating regression. The sentence is left as written because it records what v1.4 claimed.)*
- **Sound infeasibility certificate** — When a view is provably too dense for spacing to fix, the tool stops, reports the reason, and offers a user-consentable structural reflow instead of churning. It never reflows on its own — a reflow moves user-placed elements, so it is the user's decision.
- **`archimate://prompts/routing-preconditions-checklist` (new resource)** — The single checklist an agent fetches before `auto-route-connections` or `auto-layout-and-route` on a non-trivial view: three preconditions, one verification each, plus a matrix mapping view shape to precondition order.
- **Density-aware defaults** — `arrange-groups` and `adjust-view-spacing` derive a connection-count-aware spacing default when none is supplied, instead of a static value. Pass an explicit value to suppress.
- **`assess-layout` names the fix** — When the assessment finds a violation that maps to a precondition (low hub-port quality, edge-coincident segments on a grouped view, children outside a parent's bounds), the `nextSteps` envelope names the right tool and attaches the violator IDs.
- **Structured warnings on `auto-route-connections`** — The response carries a machine-readable `structuredWarnings` list (`code`, `message`, `remediationTool`, `remediationViolatorIds`) alongside the free-text warnings, so an agent can act deterministically.

### Assessment (Perception-Aligned)

`assess-layout` gains metrics for defect classes the old assessor could not see. See the [glossary](docs/glossary.md) for each metric and the [Layout Engine](docs/layout-engine.md) doc for thresholds.

- **New metrics** — M2 interior terminations, M3 zigzag/reversal, M4 connection-vs-edge coincidence, M5 hub-port quality (HPQ), and R8 corridor utilisation. M1 (non-orthogonal terminals) is corrected to count only the visible portion of a diagonal, ending an over-report.
- **Two-dimensional rating (M6)** — The overall rating now reports `(layoutTier, routingTier)` and takes the worse of the two, so a routing fix on a well-laid-out view no longer drags its layout tier down.
- **Re-anchored cut-points** — Any sibling overlap now caps the layout tier at `poor`, and a parent label obscured by a child is promoted into the rating — both align the score with the perception that a single visible defect reads as a broken view.
- **Informational narrow-corridor signal** — `parallelConnectionGap_V_p10` surfaces when a view is in the narrow-corridor regime, so an agent can recognise that spacing tools cannot help and the remedy is structural. It does not affect the rating.
- **Classification precedence** — A connection already flagged as a pass-through is no longer also double-counted as a zigzag.
- **Density-aware non-orthogonal scoring** — Non-orthogonal terminals are scored by ratio rather than raw count (so connection-heavy views are not over-penalised) and treated as cosmetic, reflecting that diagonal terminals rarely affect comprehension.

### Tool Surface Additions

- **Group and element styling** — `add-to-view`, `add-group-to-view`, `add-note-to-view`, and `update-view-object` accept `figureType` (`rectangular` / `tabbed`), `textAlignment`, and `verticalTextAlignment`. These close v1.3 feedback that groups were always tabbed and labels always centred. Additive and non-breaking; existing calls are unchanged, and the new fields read back on `get-view-contents`.
- **Hub 2D-resize suggestion** — For elements with more than 12 connections, `detect-hub-elements` also suggests a two-dimensional resize so ports can spread across all four edges, not just one.
- **Hub-aware spacing** — The spacing tools select a wider spacing tier when a view contains hub elements, since formula-sized hubs consume corridor space.

### Layout Fixes (vs v1.3)

- **Text boxes reserve room for their text** — `add-note-to-view` and `add-group-to-view` size the box to fit wrapped content when the caller does not pin a height, so descriptive titles and long group labels no longer clip. Explicit sizes are unchanged; heights clamp to documented maxima.
- **Containers reserve their icon corner** — A container that carries a corner-anchored icon grows enough to keep the icon clear of nested children, preventing the icon-on-child overlap. Containers without an icon are unchanged.
- **`arrange-groups` reserves a lane for standalone hubs** — Topology row/column arrangement now centres a top-level element that connects across multiple groups in an inter-group lane between its neighbours, delivering the "place it between the zones" layout the viewpoint recipes describe.
- **Parent groups resize to contain their children** — A child moved outside its parent group's bounds now triggers a parent resize, across all three paths that can move a child (auto-nudge, the spacing tools, and direct object update). Closes a long-standing defect where a group was left too small for its contents.

### Routing Fixes (vs v1.3)

- **Self-element pass-throughs resolved** — A connection whose route looped back through its own source or target is now corrected algorithmically. This closes a user-visible issue present since v1.0.
- **Terminals-only routing mode** — `auto-route-connections` accepts `mode: "terminals-only"`, which rectifies only the diagonal terminal segments of automatic-layout output without re-routing whole connections — avoiding the crossing inflation a full re-route causes on that input.

### Routing Pipeline Improvements (vs v1.3)

These pipeline improvements deliver better routing than v1.3 across the reference views, and are protected by regression tests:

- Seeded multi-start routing — picks the best of several candidate routes, and is never worse than the single-shot route by construction.
- Hub-perimeter and terminal-segment corridor handling for multi-bendpoint routes.
- Channel-global ordered nudging that spreads parallel segments across whole channels, including inter-group corridors.
- An invariant that locks a connection's perimeter-terminal face through the whole pipeline, preserving hub-port distribution end-to-end.

### Viewpoint Recipes

- **Recipe library (six new resources)** — A progressive-disclosure library under `archimate://recipes/*`. Fetch `archimate://recipes/index` first; it states the build sequence once, routes conventional viewpoints to the existing view-patterns principles, and points non-conventional viewpoints (application integration, behaviour/process flow, motivation, technology deployment, roadmap/migration) to a single recipe page with a topology block to match.
- **Element-type and nesting guidance** — The view-patterns and layers references are sharpened so an agent picks the right element type (Component vs Service, Process vs Function, Node vs Component, Actor vs Role) and nests structural parts instead of drawing a redundant Composition or Aggregation connector. These target recurring v1.3 reports of wrong element type and drawn-instead-of-nested composition.

## v1.3.0 (2026-04-10)

Expressiveness cycle. Adds first-class support for ArchiMate **specializations** (IS-A subtypes of element and relationship types) across the read, write, search, and resource surfaces. Tool count grew from 60 to 65. Also bundles a batch of layout, assessment, and routing-quality enhancements discovered during E2E validation runs.

### New Tools

- **list-specializations** — List every specialization defined on the model with `(name, conceptType, layer, usageCount)`. Optional `conceptType` filter narrows the result to a single concept binding.
- **create-specialization** — Define a specialization explicitly without creating any element. Idempotent — returns the existing specialization on duplicate `(name, conceptType)`. Use this to pre-register a vocabulary at session start.
- **update-specialization** — Rename a specialization. Refuses to merge into an existing target name (collision-rejecting). Existing references on elements and relationships move with the rename.
- **delete-specialization** — Remove a specialization. Refuses by default if any concept uses it; pass `force: true` to detach all references and delete in one atomic command. Refuses force-delete on concepts that carry more than one specialization (clear the extras first).
- **get-specialization-usage** — Pure query. Lists every element and relationship referencing a specialization. Call before rename or delete to audit the blast radius.

### New Capabilities

- **Inline specialization on element and relationship mutations** — `create-element`, `create-relationship`, `update-element`, and `update-relationship` accept an optional `specialization` parameter. On create, the specialization is auto-created if missing — the element/relationship and the specialization land in one CompoundCommand (single undo unit). On update, pass an empty string `""` to clear all specializations from the concept. Source, target, and type remain immutable on relationship updates.
- **Specialization filter on search** — `search-elements` and `search-relationships` accept a `specialization` filter that returns only concepts of the given specialized type. Combines with existing `type`, `layer`, and text filters.
- **specializationCount on `get-model-info`** — Model overview now reports the total specialization count. Non-zero means the model uses a custom vocabulary; call `list-specializations` to browse it.
- **`specialization` field on `ElementDto` and `RelationshipDto`** — Query responses now expose the primary specialization name on every element and relationship DTO. (See "Multi-Profile Caveat" in the new resource for the single-primary semantics.)
- **Connection styling on `auto-connect-view`** — `auto-connect-view` accepts `lineColor`, `fontColor`, and `lineWidth` parameters, applied uniformly to every connection it creates. Combines with `relationshipTypes` to batch-style connections by relationship type in a single call (e.g. blue for API calls, orange for domain events).

### Routing Pipeline Improvements

- **Self-element pass-through rating tolerance** — Self-element pass-throughs (a connection's route entering its own source or target through an interior point rather than from an edge) no longer penalise the overall layout quality rating. Cross-element pass-throughs still penalise as before. Informational reporting is preserved for both types — `assess-layout` still surfaces the count, but the rating reflects only structurally meaningful violations.

### Layout Improvements

- **Containment-aware dynamic label height in `resize-elements-to-fit`** — Replaces the fixed 25px containment top margin with a per-parent label height computed from SWT font metrics and word-wrap simulation. When a parent element wraps its label across multiple lines, children are shifted down to clear the full label height instead of being obscured by the lower lines. Parent height never shrinks during the operation — only grows to accommodate the wrapped label and its children.
- **Element-count heuristic for grouped layout intra-group arrangement** — `auto-layout-and-route` with `mode: "grouped"` and `optimize-group-order` now choose intra-group arrangement based on element count and flow direction. For vertical flow (DOWN/UP): 1-3 elements arrange as a row, 4+ elements arrange as a grid. For horizontal flow (RIGHT/LEFT): column arrangement is preserved. Replaces the previous hardcoded column arrangement that produced 1:12 aspect ratio strips on vertical-flow grouped views.

### Assessment Improvements

- **Violator IDs for targeted fixes** — `assess-layout` accepts a new optional `includeViolatorIds` parameter (default `false`). When enabled, the response includes a `violatorIds` map keyed by metric name, each containing the list of visual object IDs that violate that metric. Supported metrics: `overlaps` (both element IDs per pair), `passThroughs` (connection IDs, cross-element only), `coincidentSegments` (connection IDs sharing corridors), `nonOrthogonalTerminals` (connection IDs with diagonal entry), and `boundaryViolations` (child IDs outside parent bounds). Crossings are excluded as an emergent property best addressed by global tools. The complete ID set is returned (no cap), enabling surgical per-element fixes without full re-layout.
- **Informational containment overlap suggestion** — When `assess-layout` reports containment overlaps (ancestor-descendant nesting), the suggestions list now includes an explicit informational note clarifying these are expected overlaps that need no action. Previously, the bare counter caused LLM consumers to interpret grouped views as broken.
- **Informational detections in `assess-layout`** — Three new detections appear in the assessment output but do not affect the overall rating:
  - **Label truncation** — word-wrap-aware vertical overflow check identifies elements whose label rendering exceeds the element bounds.
  - **Parent label obscured by child** — flags parent elements whose label area is overlapped by a child element. (Notes are excluded from this check.)
  - **Image sibling overlap** — flags elements with custom images that visually overlap sibling elements at the same containment level.
  These detections give LLM agents actionable signals to fix label and image quality issues without breaking the severity-tiered rating system.

### Bug Fixes

- **Bulk specialization profile deduplication** — Fixed a data-integrity bug where `bulk-mutate` creating multiple elements with the same new specialization (e.g. 8 `ApplicationComponent` elements all with `specialization: "Cloud Platform"`) produced duplicate specialization profiles — one per element in the batch — instead of sharing a single profile. Downstream operations were affected: `update-specialization` (rename) only renamed 1 of N references, `delete-specialization` only removed 1 of N, and `get-specialization-usage` understated impact. Root cause: bulk-mutate runs all prepare methods before dispatching any commands, so `resolveOrCreateProfile` could not find profiles created by earlier (not yet executed) operations in the same batch. Fix introduces a `ThreadLocal` bulk profile cache scoped to `executeBulk`, consulted before model lookup. Single-call (non-bulk) paths are unaffected.

### Resource Updates

- **archimate-specializations.md (new resource)** — Comprehensive specialization reference at `archimate://reference/archimate-specializations`. Covers identity rules (`(name, conceptType)` pair), the specializations-vs-properties decision table (do NOT use specializations for environment/version/owner/status), the full 9-step tool pipeline, common element specializations per layer, common relationship specializations, the bulk-mutate pre-registration pattern, the multi-profile caveat (primary-only semantics), and an end-to-end Cloud Server Technology landscape walkthrough. Total resource count grew from 6 to 7.
- **archimate-view-patterns.md** — Added "Specialization Hierarchy" entry to the Common Viewpoint Patterns table and a matching row in Layout Conventions by Viewpoint, cross-linking to the new specializations reference.

### Documentation

- MCP integration documentation updated with the new specialization tools and the new `archimate-specializations` resource.

Two-pass algorithm: children sized first, then parents sized to contain children + own label + padding. Recommended after placing elements without `autoSize` or when element names change.

### New Capabilities

- **Auto-size at placement** — `add-to-view` accepts `autoSize: true` to compute element dimensions from label text at placement time using SWT font metrics with aspect-ratio-aware sizing (target 1.5:1, range [1.2:1, 2.5:1]). - **Corridor diversity routing** — `CorridorOccupancyTracker` records which corridors are used by previously routed connections. The A* cost function applies a multiplicative penalty for occupied corridors (`effectiveDistance *= 1 + occupancyWeight * occupancy`, default weight 0.75), encouraging route diversity and reducing coincident segments without post-processing.

### Routing Pipeline Improvements

- **Occupancy-aware A* routing** — New `CorridorOccupancyTracker` (pure-geometry class) records axis-aligned corridor usage after each connection is routed. Corridor keys use tolerance-aware grouping (`H:y` / `V:x`, 2px tolerance) matching the `CoincidentSegmentDetector` and `PathOrderer` formats. The A* router queries occupancy per edge and applies a multiplicative cost: `effectiveDistance *= (1 + occupancyWeight * occupancy)`. This steers later connections away from corridors already carrying traffic, producing visually diverse paths and reducing the need for post-routing coincident segment resolution.

### Bug Fixes

Previously, legitimate visual nesting was incorrectly detected as sibling overlap, causing autoNudge to skip routing and report degenerate geometry.

### Routing Pipeline Improvements

- **Clearance-weighted A* routing** — A* cost function includes perpendicular clearance penalty (`clearanceWeight / max(clearance, 1.0)`, default weight 75.0) that steers the router toward open space. `computePerpendicularClearance()` measures distance from each graph edge to the nearest obstacle boundary. E2E result: crossings -41%, pass-throughs eliminated on test views.
- **Post-routing path straightening** — New `PathStraightener` class applies four correction passes after routing: snap-to-straight alignment for near-aligned segments, direction reversal elimination, staircase jog collapse, and redundant bend removal. Terminal anchors are protected throughout.
- **Post-simplification path shortcutting** — Late-stage greedy simplification (Stage 4.7g) finds farthest reachable point via straight line, horizontal-first L-turn, or vertical-first L-turn. Terminal bendpoints preserved as chain anchors. E2E result: crossings -27%.
- **Post-simplification coincident segment resolver** — Redesigned from endpoint-based (~350 lines) to corridor-based reuse of `CoincidentSegmentDetector` (~12 lines). Catches coincidences introduced by all post-processing stages. E2E result: coincident segments -50%.
- **Proportional corridor spacing** — Replaced fixed 10px offset delta with proportional gap distribution. Three-pass architecture: collect corridor groups, compute perpendicular gap via obstacle scanning, distribute segments proportionally with 8px minimum separation floor. Falls back to fixed-delta when corridor is too narrow. E2E result: coincident segments -80%.
- **Exterior perimeter routing** — Split obstacle clearance (10px) from perimeter boundary margin (50px), enabling routes to travel around the outside of element clusters. E2E result: routing success 12% to 100%.
- **Pass-through-aware face selection** — Phase 1.3 in `EdgeAttachmentCalculator` builds trial paths with current face assignments and checks for self-element pass-throughs. When detected, tries alternative faces in angular proximity order. Phase B re-routes terminal segments after face swap. E2E result: pass-throughs -75%.
- **Router corridor re-route** — Stage 5a re-routes failed connections (element crossings) using fresh A* search with the full pipeline cleanup sequence.
- **Terminal approach direction** — Phase 1.2 in `EdgeAttachmentCalculator` prefers natural entry direction for nearly-aligned elements (dominant axis > 2x minor axis). Hub elements excluded to preserve distributed port allocation.
- **Self-element pass-through correction** — Two-phase fix: face swap + comprehensive face selection with trial path validation. Safety net re-run of `correctEndpointPassThroughs()` retained as defense-in-depth.
- **Corridor directionality penalty** — Cosine-based `computeCorridorDirectionalityCost()` penalizes A* edges that move perpendicular or away from the target (`directionalityWeight * (1 - cos(angle)) / 2`, default weight 30.0). Steers connections toward direct approach paths. E2E result: non-orthogonal terminals reduced from 33 to 2 on Application Collaboration view.
- **Clearance cap** — `MAX_EFFECTIVE_CLEARANCE` (60px) caps the clearance benefit to prevent exterior corridors with unlimited space from becoming artificially attractive ("perimeter suction"). Clearance cost formula: `clearanceWeight / max(min(clearance, 60), 1.0)`.
- **Group-wall clearance cost** — `computeGroupWallClearance()` measures perpendicular distance from A* edges to the nearest group boundary. Edges running inside groups (close to group walls) are penalized, steering the router toward inter-group gaps rather than inside-group-wall corridors. Uses the same clearance weight and MAX_EFFECTIVE_CLEARANCE cap as obstacle clearance.
- **Center-termination fix** — Stage 4.7k `fixCenterTerminatedPath()` detects bendpoints at exact element center coordinates (zero-length ChopboxAnchor ray → visual center termination) and repositions them 1px outside the correct edge face midpoint. Applied twice: after edge attachment and as defense-in-depth after cleanup.
- **Post-nudge center-termination gap** — Re-runs `fixCenterTerminatedPath()` after edge nudging to catch center-terminations introduced by nudge position shifts.
- **Interior terminal BP fix** — Stage 4.7m `fixInteriorTerminalBPs()` detects and fixes all bendpoints inside source/target element bounds (not just at exact center). Terminal BPs are repositioned to edge face midpoints; intermediate interior BPs are removed. L-bends are inserted where repositioning breaks orthogonality.
- **Post-pipeline orthogonality enforcement** — Stage 4.7n `enforceOrthogonalPaths()` detects diagonal segments remaining after all processing and inserts horizontal-first L-turn bendpoints to restore orthogonality. Catches edge cases where cleanup stages remove BPs without reinserting L-bends.
- **Approach direction threshold relaxation** — Phase 1.2 `correctApproachDirection()` threshold relaxed from 2:1 to 1.2:1 dominant-to-minor axis ratio. More connections now receive natural approach direction correction, reducing diagonal terminal segments.

### Assessment Improvements

Tier 1 (critical): overlaps, pass-throughs, coincident segments — drives overall rating directly. Tier 2 (moderate): crossings, non-orthogonal terminals — contribution capped at "fair". Tier 3 (cosmetic): spacing, alignment, label overlaps — contribution capped at "good".

- **Relaxed leniency gate** — Grouped-view crossing leniency allows up to 3 pass-throughs (previously required 0).

- **Auto-nudge on route failure** — `auto-route-connections` with `autoNudge: true` automatically moves blocking elements and re-routes failed connections in a single atomic operation (up to 2 iterations).
- **Auto-nudge group boundary awareness** — When elements are nudged, parent groups resize to accommodate the new positions.
- **Router exit point centering** — Connection terminal segments now exit from the nearest edge center instead of using ray-to-first-bendpoint geometry, producing cleaner perpendicular exits.
- **Router snap-to-straight threshold** — Eliminates Z-bends for port offsets of 20px or less, producing straight connections where near-alignment exists.
- **Hub port distribution** — Edge attachment points for high-connectivity elements are distributed evenly across the element face, reducing connection bundling.
- **Routing quality guardrails** — Crossing inflation detection and 8px minimum bendpoint clearance enforcement prevent quality regressions.
